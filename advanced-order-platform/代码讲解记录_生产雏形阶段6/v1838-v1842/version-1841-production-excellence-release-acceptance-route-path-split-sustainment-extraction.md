# version-1841：发布验收路由拆分的持续维护层提取

本篇讲解对应本项目的 v1841。它不是新增一个看起来热闹、实际上难以验证的业务入口，而是把已经存在的“发布验收路由拆分持续维护”职责从根包中完整提取到独立维护包。这样做的价值有两层：第一层是保持现有接口、返回数据和只读边界完全不变；第二层是让后续维护者能够沿着“基础拆分、关闭确认、持续维护、验收归档”这条依赖链定位代码，而不用继续在一个拥有数百个同级类的目录中搜索。本文只解释真实实现与真实验证，不用重复句子填充篇幅，禁止硬凑。

这一版本可以用一条清晰的数据链理解：外部读取请求进入根包控制器，控制器调用已迁移的持续维护服务；持续维护服务先读取 v1840 提取出的关闭确认结果，再分别构造来源快照、所有权规则、漂移守卫、边界守卫、持续集成门、消费者交接和评分卡；支持类复制所有集合并计算检查清单与最终状态；响应对象把这些只读证据交给当前调用者，同时也成为下一版验收包的唯一上游输入。整个过程不写数据库、不调用部署、不解析凭据、不启动兄弟项目，也不会改变任何线上路由。

## 实际工作量说明

本版迁移了十九个非控制器生产类和四个包内测试类。十九个生产类并不是随意凑成的一组，它们共同组成一个可闭合的职责单元：一个服务负责编排，一个响应记录负责公开结果，一个支持类负责不可变复制和状态计算，六组目录与渲染器负责来源、所有权、漂移、边界、持续集成、消费者交接，另有评分卡目录、评分卡渲染器、总渲染器和渲染支持。把其中任意一半留在根包，都会产生反向依赖或迫使内部实现公开，因此本版以完整依赖闭包作为迁移单位。

根包中的直接生产文件由七百五十一个降至七百三十二个，仍待提取的非控制器文件由六百四十六个降至六百二十七个，发布验收路由拆分桶由五十五个降至三十六个。三个数字分别回答三个不同问题：根包是否持续变小、最终目标之外还有多少工作、当前三段式拆分是否按预定顺序推进。未归类文件保持为零，说明迁移没有把文件藏到统计脚本看不到的缝隙里；全部运维生产类总数仍受一千三百五十二的上限约束，说明本版没有通过复制类来伪造“提取”。

根包只保留持续维护控制器及其控制器测试。保留控制器不是因为迁移困难，而是当前架构把所有外部运维入口集中在根包，以便统一审查请求映射；实现细节则进入维护子包。这个边界让使用者仍能在固定位置找到入口，让维护者能在独立包中找到完整业务链。四个迁移测试分别验证目录内容、不可变响应、渲染结果和测试支持，它们与实现共享包级可见成员，不需要为了测试而扩大生产接口。

此外，本版同步更新了四处静态分析排除项中的响应类型全限定名。这里容易被误解为“为了绕过检查而改配置”，实际恰好相反：原有排除项描述的是该响应记录及其嵌套列表结构，类迁移后规则若仍指向旧地址，就会悄悄失效。守卫测试同时要求新地址存在、旧地址不存在，因此以后再次移动时必须显式处理，不能留下真假难辨的陈旧配置。

## 入口路由

入口仍由根包中的持续维护控制器提供。控制器在类级别使用共享基础路径，在方法级别使用持续维护注册表的相对路径，两者拼接成稳定的只读地址。v1840 已经把这一组发布验收路径集中到公开的专属路由所有者，本版控制器和服务都从该所有者读取常量，所以不存在两份容易漂移的字符串。

一次典型输入可以写成：调用方发起读取请求，请求中不携带部署指令、数据库语句或凭据值。控制器没有解析复杂参数，也不创建执行上下文，只调用服务的注册表方法。服务方法标记为只读事务，这既向 Spring 表达事务意图，也向代码评审者明确声明本链路不得通过持久化上下文修改订单、库存、支付或运维状态。

控制器返回的是持续维护响应，而不是内部目录类或渲染器。这样的入口有三个稳定点：请求地址不因包迁移改变；公开返回类型仍保持相同字段；控制器依赖的只有公开服务与公开响应。目录、渲染器和支持类继续保持包级可见，外部调用者无法跨层拼装一个绕过状态检查的响应。

若用通俗比喻理解，控制器像只负责收件和交件的窗口，服务像核验材料的工作人员，七组目录像不同栏目的核对表，支持类像最后盖章前的总校验。窗口本身不替材料造数据，也不会因为文件搬到另一个柜子就改变办理地址。

## 响应模型

持续维护响应是一个不可变记录。顶层先给出项目、版本、只读标记、执行许可、来源计划、上游关闭版本与地址、基础拆分版本与地址、当前地址和配置标识；随后给出每类证据的数量；最后给出七组结构化证据、渲染后的章节、检查清单和状态。调用者既可以读取结构化字段做机械判断，也可以读取渲染章节做人工审阅，不必从一段长文本中反向猜测结论。

结构化内容包括一份来源快照、六条所有权规则、六条漂移守卫、七条边界守卫、五个持续集成门、五个消费者交接项和八条评分卡记录。渲染结果固定为七个章节。这些数量不是文档中的装饰数字，支持类把它们写成预期值并在状态计算中逐项比较。少一项、重复一项或漏掉一个章节，最终状态都会从通过变为阻断。

支持类不会把目录返回的可变集合原样塞进响应，而是先逐一执行不可变复制。其意义在于：服务完成校验后，后续代码不能再通过持有原列表引用来增删条目，从而让“检查时通过、返回时已变”的时间差问题失去发生条件。响应中的嵌套记录也只承载值，不提供修改方法，因此输出适合被测试、序列化和下游只读消费。

输出示例可以简化为：只读标记为真，执行许可为假，来源关闭状态为通过；来源数量为一，所有权、漂移、边界、持续集成、交接和评分条目数量分别等于预期；检查清单记录稳定入口、禁止运行时执行、禁止凭据读取等事实；只有所有数量、来源版本和布尔门同时满足，状态才是通过。这里的“通过”表示证据包内部一致，不表示系统已经执行部署或获得生产写权限。

## 上游证据配置

本版唯一的业务上游是 v1840 已提取的关闭确认服务。持续维护服务调用其关闭方法，得到一个已经包含基础拆分版本、路由数量、兼容性检查和边界断言的响应。随后来源目录把这份响应压缩为一份来源快照，所有权目录根据它声明组件负责人和落盘位置，漂移目录把版本与数量写成锁定条件，边界目录把不可越过的执行能力写成明确条目。

这种单一上游很重要。假如持续维护层分别去根包读取十几个旧目录，它就会重新形成横向耦合，未来任何类迁移都可能牵动整个网状依赖。现在它只依赖关闭服务和关闭响应，v1840 是明确的生产者，v1841 是明确的消费者。下一版又只依赖本版公开服务与响应，于是依赖方向始终从基础事实流向更高层验收，不会倒流。

状态计算还核对两个历史版本锚点：来源关闭版本必须对应既定关闭契约，来源基础拆分版本必须对应既定拆分契约。锚点不是为了追逐当前 Git 标签，而是为了确认当前运行模型仍在解释原有只读协议。如果有人只改目录数量却忘记同步协议，或者把另一个不相干响应接进来，来源检查会失败。

上游只提供事实，不向本层授予能力。本层读取“路由有多少、兼容检查是否通过、边界断言是什么”，不会因为看到通过状态就获得写路由、连接审计库或执行回滚的对象。证据传递与能力传递被严格分开，这是本项目把运维可观测接口保持为只读面的核心机理。

## 服务层核心流程

服务方法首先调用关闭确认服务。若把这一步看作输入，输入不是用户随意提交的文本，而是一份由上游类型系统约束、已经经过自身规则计算的关闭响应。接下来七个目录函数都以该响应或前面生成的结构为参数，每个函数只负责一种语义，避免把所有逻辑堆进一个巨型方法。

第一步生成来源快照，保存来源名称、版本、地址、状态和所有权。第二步生成所有权规则，回答每个组件由谁负责、规则是什么、应该落在哪个包以及是否强制。第三步生成漂移守卫，回答观察哪个信号、预期值是什么以及是否锁定。第四步生成边界守卫，列出运行时执行、凭据、原始端点、审计连接、部署回滚和兄弟服务启动等能力是否关闭。

第五步形成五个持续集成门：聚焦持续维护测试、相关路由拆分测试、Java 全量回归、差异空白检查和远端流水线确认。这里保存的是应该执行的命令与范围，并不会从接口内部调用命令。第六步形成五个消费者交接项，声明谁可以读取、应如何使用、是否已准备好。第七步综合前述内容形成八条评分卡，只有来源、所有权、漂移、边界、持续集成、消费者、运行时关闭和拆分可维护性全部成立，评分卡才全通过。

总渲染器随后把结构化证据转换为七个便于人工阅读的章节。支持类对所有集合做不可变复制，计算包含数量与禁止事项的检查清单，再执行最终状态函数。状态函数有三组条件：数量必须完全匹配，来源状态和历史版本必须匹配，所有需要强制、锁定、必需、就绪或通过的布尔值都必须为真。三组条件以逻辑与连接，任何一组失败都返回阻断，不存在“多数通过就算成功”的模糊规则。

最后，支持类构造响应并返回。这个输出既供当前控制器序列化，也供下一层验收包读取。下游验收包不会绕过本层重新抓取关闭响应，而是调用本层公开服务，继续构造来源、谱系、决定、归档、复核、持续集成证据、运行边界和下一变更规则。这证明本次提取不仅让目录更整洁，也真正建立了一条可维护的层间契约。

## Java 证据检查

Java 侧的验证分为编译、聚焦测试、结构守卫、全量质量门和远端流水线五层。编译首先证明包声明、导入和可见性正确；如果内部类不该公开却被跨包使用，编译器会直接指出依赖方向。聚焦测试覆盖持续维护目录、不可变响应、渲染输出、控制器和测试支持，也回归 v1840 的拆分边界，避免本版只验证自己而破坏上游。

结构守卫逐个枚举十九个生产文件，要求新包存在且根包旧位置不存在，同时要求控制器仍在根包。它还读取真实源码，确认迁移服务依赖 v1840 关闭服务、来源目录依赖 v1840 关闭响应，并确认下一版验收包已经导入本版服务与响应。这样的断言比“某个目录文件数变少”更强，因为它同时固定位置和依赖方向。

计数守卫要求根包精确等于七百三十二，全部运维生产类不超过一千三百五十二；终局清单守卫还要求保留数为一百零五、待迁移数为六百二十七、未归类为零、当前拆分桶为三十六。历史版本的精确值会改成上界，而当前版本持有新的精确值，因此阈值只收紧，不会为了让测试变绿而回升。

静态分析配置守卫要求四处响应类型镜像全部指向新包，并禁止旧全限定名残留。维护性讲解守卫要求本文在全量验证前存在，包含固定标题、版本、本项目、禁止硬凑等语义，还会统计中文字符数量与中英文比例。最终全量验证再运行格式化检查、单元与集成测试、覆盖率门和静态缺陷扫描。远端提交触发的流水线是最后一层独立环境证据。

## mini-kv 证据检查

本版本不会启动、停止或修改 mini-kv。持续维护响应中提到兄弟项目，只是为了表达跨项目只读边界和后续消费者规则，不代表 Java 进程取得了执行 C++ 命令行、写入日志文件或改动快照的权限。服务实现没有进程启动器、网络客户端、文件写入器，也不接收 mini-kv 的凭据或原始地址。

因此 mini-kv 侧的输入是“无运行时输入”，输出也是“无运行时副作用”。Java 所能给出的机械证据是：边界目录包含禁止自动启动兄弟服务的锁定项，检查清单包含不自动启动 Node 或 mini-kv 的声明，评分卡要求边界全部锁定；代码扫描与测试则证明服务链只调用 Java 内部的关闭服务和纯目录函数。

如果未来要做真实跨项目验收，应由专门的、显式启用的联合测试命令负责，并在隔离环境中启动真实可执行文件、记录新鲜输出、验证退出码和清理进程。不能把那种执行能力偷偷塞进一个供运维人员读取的注册表接口。v1841 的责任是把“不得执行”的边界表达得可读、可测、可追踪，而不是假装已经完成联合运行验证。

## 阻断与安全边界

本层默认是只读并且明确禁止执行。响应的只读字段恒为真，执行许可恒为假。事务注解为只读，服务没有仓储写方法，目录只创建值对象，支持类只复制集合和计算状态。即使所有评分条目都通过，返回的也只是证据状态，不是操作令牌。

会触发阻断的情况包括：上游关闭状态不是通过；来源关闭版本或基础拆分版本改变；任一目录条目数量与预期不符；任一所有权规则未强制；任一漂移或边界守卫未锁定；任一持续集成门不是必需；任一消费者尚未就绪；任一评分条目失败；渲染章节缺失。阻断结果由同一个纯函数集中计算，调用者不需要猜测某个缺项是否严重。

边界守卫覆盖的禁止事项包括写路由、运行活动分片路由器、读取凭据值、解析原始端点、建立受管审计连接、部署与回滚、执行数据库语句，以及自动控制 Node、Java 或 mini-kv 进程。这里“Java 进程”指通过此证据接口额外拉起或停止另一个运行实例，不影响当前应用正常响应只读请求。

这种设计避免了一个常见风险：把观察面逐渐演变成控制面。观察面可以告诉维护者哪些门需要通过、当前证据来自哪里、哪些边界已锁定；控制面才有权修改配置和运行部署。v1841 只属于观察面。任何未来变更如果加入外部命令执行、凭据解析或写操作，都应被视为协议升级，必须另立安全设计和显式测试，不能借“维护便利”混入现有接口。

## 测试覆盖

目录测试验证六类目录和评分卡条目内容、数量及布尔状态，确保每一类证据都来源明确。不可变性测试验证返回集合不能被调用者修改，防止校验完成后数据漂移。渲染测试验证七个章节及关键文本，使人工阅读视图与结构化事实保持一致。控制器测试验证请求映射与返回形状，证明包迁移没有改变对外入口。

测试支持类跟随实现迁入新包并只公开下游测试确实需要的工厂方法。这样既避免复制复杂装配，也避免把生产内部目录为了测试全部改成公开。根包控制器测试通过导入公开测试支持继续工作，形成“生产最小公开面、测试明确桥接面”的可见性结构。

v1841 的新增机械守卫还检查迁移文件清单、旧位置消失、上游和下游导入、静态分析配置、根包精确计数、总量上限以及本文的版本化归档。聚焦门通过后仍要执行全量验证，因为订单创建、库存、支付、消息外发等核心业务虽然没有被直接编辑，Spring 扫描、静态分析和覆盖率仍可能受到包迁移影响。只有全量门通过，才能说明这次结构优化没有以业务回归为代价。

验证顺序也有意固定：先写实现和本文，再运行聚焦测试，最后运行全量验证。不能等测试通过后再补一篇与实际过程脱节的说明，也不能修改旧夹具字节或提高阈值来迁就迁移。若门失败，应修正包依赖、可见性、格式或证据缺口；测试期望只有在真实架构契约改变且有独立理由时才允许调整。

## 一句话总结

v1841 把十九个持续维护实现和四个同包测试完整移出根包，在不改变入口、返回结构与只读语义的前提下，将 v1840 关闭证据转换为可机械阻断、可人工审阅、可供 v1842 单向消费的维护契约，并用计数、依赖、静态分析、讲解、全量测试和远端流水线共同证明这次提取真实有效。
