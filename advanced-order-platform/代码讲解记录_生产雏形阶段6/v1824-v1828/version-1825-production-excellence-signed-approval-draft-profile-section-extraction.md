# v1825 代码讲解：先拆 ProfileSection 基座，再拆文本包与交接层

## 一、这一版到底在解决什么问题

这一版处理的是 Java 项目中 `ProfileSection` 相关代码的第一层，也就是
`SignedApprovalDraftProfileSection` 基础注册表。它的职责并不是生成订单、修改审批状态，
也不是把草稿真正写入存储，而是把五条已经存在的只读证据路由整理成一组稳定的“章节”。
每个章节记录来源版本、接口地址、配置标识、Node 对齐版本和只读状态，随后再生成字段清单、
Markdown 展示块以及路由字段锁。换句话说，它更像一张经过程序校验的目录卡：上游已经给出
五份材料，这里负责把材料排好顺序、标清来源、锁住关键字段，供后续文本包展示和交接流程读取。

过去这些类都堆在 `ops` 根包中。根包同时容纳控制器、响应模型、服务、目录生成器、渲染器、
测试辅助类和大量其他家族，文件数曾超过一千。即使某个类本身不复杂，维护者也很难通过目录
位置判断它属于哪条业务链。v1825 的目标就是把基础注册表搬进
`ops.maintenance.signedapprovaldraftprofilesection`，让包名直接表达所有权，同时保留根控制器
作为已有 Spring 路由的稳定入口。这样既减轻根包压力，又不改变外部调用方式。

## 二、为什么必须按三版理解，而不是把它看成十二个文件

这里最容易出现的误判，是只搜索一个前缀后看到十来个文件，就把它当成一个孤立家族。实际上，
完整的 ProfileSection 集群共有三层、三十六个生产文件。第一层是本版处理的基础注册表，共
十一文件；第二层是 `SignedApprovalDraftTextPackageProfileSection`，共十四文件；第三层是
`SignedApprovalDraftProfileSectionHandoff`，共十一文件。三层之间不是并列关系，而是有明确
数据流：基础层先把五个草稿阶段整理为章节；文本包层再把提交、预检、比较和证据接收等九条
文本包路由整理成两个渲染组；交接层则消费基础层输出，把章节和路由锁转换为下游可读的交接契约。

因此最合理的拆法是从底层向上。若先迁移 Handoff，Handoff 仍会反向依赖根包里的基础响应和
服务，下一版又要重改导入；若先迁移 TextPackage，它虽然相对独立，但不会为 Handoff 清除
基础依赖。先迁基础层后，公共服务与响应模型已经落在稳定窄包中，未来迁移 Handoff 时只需把
已有显式导入一起带走。这个顺序减少了重复修改，也让每一版都有清楚的输入、输出和验证边界。

## 上游证据配置

基础注册表有五个只读输入，分别来自草稿预检、草稿就绪、评审包预检、编写就绪和指令预检。
对应的服务已经在 v1813 到 v1818 的拆分中迁入各自窄包，所以 v1825 并没有重新发明上游数据，
只是继续消费它们公开的只读目录接口。服务调用五个 `catalog()` 方法后，得到五份响应对象；
`SourceCatalog` 从中提取版本、端点、profile、门禁数量和状态，并补上与 Node 版本对应的标记。

这些输入有三个重要特点。第一，它们都是内存中的只读响应，不涉及数据库写入。第二，基础注册表
只读取字段，不接收原始凭据、签名内容或草稿正文。第三，来源顺序是契约的一部分：预检在前，
随后是就绪、评审包预检、编写就绪和指令预检。测试会精确校验顺序和版本标记，避免未来维护者
因为“看起来可以排序”而无意改变输出。输入稳定，后续章节、字段和 Markdown 才能稳定。

## 服务层核心流程

`RegistryService` 是编排入口。它先调用 `SourceCatalog.sources()` 构造五条来源记录，再交给
`Catalog.sections()` 把每条来源映射为一个章节。章节会增加人类可读标题、字段数量和渲染器
所有者。接下来 `FieldCatalog.fieldEntries()` 为每个章节生成六个字段：Java 版本、endpoint、
profile、Node 标记、来源状态和只读边界。其中前五个属于路由可见字段，最后一个边界字段固定为
`read-only-no-runtime`，明确告诉读者这份注册表不是执行入口。

字段生成后，`Renderer.render()` 按章节聚合字段，生成 Markdown 标题和正文；`RouteLockCatalog`
则为每个章节生成一条路由字段锁，冻结 endpoint、profile、Java 版本、Node 标记和状态五项内容。
`ModuleCatalog` 描述本注册表由哪些模块组成。最后 `RegistrySupport.response()` 对所有列表做
不可变复制，计算总数，追加检查项，并用 `isComplete()` 验证模块数、来源数、章节数、字段数、
渲染数、路由锁数和门禁数是否全部符合预期。只有所有计数一致，最终状态才是 `passed`。

## 五、为什么把 GateCatalog 合进 Support

原先 `GateCatalog` 是一个单独文件，但它只做一件事：根据固定数量生成四十六条带序号的
“禁止运行时行为”字符串。它没有独立状态、没有外部依赖，也不承担可复用领域规则。若机械地把
它搬入新包，同时再增加一个 route owner，项目总文件数会从一千三百五十二增长到一千三百五十三。
这与本轮“降低根包压力但不制造新的治理膨胀”的目标相悖。

因此本版把 `gates()` 放进 `RegistrySupport`。Support 本来就拥有 `EXPECTED_GATE_COUNT`，
也负责把门禁列表写入最终响应和检查项；门禁生成与门禁完整性校验放在同一处，阅读路径反而更短。
结构测试明确要求旧 `GateCatalog.java` 不得复活。这里不是为了少一个文件而强行拼接无关代码，
而是把一个只依赖 Support 常量、只服务 Support 完整性判断的微型生成器归还给真正的所有者。

## 入口路由

基础注册表的公开路径仍然是
`/api/v1/ops/shard-readiness/signed-approval-draft-profile-section-registry`。
过去后缀常量放在 `CandidateDocumentRoutePaths`，根聚合器再从那里转发。这个位置是历史演进结果，
并不能准确表达当前所有权。v1825 新增
`OpsShardReadinessSignedApprovalDraftProfileSectionRoutePaths`，由它持有基础路径和注册表后缀。

根 `OpsShardReadinessRoutePaths` 改为委托新 owner；历史
`OpsShardReadinessCandidateDocumentRoutePaths` 也改为委托同一个 owner，而不是继续保存第二份
字符串。这样旧引用仍然可用，新代码也能从语义正确的位置取值，并且整个项目只有一个真实字面量。
服务用新 owner 拼接 `ENDPOINT`，根控制器继续使用根聚合常量。两条路径最终得到完全相同的字节串，
所以 HTTP 契约、MockMvc 测试和下游证据中的地址都不会变化。

## 阻断与安全边界

迁移后，`RegistryService` 和 `RegistryResponse` 仍然是公共类型。原因不是为了扩大 API，而是因为
根控制器和下一层 Handoff 都需要跨包读取它们。服务暴露 `registry()`，响应记录暴露只读组件；
这是明确且最小的跨包边界。其他目录类、渲染器、路由锁和 Support 都保持包级可见，因为它们只是
注册表内部装配细节，不应被其他家族直接拼装。

这种可见性划分很重要。如果把所有类都改成 public，拆包只是把文件换了目录，却没有建立模块边界；
如果把服务或响应错误地保持包级可见，根控制器与 Handoff 又无法编译。v1825 让编译器参与边界
设计：生产编译首次通过说明根控制器和 Handoff 的显式导入已经完整；测试编译随后发现 Handoff
测试辅助类仍按旧包寻找 TestSupport，补上这条导入后再次通过。编译错误在这里不是坏事，而是精确
指出仍未显式声明的跨包依赖。

## 响应模型

对 HTTP 调用者来说，输出结构完全不变。响应仍包含项目名、版本、只读标记、来源计划、注册表状态、
endpoint、profile，以及模块、来源、章节、字段、渲染结果、路由锁、门禁和检查项。固定计数仍为：
八个模块、五条来源、五个章节、五个渲染块、三十个字段、五条路由锁、二十五个锁定字段和四十六条
门禁。草稿产物数、签名审批数、运行时载荷数、写操作数和兄弟注册表修改数仍全部为零。

对代码维护者来说，输出则是一个更清楚的包边界。进入
`signedapprovaldraftprofilesection` 目录，就能同时看到服务、响应、来源目录、章节目录、字段目录、
模块目录、渲染器、路由锁和 Support，不必在八百多个根文件中搜索共同前缀。根包只留下控制器，
提醒维护者这里是兼容入口，而不是实现所有者。根文件数从八百九十七降到八百八十七，总文件数保持
一千三百五十二，说明拆分没有通过新增治理文件换取表面上的整洁。

## 测试覆盖

原有基础层测试大部分与实现一起迁入新测试包，包括聚合计数、边界标志、章节标题、字段属性、
门禁数量、Markdown 稳定性、模块顺序、服务结果、渲染输出、路由证据、路由锁和来源顺序。它们
继续直接访问包内实现，保证细节行为没有因为迁移而丢失。控制器测试留在根包，并通过公开测试工厂
构造迁移后的服务，证明根控制器仍能连接新实现。Handoff 测试工厂也显式导入新 TestSupport，
证明下一层仍然能消费基础注册表。

新增的 `ReadabilityUpkeepOpsConsolidationExtractionV1825Tests` 负责结构不变量。它检查说明文档能从
索引发现，代表性文件已经进入窄包，根包旧文件不存在，独立 GateCatalog 不存在，根控制器与根路由
聚合器仍存在，后续 TextPackage 和 Handoff 两层尚未被误删，并将根文件上限锁在八百八十七、
总文件上限锁在一千三百五十二。SpotBugs 中响应类型的两个 FQN 也同步迁移，避免静态检查把同一
历史认可项误判成新问题。

## Java 证据检查

这类重构的价值不在运行速度，而在降低变更成本。以前修改基础 ProfileSection 时，开发者首先要
在根包中辨认哪些同名前缀属于基础层，哪些属于 TextPackage，哪些属于 Handoff；还要猜测路由常量
为什么放在 CandidateDocument 下。现在基础层有独立目录和独立路由 owner，依赖方向一眼可见：
五个已拆出的草稿只读服务进入基础注册表，基础注册表再被根控制器和 Handoff 消费。

更重要的是，这一版为后两版创造了稳定着陆点。v1826 可以迁移十四文件的文本包层，不必同时承担
基础层的移动风险；v1827 迁移 Handoff 时，输入服务和响应已经在最终包中，只需移动交接内部实现
并更新控制器导入。每版都有可独立回滚的提交、标签、测试和讲解，问题发生时能够精确定位到哪一层，
而不是在三十六文件的大提交中猜测。这样的拆分既避免小到无意义，也避免大到无法审查。

## 十一、输入到输出的通俗示例

可以把整个过程想成整理五份施工验收单。第一份写“草稿预检通过”，第二份写“草稿已就绪”，第三份
写“评审包预检完成”，第四份写“可以开始编写”，第五份写“指令已经核对”。基础注册表先给每份
验收单编号，记录它来自哪个 Java 版本和哪条接口；再为每份单据生成统一的六栏摘要；随后把摘要
排成五段 Markdown，最后在关键五栏上盖“不得擅自改写”的锁章。

调用者拿到的不是施工材料本身，也不能凭这张目录卡批准施工。它只能看到五份材料是否齐全、来源
是否稳定、字段是否锁定。若少一份来源、少一个字段、少一条路由锁或门禁数量不对，完整性判断就会
返回 `blocked`。所以这套机制的核心不是“生成漂亮文本”，而是把跨版本只读证据转成机器可检查、
人也能阅读的稳定目录，同时始终关闭审批、写入和运行时执行。

## 十二、后续两版应怎样继续

下一版应处理十四文件的 `SignedApprovalDraftTextPackageProfileSection`。它会整理九条文本包相关
路由，并按 submission 与 compared-evidence 两组渲染。拆分时应继续保留根控制器，建立文本包层
自己的 route owner，并寻找与 Support 高内聚的微型目录来抵消新增文件，保持总量不增长。再下一版
处理十一文件的 Handoff，把基础注册表的章节与路由锁转换为下游交接条目和路由契约。

顺序不能倒置：基础层已经在 v1825 稳定；文本包层没有必要等待 Handoff；Handoff 作为消费基础层的
上层，应最后迁移。完成三版后，三十六文件会按真实职责落入三个窄包，根包只保留三个兼容控制器，
路由字符串仍字节级不变，归档目录也完全不动。这才是本轮 ProfileSection 集群拆分的完整终点。

## mini-kv 证据检查

本版没有读取、修改或启动 `D:\C\mini-kv`。ProfileSection 基础注册表消费的五个输入全部来自 Java
项目内部已经存在的只读服务，路由 owner、响应模型、结构守卫和中文讲解也全部落在 Java 仓库。
没有调整 mini-kv 的 RESP 命令、WAL、快照、分片证据、归档目录或版本标签，也没有把 Java 的包结构
变化伪装成跨项目契约变化。这样处理的意义是保持依赖边界透明：Java 内部可维护性重构可以独立推进，
只有真正修改共享 schema、证据字段或下游消费约定时，才需要重新核验 mini-kv 和 Node。

## 实际工作量说明

本版的真实工作量包括：用 CodeGraph 重建三十六文件的三层依赖图；确认十一文件基础层、十四文件
文本包层和十一文件交接层的顺序；迁移九个实现文件和十三个测试文件；删除并折叠一个 GateCatalog；
新增专属 route owner；修复根控制器、五个 Handoff 生产类、控制器测试和 Handoff 测试工厂的跨包
导入；迁移两个 SpotBugs 响应 FQN；同步三处根包计数；增加结构守卫、运维说明、索引、变更记录和
中文讲解；执行编译、聚焦测试、格式检查、全量测试、覆盖率与静态分析。禁止硬凑意味着篇幅必须来自
这些可核验的本项目工作，而不是把同一结论换词重复。每项工作都有对应文件、编译边或测试门禁。

## 一句话总结

v1825 把 ProfileSection 三十六文件集群的基础十一文件先迁到语义正确的窄包，保持路由和响应完全
不变，同时为 v1826 的文本包层与 v1827 的交接层提供稳定公共边界。
