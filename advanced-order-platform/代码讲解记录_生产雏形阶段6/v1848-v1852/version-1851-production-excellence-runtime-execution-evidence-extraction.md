# version-1851：运行执行只读证据链提取讲解

## 实际工作量说明

本版继续只做本项目 Java 仓库，不修改 Node、mini-kv 或其他项目。目标不是增加一个看得见的新接口，
而是把长期散落在根 `ops` 包中的运行执行证据链整理成一个边界完整、依赖方向清楚、能够独立验证的
模块。禁止硬凑字数，也禁止把目录移动包装成功能开发。本版实际处理九组生产 Service/Response、
九个行为测试、一个留根 Spring 控制器、五个留根只读证据消费者、十余个人工证据工作表消费者、六个
V1 合同测试、两份 SpotBugs 镜像、三处全局活棘轮、三份近期版本活守卫、endgame census、版本精确
守卫、测试图装配重构、索引文档和这篇长篇讲解。

九组类型并非只因文件名前缀相同而被机械打包。它们表达一条真实的时间链：先把 Java 已声明的操作
员生命周期投影成运行制品候选，再声明这个候选如何贡献给跨项目运行包；随后形成审批门输入、合同
交接、模板兼容接收、值校验、实时只读门，最后收拢通过证据。每一级只读取前一级 Response，并产生
下一份不可变 Response。若只迁其中一半，根包与新包之间会形成来回依赖，调用者也容易绕过前序检查。
因此十八个生产类型是一刀完整的最小闭包。

目录变化之外，本版做了一项直接降低维护成本的测试重构。原有根测试工厂和最后一级行为测试分别
构造同一条九级服务图，任何构造参数变化都要改两套代码。迁移后，新包提供一个测试源集专用的
TestSupport，集中装配从证据索引到通过证据收尾的完整链；根测试工厂只委托这个入口。它不进入生产
制品，也不扩大生产能力，却让下一版 ReadOnlyEvidence 测试能够复用同一可信输入，避免第三份装配
副本出现。

移动后的最长主源码绝对路径是一百九十七字符，最长测试路径是二百零一字符。这个长度既保留
`runtimeexecution` 的清晰语义，也给编译器生成的类文件、测试报告和后续子包留出空间。所有类名、
Bean 类型、方法名、返回类型和历史版本文字保持不变。最终根包从五百个主源码降到四百八十二个，
可迁 backlog 从三百九十五降到三百七十七，两个 RuntimeExecution 普查桶由四加十四共同归零，
一百零五个最终保留文件和零未分类文件不变。

## 入口路由

HTTP 入口仍由根包的 RuntimeExecution 控制器持有。控制器保留九个 GET 方法，每个方法只调用一个
对应 Service，并原样返回 Response。它没有请求体、没有动态 URL、没有凭据字段，也没有“执行”
按钮。迁移前后调用者看到的完整路径、请求方法、响应媒体类型和字段字节完全相同；变化仅是控制器
通过显式 import 找到新包中的公开 Service/Response。

为什么本版不创建新的 RoutePaths 类？这九个端点从历史 v162 到 v170 一直由各自 Service 保存完整
常量，根控制器的映射文字也已经被历史接口测试固定。为了目录形式统一而复制一套 route owner，会
增加一个主源码并产生两个权威来源；若顺手修改控制器，则会扩大行为风险。本版选择保留既有所有权，
用精确守卫检查每个 Service 仍含原端点常量，并用完整历史测试验证控制器路径。结构治理服务于真实
可维护性，而不是要求所有家族长成同一形状。

通俗地说，这九个入口像同一条检查流水线上的九个观察窗。外部审查者仍从原来的窗口领取同样格式的
只读回执，窗口号码没有换；变化在窗口后面：过去九组整理人员坐在一个容纳数百文件的大办公室，
现在进入标明“运行执行证据”的独立房间。控制器仍在前台，内部房间不能直接接收任意网络地址或执行
命令。以后排查某个端点时，维护者先看前台映射，再进入一个十八文件的闭包，不必在四百多个根文件
里辨认相似长名称。

每个端点的输入都是当前 Spring Bean 图中前一级只读结果，而不是调用者传来的可变配置。入口不允许
传入数据库连接、主机端口、密钥、审批结论或部署目标。这一点很重要：端点名称包含 runtime 和
execution，不代表接口能够启动服务。它只回答“现有证据是否形成某一步的只读回执”，不能把 false
边界提升为真实执行许可。

## 响应模型

九个 Response 都是不可变 record。共同头部说明项目、Java 版本、只读状态和执行禁用状态；中间部分
记录前一级证据是否存在、是否完整、本级 Node 对照材料是否出现、是否通过；尾部给出统计数量、检查
列表、失败关闭规则、归档路径、回执标识和状态。每一级字段更多，是因为它在保留前序事实的同时增加
本级证据，不是因为它获得了更强执行能力。

以最后一级 PassEvidenceCloseout 为例，输入是 LiveReadGate Response。输出会说明本地回环只读冒烟
是否通过、清理证明是否存在、归档验证是否通过、各来源检查数量是否一致，以及下一位消费者应读取
哪个版本。与此同时，它明确保留一组否定字段：Java 和 mini-kv 服务均未启动或停止，Java 与
mini-kv 状态均未修改，托管审计连接未建立，凭据值未读取，原始 URL 未解析，写操作未允许，活动
分片原型未启用。状态为 passed 只表示证据包闭合，不等于允许生产执行。

本版没有重新声明任何 record，也没有调整构造参数顺序。九个 Response 文件只改变 package；字段名、
字段类型、列表顺序、版本文字、证据路径和状态词保持原样。Jackson 因而继续输出同样 JSON，行为测试
继续逐字段断言同样值。八个含集合字段、原本需要 SpotBugs 暴露规则镜像的 Response，只把完整类名
从根包改成新包；规则内容、缺陷类型和双镜像结构不变。TemplateCompatibilityIntake 没有既有镜像，
本版也不为了“凑齐九个”增加无依据排除。

Response 的输入输出可用一个具体例子理解。假设 ArtifactCandidate 收到已声明操作员生命周期，输出
“候选存在、只读、尚未批准执行”；PacketContribution 把候选版本和 Node 对照版本写入贡献回执；
ApprovalGateInput 汇总贡献，但仍声明没有真实审批；合同交接固定字段语义；模板兼容只证明模板可被
识别；值校验只证明必填值满足规则；LiveReadGate 只证明可以进行既定只读观察；Closeout 最后证明
这次观察的通过、清理和归档材料齐全。每一步输入更具体，输出更完整，能力始终没有增加。

## 上游证据配置

这条链唯一位于包外的生产上游是 DeclaredOperatorLifecycle。ArtifactCandidate Service 读取其
Service/Response，得到 Java 已声明的操作员生命周期。之后八级都在新包内部传递，不再回到根包寻找
旁路输入。这个边界比“所有 ops 类都在同一包可直接访问”更容易审查：从 import 就能看出唯一上游，
任何新增根包依赖都会在代码审查中显眼出现。

链中还保留三类静态证据定位：ENDPOINT 是对外只读入口，FIXTURE_ENDPOINT 是合同 fixture 的资源
位置，EVIDENCE_PATH 是历史证据归档位置。过去消费者与服务同处根包，这些常量可以包私有；迁移后
ReadOnlyEvidence 快照、端点完整性快照和人工工作表仍要读取它们。于是本版只把这三类不可变字符串
改为公开静态常量，没有公开私有算法、集合构造器或状态变更方法。

这种可见性变化是最窄的跨包合同。消费者得到的是固定地址文字，不会得到 Service 内部判断过程。
端点目录可以比较九个入口是否齐全，fixture 目录可以确认九份合同材料是否存在，evidence 目录可以
确认历史归档引用是否完整；它们不能借此触发请求、读取秘密或写文件。PacketContribution 的 ENDPOINT
原先甚至不是 public，本版因只读目录确实需要而与其余八组统一公开，精确守卫会防止未来又退回隐式
同包可见性。

下游分为三类。第一类是根控制器，它注入九个 Service 并返回九个 Response；第二类是人工证据工作表，
它只把若干 endpoint 作为表格目标或校验规则；第三类是 ReadOnlyEvidence 与 V1 合同快照，它们比较
endpoint、fixture、evidence 三张清单的顺序和完整性。没有下游导入新包的私有辅助器，因为新包本来
就没有公开这种辅助器。下一版迁移 ReadOnlyEvidence 后，依赖方向自然成为证据目录读取
RuntimeExecution，而不是 RuntimeExecution 反向读取目录。

## 服务层核心流程

第一步，ArtifactCandidate 在只读事务中读取操作员生命周期，固定 Java v162 与 Node 对照版本，形成
候选制品回执。它不创建真正制品，也不写发布目录。第二步，PacketContribution 读取候选，声明候选
可作为跨项目运行包的一项贡献，同时保留“未获得执行审批”。第三步，ApprovalGateInput 把贡献转换为
审批门可读输入，但不创建审批决定或审批账本。

第四步，ApprovalInputContractHandoff 固定输入字段、版本与消费规则，使下游知道什么可以被当作合同
材料。第五步，ApprovalInputTemplateCompatibility 对照 Node 模板，判断字段形状是否兼容；第六步，
CompatibilityIntake 记录兼容结果已经被接收，但不把模板实例化成真实审批输入。第七步，ValueValidation
核对必填值与禁止值，仍只产生验证回执。第八步，LiveReadGate 综合这些结果，判断只读观察门是否具备
证据条件。第九步，PassEvidenceCloseout 汇总冒烟、清理、归档和收尾材料，关闭本链。

九步都使用构造注入，调用方向由类型直接表达。每个 Service 的公开业务方法在只读事务内调用前一级，
再创建本级 Response；辅助布尔判断和列表组装仍留在各自类中。包迁移没有把服务合并成巨型文件，
也没有为了减少文件数牺牲职责。十八个生产文件让每一级仍是一对输入处理和输出模型，而包边界把它们
组合成一个可理解模块。这种粒度兼顾局部阅读和全链追踪。

测试图重构与生产流程对应。新的 TestSupport 从 EvidenceIndex、Verification、Handoff 开始，构造
ActiveShardPlanHandoff、LiveReadGatePlan、OperatorServiceLifecycle 和 DeclaredOperatorLifecycle，
然后顺序装配九级 RuntimeExecution。最后一级测试直接调用该支持类；根 ServiceGraphTestFactory 也
委托它。以后构造参数变化只需修改一处，所有消费者仍通过真实构造器工作，不使用 mock 掩盖依赖。

## Java 证据检查

v1851 精确守卫首先枚举九个家族，每个家族必须同时存在 Service 和 Response，目标包总数必须恰好
十八，根包同名文件必须不存在。控制器必须继续位于根包并显式导入新包。九个 Service 都必须公开
三类不可变路径常量，并且不能突然依赖根 RoutePaths。九个行为测试必须移动，目标测试目录还必须
恰好包含一个 TestSupport，总数为十。

守卫其次检查测试装配所有权。新 TestSupport 必须公开唯一的 PassEvidenceCloseout 构造入口，不能
反向依赖根测试工厂；根工厂必须委托新支持类，旧的私有 LiveReadGate 构造链必须消失。这个断言不是
美化测试代码，而是防止下一次构造参数变化重新出现两份长链。生产源集与测试源集边界仍由 Maven
天然隔离，测试公开类不会进入运行 jar。

第三层检查跨包常量和静态扫描。ReadOnlyEvidence 快照必须导入新包，且不再保留旧根包 import；
SpotBugs 的八个既有 Response 完整类名必须全部指向新包，旧完整类名必须为零。首次 `test-compile`
编译了一千四百八十三个主源码与八百四十八个测试源码并成功，证明控制器、工作表、V1 合同测试和
根测试工厂的跨包边均已闭合。

第四层检查数量。根包必须恰好四百八十二，所有 ops 主源码仍不得超过一千三百五十二；普查脚本必须
报告保留一百零五、待迁三百七十七、未分类零，两个 RuntimeExecution 桶均为零。历史 v1850 文档中
“五百二十五到五百”和更早变化保持不动，只有活计数收紧。这样版本历史和当前事实同时可复核，不会
因更新门槛而篡改过去。

机械 import 转换第一次遇到仓库已有超长路径，普通 Windows 文件 API 在扫描深层长类名时超时。处理
方式不是跳过这些文件，也不是缩短历史类名，而是用扩展路径前缀重跑同一幂等替换。随后立即执行
`test-compile`，一次通过。这个过程被写入版本文档，提醒维护者：大仓库的路径约束是真实工程输入，
批量工具必须支持它，不能把部分成功误报为迁移完成。

## mini-kv 证据检查

本版没有编辑或启动 mini-kv。Response 中出现的 mini-kv 版本、清理证明或归档提示，是历史跨项目
证据在 Java 侧的只读投影，不是本版实时执行 C++ 二进制得到的结果。因此本版结论严格限于 Java 单仓
结构、行为与安全边界，不声称 C1-C4 联合验证已经完成。系统级 capstone 仍由 Node 窗口统筹；若它
要求 Java 提供真实 jar 和只读端点，本窗口再按授权配合。

每一级 Response 都保留 mini-kv 相关否定边界：不会启动或停止服务，不会修改键值状态，不会读取
凭据，不会把历史证据路径当作可执行命令。LiveReadGate 的“ready”表示资料允许进入既定只读观察，
不是允许连接任意实例。PassEvidenceCloseout 的“passed”表示来源检查、清理证明与归档引用数量一致，
不是 Java 已替 mini-kv 做过生产变更。

通俗理解，Java 手里拿的是一份签过摘要的检查表，而不是机房钥匙。本版把九页检查表放进同一档案夹，
校对页码和引用；它没有走进机房，也没有转动任何开关。若未来联合测试真实执行 `minikv_cli`，必须由
独立的、环境开关保护的 capstone 记录新鲜输出，并继续证明无写边界，不能把本版历史只读回执冒充成
实时联调结果。

## 阻断与安全边界

第一，禁止写入。九个 Service 只有只读事务和纯对象构造，没有 repository save、文件追加、消息
发布、审批账本写入或远端上传。第二，禁止执行。控制器没有命令参数，服务不启动 Java/mini-kv，
不部署、不回滚、不执行 SQL。第三，禁止秘密和任意网络。没有 credential value 读取，没有 raw URL
解析，没有托管审计连接，也没有把固定 endpoint 常量当成动态目标。

第四，禁止契约漂移。九个 endpoint、九个 fixture 路径、九个 evidence 路径、Response 字段、列表
顺序、版本文字和状态值均保持原样。第五，可见性只按真实消费者开放。Service/Response 原本就是
Spring 和控制器需要的边界；三类路径只是不可变引用；其余算法继续封装。编译错误不能成为批量公开
内部方法的理由，测试失败也不能通过删除断言或放宽 SpotBugs 解决。

第六，失败关闭。任何来源不完整、本级校验未通过、清理证明缺失、归档引用数量不一致或安全否定字段
被翻转，都必须让对应 ready/passed 结果失败。目录变得整洁不能覆盖行为失败。明确关账阻断包括：
十八个实现缺失、控制器离根、测试未随实现移动、出现第二套服务图、根包高于四百八十二、桶未归零、
未分类非零、总文件数增长、讲解不足三千汉字，或 focused、Spotless、JaCoCo、SpotBugs、完整 verify
任一失败。

## 测试覆盖

Focused 集以 RuntimeExecution 九个行为测试为核心，同时运行 ReadOnlyEvidence、人工证据工作表、
V1 合同端点稳定性、v1850/v1851 结构守卫、v1828 census、三处全局活棘轮和讲解合规门。它既验证
九级业务输出，也验证所有真实下游在 FQN 变化后仍能读取同样常量。单纯运行九个服务测试不足以发现
目录快照或合同测试遗漏，因此下游被有意纳入。

Spotless 负责统一二十余个消费者新增 import、新包源码和测试支持类的格式。完整 `mvnw verify` 还会
执行所有历史行为测试、Spring 集成测试、JaCoCo 覆盖率、SpotBugs、架构棘轮与文档规则。迁移在完整
门之前先写版本文档和讲解，避免测试成功后倒推故事；只有真实输出出现后，才在回执区补充测试数量、
耗时、覆盖率和静态扫描结果。

输入证据是 v1850 已推送提交与 tag、唯一远端状态、上一版 CI、十八文件精确清单、九测试清单、跨包
引用扫描、最长路径和迁移前普查。输出证据将是编译回执、focused 数量、Spotless、完整测试总数、
JaCoCo、SpotBugs、迁移后普查、实现提交、关账提交、注解 tag 与 GitHub Actions run。下一版开头检查
本版 CI，不在中间版本原地空等；v1852 完成后统一进入五版检查点。

审查时不需要相信本文自述。先运行普查脚本确认四百八十二、三百七十七、两个零桶和零未分类；再看
目标包是否恰好十八个生产文件、根控制器是否仍在；随后运行 focused 检查九级输出与下游目录；最后
运行完整 verify 并核对 SpotBugs 和覆盖率。若任一数字无法复现，版本应退回实现阶段，而不是在账本
里写“已知偏差”。

## 一句话总结
