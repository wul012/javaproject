# version-1833 production excellence compared evidence candidate intake preflight extraction

## 实际工作量说明

本版本处理的是候选接收预检这一族只读证据。它位于候选蓝图之后，包审阅之前，职责是说明一份候选证据在进入后续评估前必须满足哪些来源、比较、策略和收尾条件。上一版已经把候选蓝图迁到独立维护包，候选接收预检现在正好可以顺着这条依赖线继续外移。v1833 的核心结果是：根包直接文件从八百一十九降到八百零五，剩余可搬根包非控制器从七百一十四降到七百，总运维包文件数仍保持一千三百五十二，候选接收预检 bucket 归零。

本轮真实工作量不是简单搬目录。第一，十三个实现文件移动到新的维护包，控制器留在根包，保证入口仍然容易被找到。第二，新增候选接收预检自己的路径拥有者，五个路径后缀和五个完整端点都由这一族自己保存。第三，历史上候选文档路径类曾经暴露候选接收预检的目录后缀，本版把它改为委托新路径拥有者，避免两个类同时像 owner。第四，为了不让新增路径类导致总文件数增加，原本独立的门禁目录并入阻断目录，因为二者都描述接收预检的失败闭锁条件。第五，下游画像章节继续读取这一族的目录服务和响应模型，因此导入关系改到新包。第六，静态分析配置、根包计数测试、终局清单、进度账本、变更记录和中文讲解同步更新。

这一版仍然强调禁止硬凑。为了满足讲解字数而写无关内容没有意义，真正需要讲清楚的是为什么候选接收预检值得单独成包。它不是候选蓝图，也不是评估预检，更不是包审阅；它关心的是“候选材料能否被接收进入下一阶段”。来源材料是否真实存在、比较材料是否离线可审查、策略执行材料是否不含写入、收尾材料是否保留审阅追踪，这些都属于接收前的门槛。把这组门槛放在同一个维护包里，后续维护人员就能顺着业务语义阅读，而不是在根包里用长前缀搜索。

本项目进入后期保养后，最重要的不是一次降低多少文件，而是每一刀都能被复核、被回退、被下一刀继承。v1833 的设计保持了这种节奏：候选蓝图先出根包，候选接收预检再读它；评估预检还留在根包，等下一版单独处理；包审阅也不提前混入。这样每一版只有一个主语，失败时能直接定位，不会让评审者在多个迁移族之间猜测原因。

## 入口路由

入口层继续保留根包控制器。运维人员查外部只读接口时，不需要先理解维护包内部结构，仍然可以在根包看到候选接收预检控制器。这个控制器只负责把五个只读路由分发给目录、来源、比较、策略和收尾服务，不接收上传文件，不写数据库，不触发队列，也不调用外部执行面。控制器的保留符合终局清单里“公共控制器可留根包”的规则。

路径所有权则从根包和历史候选文档类中分离出来。新的候选接收预检路径类保存目录、来源、比较、策略、收尾五个后缀，同时保存由基础路径拼接出的完整端点。根包聚合器只做委托，不再硬编码这些字符串。候选文档路径类中保留的历史目录后缀也改成委托同一个新 owner。这样一来，历史消费者仍然能读到相同字节，当前语义 owner 却变成候选接收预检自己。

这种安排比直接删掉候选文档里的旧常量更稳。候选文档曾经把候选接收预检目录当作自己请求包证据的一部分，已有消费者可能通过那里读到 catalog 后缀。如果本版直接移除旧暴露，会制造无关破坏。委托方案保留旧入口但消除双重来源：旧入口只是转发，新入口才是事实 owner。路径字节不变，依赖方向更清楚。

## 响应模型

响应模型随实现一起迁到维护包。它仍然表达接收预检的只读结果，包括 slot、guard、gate、检查项和几个布尔边界。迁移没有改变字段含义，没有改变集合内容，也没有改变序列化结构。控制器返回的仍是同一类业务响应，只是 Java 包名变得更准确。下游画像章节读取这个响应时，现在必须显式导入候选接收预检维护包，这比根包默认可见更透明。

响应模型迁移后，静态分析配置必须跟随。此类包含集合组件，已有排除镜像块用于说明暴露集合结构的受控边界。如果配置继续指向旧根包，就会让静态分析账本与代码现实不一致。v1833 把两个镜像块都指向新包，并在可读性测试里断言旧根包响应名不再出现。这样后续有人移动或回退 response 时，工具会提醒他同步配置。

响应模型的业务边界也没有扩大。它没有新增命令字段，没有包含凭据，没有暴露原始连接，也没有加入执行令牌。它只是把接收预检的静态只读证据组合成响应。维护人员以后若要调整某个 slot 或 guard，应先确认这是接收前置条件，而不是评估结果或包审阅结果。包边界能帮助做这个判断。

## 上游证据配置

候选接收预检的上游主要是上一版迁出的候选蓝图。来源、比较、策略、收尾 slot catalog 都需要指向候选蓝图相应端点，说明接收前要先有蓝图层面的只读证据。v1833 保留这些依赖，并让它们继续导入候选蓝图路径 owner。由于候选蓝图已经在 v1832 独立成包，v1833 不需要再公开新的蓝图服务，只要继续读取它的公开端点即可。

这一点体现了按链条迁移的好处。如果没有先迁候选蓝图，候选接收预检迁移时就会被迫读取根包里的 package-private 常量，或者一次性扩大多个类的可见性。现在上游已经准备好，候选接收预检只需要把自己的包边界立起来。下一版如果处理评估预检，也会获得同样收益：下游候选蓝图和接收预检已经稳定，评估预检可以专注自己的路径和读者。

下游则是画像章节。画像章节聚合多个只读来源，把它们整理成人能审阅的证据视图。它读取候选接收预检目录服务和响应模型，本版把导入改到新包。测试支持类也同步导入新服务，避免测试还从旧根包构造对象。这样主代码和测试代码的依赖方向一致，不会出现生产代码已迁移、测试仍暗中依赖旧位置的假象。

## 服务层核心流程

服务层保持原有五段式流程。目录服务聚合所有 slot、guard、gate 和检查项，返回完整目录。来源服务只返回来源相关 slot，比较服务只返回比较相关 slot，策略服务只返回策略相关 slot，收尾服务只返回收尾相关 slot。每个服务都使用同一个响应组装支持类，保证字段计算方式一致。移动包不会改变这些计算，只改变类所在的位置和端点常量来源。

本版把门禁目录并入阻断目录，是一个有意的维护性重构。原门禁目录只保存一组静态 gate 字符串，阻断目录则根据 slot 生成 fail closed guard。二者都服务同一件事：说明接收预检为什么必须阻断不合格输入。把 gate 列表放到阻断目录里，可以减少一个无状态文件，同时让接收预检的失败条件集中阅读。它不是把不相关职责硬塞到一起，而是把同一失败边界的两种表达放在一个类里。

服务端点常量也从根包聚合器切换到本族路径 owner。目录、来源、比较、策略、收尾服务的端点常量都变为公开不可变字符串，下游测试和未来读者可以明确引用。公开的是端点字符串，不是服务执行能力；服务本身仍然通过 Spring 管理，控制器仍然只读，事务仍然是只读。这个公开面与上一版候选蓝图保持一致，便于后续链条继续迁移。

## Java 证据检查

Java 证据首先来自编译。移动包后，根包控制器、画像章节、候选文档路径类、候选接收预检自身服务都需要跨包 import，如果有任何可见性遗漏，编译会直接失败。本轮在补文档前已经跑过跳过测试的编译，确认主代码可以通过。最终还要跑 focused gate 和完整验证，编译只是第一层。

第二层证据来自终局清单脚本。脚本输出 direct root 八百零五、retained root 一百零五、remaining 七百、未分配为空、候选接收预检 bucket 为零。这个脚本的意义是让评审者可以复现同一组数字，而不是相信进度表。对应测试也绑定这些数字，未来如果有人把类放回根包或放松 root 上限，会直接失败。

第三层证据来自 v1833 可读性测试。它要检查文档是否能从索引和清单发现，检查 moved files 是否真的在窄包，检查 root 只剩控制器，检查 route owner 是否持有后缀和完整端点，检查候选文档旧常量是否委托到新 owner，检查 GateCatalog 是否已经并入 GuardCatalog，检查画像章节导入是否同步，检查静态分析配置是否指向新响应，检查总文件数仍然守住一千三百五十二。这样的测试把“我做了”变成“回归会失败”。

## mini-kv 证据检查

本版没有修改 mini-kv，也没有启动任何 C++ 进程。候选接收预检是 Java 内部只读证据整理，既不改变跨项目 schema，也不改 fixture 字节，不触碰 Node 里指向上游归档的路径，更不改变 mini-kv 的命令、持久化、快照或网络行为。因此 mini-kv 侧的正确结论是“不参与本刀执行，且没有需要它复核的契约变化”。

这个说明不是敷衍，而是在四项目协作里划清边界。真正需要 mini-kv 的情况通常是端到端 capstone 或跨项目新证据格式；本版没有这类内容。若把 mini-kv 拉进来，只会制造无关变量。后期保养的原则是该查的必须查，不该动的保持安静。v1833 只做 Java 项目自身的可维护性减压，mini-kv 保持不动就是正确行为。

## 阻断与安全边界

安全边界没有变化。没有写路由，没有活动分片路由器，没有凭据值，没有原始端点，没有受管审计连接，没有部署或回滚动作。所有新增公开常量都是只读路径字符串，不携带执行能力。控制器没有新增入参，也没有接受文件或正文。服务继续返回静态只读证据，事务仍然只读。

归档边界也没有变化。历史截图、讲解、证据目录和版本归档不移动、不重命名、不压缩。新增讲解放在当前续写目录内，只增加 v1833 的说明文件。这样既避免单个旧目录继续膨胀，也不破坏历史路径。Node 和 mini-kv 工作区都没有被修改。

本版还到达第五批检查点。检查点的意义不是停止推进能力，而是让评审者按真实仓库状态复核：root 数字是否可信，路径 owner 是否清楚，中文讲解是否合规，远端 CI 是否通过。只有这个检查点被确认，下一轮五批才应该继续。这个节奏保护连续推进不变成盲目推进。

## 测试覆盖

测试覆盖包括原有业务测试和新增工程守门。候选接收预检的目录、服务、支持类测试随实现进入新包。控制器测试留在根包，因为控制器仍在根包，它通过导入 moved services 构造对象。路由测试留在根包，因为它负责证明根聚合器仍然暴露同一组路径，同时新增断言证明服务端点来自新 route owner。

新增可读性测试是这版的核心守门。它会检查文档索引、终局清单、 moved package、root controller、路径 owner、候选文档委托、GateCatalog 折叠、ProfileSection 导入、SpotBugs FQN、root 精确数、total 上限和中文讲解。focused gate 会把这一组测试和相关候选蓝图、画像章节、历史 ratchet、讲解合规测试一起跑。完整验证会再跑全项目测试、覆盖率、静态分析和格式检查。

远端 CI 也必须看。v1833 完成本地后会提交、打 tag、推送，然后等待 GitHub Actions。若远端失败，必须按失败日志修，而不是把失败记成“后续处理”。由于这是检查点版本，远端状态尤其重要：本地通过但远端失败，不能进入下一轮。

## 一句话总结

v1833 把本项目候选接收预检从根包迁到独立维护包，建立自己的路径 owner，折叠门禁目录抵消文件数，保持只读和归档边界不变，并把第五批检查点所需的代码、文档、测试和讲解证据落到可复核状态。
