# v1815 生产卓越：签批工件草稿就绪通道注册表迁出

本版继续沿着上一版已经打通的签批工件草稿链路推进。v1814 先把“草稿预检”从根 `ops` 包迁入专属包，并公开了九个只读端点常量；v1815 顺着依赖方向处理它的直接下游，也就是“草稿就绪通道”。这不是新增一个业务能力，而是把已经稳定的只读证据注册表从拥挤根包里移出来，让维护者能够按功能边界理解代码。本项目的根 `ops` 包长期承载太多生产雏形证据类，阅读时很难看出哪些类是一组，哪些类只是暂时相邻。J25 的价值就在于把一组有共同语义、共同路由、共同响应模型、共同上游证据来源的类收束到 `ops.maintenance.signedapprovalartifactdraftreadinesslane`，并用测试把这种收束固定下来。

这一版的核心动作有四个。第一，保留两个对外控制器在根包，因为控制器仍然承担 Spring 扫描、公开 HTTP 入口和兼容旧路由聚合器的职责。第二，把十五个实现文件迁到新包，包括目录服务、通道目录、阻断目录、响应模型、支撑构造器和九个只读服务。第三，新增一个公开的路由 owner，让九个 suffix 常量不再直接写在根聚合器里，根聚合器只负责委托。第四，把原来独立的 `GateCatalog` 合入 `BlockerCatalog` 文件尾部，因为两者同属 fail-closed 控制清单，生命周期一致，合并后可以抵消新增 route owner，保证整棵 `ops` Java 文件数仍然是 1,352。这样根包直接文件数从 1,057 降到 1,041，而不是用新增文件制造账面优化。

## 入口路由

入口路由仍然由根包里的两个控制器负责。一个控制器承接基础侧端点：目录、摘要钉扎、操作员复核、签名复核；另一个控制器承接保障侧端点：证据复核、值脱敏、禁运锁、人工包门禁和收尾。这样安排不是偶然的。对外入口继续留在根包，能够保持 Spring 控制器命名、扫描路径和既有 route tests 的兼容；内部实现迁走，则让读代码的人不必在根包的一千多个文件里来回寻找同族服务。

本版新增 `OpsShardReadinessSignedApprovalArtifactDraftReadinessLaneRoutePaths`。它只保存这一族的 `BASE_PATH` 和九个 suffix 常量，不承载业务逻辑，也不持有状态。根 `OpsShardReadinessRoutePaths` 继续存在，但对应的九个常量改为委托给这个新 owner。路由字符串没有变化，端点路径没有变化，控制器上的 `@GetMapping` 仍然读根聚合器；区别只是“常量的所有权”从根包转到了语义更窄的 signed approval 路由包里。这个小动作很关键，因为后续迁移 `ReviewPackagePreflight` 时，它可以继续按一族一个 owner 的方式推进，而不会把更多 suffix 堆回根聚合器。

举例说，目录端点仍然是“签批工件草稿就绪通道目录”那条只读路径，摘要端点仍然是“digest pins”，收尾端点仍然是“closeout”。调用方看不到任何差异；维护者看到的是责任边界更清楚了：HTTP 入口留根包，路由 suffix 由族 owner 管，服务和响应模型在专属包内闭合。

## 响应模型

响应模型迁到了新包中，但字段没有改。它仍然表达一个只读就绪通道的结果：项目名、版本号、只读标记、是否允许执行、上游 Node/Java 版本、人工包状态、签名捕获状态、审批授权状态、值导入状态、运行时状态、通道数量、阻断数量、门禁数量、检查列表和最终状态。

这类响应的机理可以用一个通俗例子说明。假设后面真的要人工编写一份签批草稿，系统不能直接开始写草稿。它要先确认：草稿请求是否存在，来源预检摘要是否固定，操作员身份是否只是别名而不是凭证，签名算法是否只是策略而不是签名材料，证据文件是否只是编号而不是文件内容，值是否已经脱敏，审批授权是否仍然没有发出。ReadinessLane 响应就是一张“能不能进入人工包准备阶段”的检查表。它不是草稿本身，也不是审批本身，更不是执行命令；它只是把下一步所需的只读条件列出来，并明确哪些条件仍然保持锁闭。

本版没有改动 record 字段，也没有改变嵌套项的名字。`ReadinessLane`、`ControlBlocker`、`ReadinessLaneGate` 三类条目仍然由支撑构造器统一创建。迁包后，包内类之间直接调用，不需要跨 root 包访问 package-private helper；对外只有服务类的 `ENDPOINT` 需要 public，因为下游 `ReviewPackagePreflight` 要引用这些只读端点作为来源证据。

## 上游证据配置

这一族的上游来自 v1814 的 `ArtifactDraftPreflight`。上一版已经把草稿预检服务迁入 `ops.maintenance.signedapprovalartifactdraftpreflight`，并公开了九个 immutable `ENDPOINT` 字符串。v1815 的两个 lane catalog 正是读取这些端点：基础通道读取目录、摘要链、操作员窗口、签名声明和证据来源；保障通道读取证据来源、脱敏来源、fail-closed lock、归档计划和 closeout。

换成日常语言，就是先有“预检字段表”，再有“就绪通道表”。预检字段表说某个字段从哪里来、为什么不能被材料化；就绪通道表把这些字段转成下一阶段可以审查的通道。例如预检里有一个签名声明端点，就绪通道里会形成签名算法、签名占位、签名脱敏策略、审批声明摘要等通道。它们都只引用端点字符串，不去调用上游服务生成新对象，也不去读取真实签名材料。

这也是本版为什么适合作为 J25。它的 outbound edge 已经被 v1814 处理完了：所有上游端点都是 public，并且仍然是只读证据常量。本版只需要把 import 指向上游新包，不需要打开新的出站可见性。

## 服务层核心流程

服务层的流程很朴素，但边界严。每个 service 暴露一个只读方法，例如目录服务返回完整通道目录，摘要钉扎服务返回摘要相关通道，操作员复核服务返回身份、角色、窗口和通道策略，签名复核服务返回签名策略与声明摘要，证据复核服务返回来源版本、文件和片段，值脱敏服务返回脱敏摘要和值形态，禁运锁服务返回原始秘密、授权、导入、写路由和兄弟状态锁，人工包门禁服务确认还不能创建人工包，收尾服务确认下一步必须另起明确计划。

这些方法最后都汇入同一个支撑构造器。支撑构造器会复制输入列表，统计通过的通道数量和阻断数量，追加固定检查项，再生成不可变响应。它没有保存成员变量，没有访问数据库，没有发出网络请求，也没有改变任何运行时状态。`@Transactional(readOnly = true)` 继续保留在服务方法上，表达这类证据端点只能读取、拼装和返回静态证据。

本版迁移后，服务层的代码阅读路径更短。原来维护者要在根包里找到 `CatalogService`、`FoundationLaneCatalog`、`AssuranceLaneCatalog`、`BlockerCatalog`、`GateCatalog`、`Support` 和九个 service；现在进入一个新包就能看到这一族的全部内部结构。控制器留根包只是边界适配，不再把内部实现打散。

## Java 证据检查

Java 侧证据主要有三层。第一层是编译证据：迁包后所有 package-private 构造器和 helper 都必须在新包内闭合，root 中的 controller、route test、下游 slot catalog 必须通过 import 读取 public 服务或响应。如果有任何遗漏，`test-compile` 会直接失败。本版先用编译器确认这个边界。

第二层是路由证据。保留的 route-path 测试现在同时比较三件事：root 聚合器 suffix、新 route owner suffix、service `ENDPOINT`。这能证明外部 HTTP 字符串没有改变，也能证明根聚合器没有重新偷偷拥有字符串字面量。对维护者来说，这比只看 diff 更可靠，因为常量拼接很容易在长类名里看花眼。

第三层是治理证据。新增的 v1815 可读性测试会检查短说明是否被 ops README 收录，代表性文件是否确实迁到新包，两个 controller 是否仍在根包，root 直挂 Java 文件数是否不超过 1,041，总 `ops` Java 文件数是否不超过 1,352。这样未来如果有人把文件移回 root、删除说明、或者为了迁移新增很多小文件，测试会第一时间报警。

## mini-kv 证据检查

mini-kv 在本版没有被修改，也不应该被修改。这里的“mini-kv 证据检查”不是运行 C++ 项目，而是确认本次 Java 改动没有碰跨项目契约。ReadinessLane 仍然只是 Java 内部的只读证据目录；它没有改变 Node、mini-kv 或其他项目会消费的归档路径，也没有重命名 `e/<version>/`、截图目录、历史 fixture 或证据 JSON。

从四项目协作角度看，本版属于非契约内部维护。它不新增写路由，不打开主动分片路由，不处理凭证值，不解析原始 endpoint，不启动 Java 进程以外的运行时，也不要求 Node 或 mini-kv 同步版本。mini-kv 只需要保持原有证据链可引用即可。这个边界很重要，因为跨项目系统里最怕“整理代码”顺手移动历史证据目录，导致下游硬编码路径或 digest 检查失效。本版只改 Java 源码组织和 Java 文档，不动这些归档根。

## 阻断与安全边界

ReadinessLane 的核心语义就是阻断。它把“还不能做什么”写成可审查的证据，而不是偷偷允许执行。比如它明确没有人工草稿、没有草稿材料化、没有签名捕获、没有审批授权、没有操作员值提交、没有证据导入、没有运行时 payload、没有兄弟状态突变。这些字段和检查项不是装饰，它们是在保护后续阶段不要提前越界。

本版的合并点也遵守这个语义。`GateCatalog` 被放到 `BlockerCatalog` 同一文件里，是因为 gate 和 blocker 都是 fail-closed 控制清单：一个描述必须满足的门禁，一个描述不满足时拒绝的原因。两者放在一起，维护者能同时审查“禁止什么”和“为什么禁止”。这不是为了凑文件数，而是因为它们的变更理由高度一致。禁止硬凑的标准在这里很明确：如果两个类职责不同、生命周期不同、测试关注点不同，就不应该为了文件数强行合并；本版选择这两个目录类，是因为它们正好属于同一安全边界。

## 测试覆盖

测试覆盖分为迁移内测、边界测试和治理测试。迁移内测包括服务测试、通道目录测试、阻断目录测试、gate 测试和 support 测试，它们迁入新包后仍然可以访问 package-private helper，证明内部闭合没有丢失。边界测试包括两个 root controller 测试和 route-path 测试，它们证明外部入口继续工作。治理测试是 v1815 新增的可读性测试，用路径和计数把本版成果固定下来。

后续还会用 focused test 先覆盖本族、下游 `ReviewPackagePreflight`、讲解归档合规和 v1815 可读性测试，再用完整 `mvnw verify` 覆盖全仓库。这样的顺序比较稳：先快速证明本版改动点，再让全量测试发现意料之外的跨模块影响。由于本版没有修改数据库、消息、运行时配置和部署脚本，主要风险集中在 Java 包可见性、路由常量和文档合规上。

## 实际工作量说明

本版不是“小粒度改名”。实际工作量包括：用 CodeGraph 和本地扫描确认 J25 依赖方向；移动十五个实现文件和六个内部测试；保留两个控制器和 root route 测试；新增一族 route owner；把九个 service endpoint 改为 public immutable 字符串；让下游 `ReviewPackagePreflight` 两个 slot catalog 显式 import 新包；合并 gate 与 blocker 目录以保持总文件数不涨；迁移 SpotBugs 的响应类排除项；新增 v1815 可读性测试；更新短说明、README、CHANGELOG、progress 和本篇中文讲解；最后用编译、focused gate、完整 verify 和 CI 做闭环。

这一串动作的价值是降低未来维护成本。下一版如果处理 `ReviewPackagePreflight`，它的 outbound edge 已经被本版准备好：它读取的 ReadinessLane endpoint 现在都在新包公开。维护者不需要重新猜测“这些常量为什么能跨包访问”，因为 v1815 的短说明、长讲解和 route tests 已经把这个原因写清楚了。

## 一句话总结

v1815 把签批工件草稿就绪通道从根 `ops` 包迁到专属维护包，用新 route owner、public endpoint、下游 import 和计数测试固定边界，让本项目继续沿着“每版真实减少根包复杂度、同时保持契约不变”的路线前进。
