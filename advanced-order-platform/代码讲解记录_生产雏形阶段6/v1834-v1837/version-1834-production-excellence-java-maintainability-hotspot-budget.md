# Java v1834：把“巨型文件需要优化”变成会失败的维护性预算

## 实际工作量说明

本版本没有新增订单能力、运维接口或证据字段，而是先解决一个长期妨碍深度重构的问题：大家都能看出若干 Java 文件过大，却没有一条统一、可复现、会在回归时失败的度量。没有机械门时，“以后再拆”只是愿望；即使某次把一个文件缩小，后续开发也可能把逻辑重新堆回去。v1834 因此不是简单写一份统计文档，而是同时交付普查脚本、独立 JUnit 预算门、重点文件单独上限、四版执行契约、失败条件、账本纠偏和归档讲解。

第一项工作是新增 `scripts/java-maintainability-census.ps1`。脚本从项目根目录推导 `src/main/java` 和 `src/test/java`，递归寻找 Java 文件，再逐行读取并计算文件数、最大行数、超过五百行、七百五十行和一千行的文件数。它既支持面向人的表格输出，也支持 `-Json` 结构化输出；`-Top` 参数允许维护者控制热点列表长度。脚本没有依赖 IDE、Git 状态或某台机器上的临时缓存，因此评审者可以用同一命令重算。

第二项工作是处理 Windows 长路径。项目中存在包名和类名都很长的维护证据文件，普通 `Get-Content` 在部分路径上会报“文件不存在”，实际原因是旧式路径解析到达长度边界。脚本在打开文件前为绝对路径增加 `\\?\` 前缀，再用 `StreamReader` 顺序读取。这样统计范围不会悄悄漏掉最需要治理的长文件。这个细节很重要：如果普查工具本身跳过长路径，漂亮的数字反而会掩盖真实债务。

第三项工作是新增 `JavaMaintainabilityBudgetTests`。测试并不调用 PowerShell，因此 Linux CI 与 Windows 本地环境都能独立验证同一事实。测试使用 Java NIO 遍历源码、按 UTF-8 计算行数，分别约束生产代码和测试代码的四档指标。生产代码的 v1834 历史上限是最大 1530 行、超过五百行不多于 39 个、超过七百五十行不多于 5 个、超过一千行不多于 3 个。测试代码的上限是最大 854 行，三个区间分别不多于 8、2、0。后续只能把这些数字调低，不能因为新增内容而调高。

聚合数字仍可能被钻空子：一个重点文件增长二百行，另一个文件刚好缩小并跨过阈值，总数可能不变。因此第四项工作为五个风险最高的生产文件设置单文件上限。它们分别是 `OpsEvidenceService`、`FailedEventMessageService`、`OpsShardReadinessRoutePaths`、`ReleaseApprovalVerificationHintBuilder` 和凭据解析器禁用预检构建器。后续拆分哪一个，就同步降低哪一个的上限。这样优化成果不能被别处的偶然变化抵消。

第五项工作是落实检查点评审。v1833 实际已经提交、打 tag、推送并通过 GitHub Actions，但进度账本仍写着“待提交”。本版本把 J43 压缩为可阅读的短行，写明提交 `df44a1cf`、描述性 tag 和 CI run `28848977233`。Claude 在 `AGENTS.md` 中新增的“版本与账本同会话关闭”规则被保留并纳入本版本。它不是装饰性约定：以后任何行在代码已推送后仍声称 pending，都属于关闭失败。

## 入口路由

v1834 不增加也不修改 HTTP 入口。订单创建、失败事件管理、重放审批、运维概览和只读证据接口的 Spring 映射保持原样。这里新增的入口是维护者命令：

```powershell
.\scripts\java-maintainability-census.ps1
.\scripts\java-maintainability-census.ps1 -Json
.\scripts\java-maintainability-census.ps1 -Top 10
```

默认模式先输出生产源码摘要和热点表，再输出测试源码摘要和热点表。`-Json` 用于评审、后续脚本或 CI 消费；`-Top` 只改变展示多少个热点，不改变统计口径。三个入口最终都调用同一套文件发现、逐行计数和聚合函数，不存在“人看到一个数字、机器验证另一个数字”的双重定义。

对运行中应用而言，本版本的入口路由变化为零。测试门会继续通过原有控制器、集成测试和历史快照证明这一点。维护脚本也不会启动 Spring、Docker、RabbitMQ 或数据库，它只读取工作区中的 `.java` 文件。把维护入口与业务入口明确分开，可以避免一次源码治理工具误触生产依赖。

## 响应模型

虽然没有新增 API 响应，本版本仍定义了清晰的维护结果模型。JSON 顶层包含 `Production` 和 `Tests` 两个对象；每个对象都有 `Scope`、`JavaFiles`、`MaxLines`、`FilesOver500Lines`、`FilesOver750Lines`、`FilesOver1000Lines` 与 `Hotspots`。热点条目只包含相对路径、行数和字节数，既足够排序，又不暴露机器绝对路径。

行数与字节数同时保留是为了回答不同问题。行数更接近维护者阅读和审查的负担，也是预算门采用的主指标；字节数能帮助识别极长常量、单行生成内容或格式异常。预算只绑定行数，避免换行风格差异造成无意义波动；热点报告保留字节数，供人工进一步判断。JSON 字段顺序固定且名称明确，后续版本不需要解析控制台表格。

JUnit 内部使用 `SourceMetrics` 记录最大行数和三个阈值计数。这个模型刻意很小，不把所有热点路径复制进测试结果。单文件风险由 `PRIORITY_HOTSPOT_LINE_CAPS` 单独表达，聚合风险与重点风险因此是两条互补的证据链。若某文件越界，AssertJ 会在失败信息中打印对应路径；若整体档位恶化，则直接指出哪个阈值被突破。

## 上游证据配置

维护性普查的上游不是网络服务，而是版本库中的源码树。生产范围严格限定为 `src/main/java`，测试范围严格限定为 `src/test/java`，只接收扩展名为 `.java` 的普通文件。`target`、历史证据目录、Markdown、JSON fixture 和截图都不计入 Java 源码预算。这样结果不会被构建产物或归档规模干扰。

v1834 的基线来自同一工作树中的 1475 个生产 Java 文件。最大文件是 1530 行的 `OpsEvidenceService`；`FailedEventMessageService` 为 1126 行；根路由聚合器为 1111 行；`ReleaseApprovalVerificationHintBuilder` 为 874 行。生产源码超过五百行、七百五十行和一千行的数量分别是 39、5、3。新增测试门之后，测试 Java 文件总数会增加一，但最大值和各档位上限不变。

配置的核心原则是“维护预算只能收紧”。这些数字不是质量目标，更不是允许新文件长到相同尺寸的许可证。它们是对现存债务拍下的快照。后续 v1835、v1836 和 v1837 每完成一次真实拆分，就降低对应单文件上限；如果跨过五百、七百五十或一千行档位，也同步降低聚合上限。任何人为了让失败测试重新变绿而把数字调高，都违反本版本的失败条件。

## 服务层核心流程

脚本的第一步是从自身目录反推项目根目录，避免依赖调用者当前所在位置。第二步分别构造主源码和测试源码根路径。第三步由 `Get-JavaFileRows` 递归枚举文件，并为每个文件建立路径、行数、字节数三字段记录。相对路径统一使用正斜杠，保证 Windows 输出更接近 CI 和文档中的路径形式。

逐行计数由 `Get-LineCount` 单独负责。函数创建 `StreamReader` 后进入 `try/finally`，无论成功还是异常都会释放文件句柄。它不一次性把 1475 个文件全部载入内存，也不依赖 PowerShell 对超长路径的默认处理。这个函数解决的是正确性和资源释放问题，而不是追求看起来短的单行命令。

聚合阶段由 `Get-SourceSummary` 完成。它先按行数降序、路径升序排序；路径作为第二排序键，可以让同行数结果稳定。随后计算文件总数、最大行数和三个严格“大于”阈值的数量，最后截取前 `Top` 个热点。严格大于五百意味着恰好五百行不会计入该档位，测试与脚本使用相同定义。

JUnit 走一条独立实现路径：`Files.walk` 找文件，`Files.lines` 按 UTF-8 计数，排序后构造 `SourceMetrics`。脚本和测试没有共享代码，这在此处是有意的交叉验证，而不是重复业务逻辑。如果 PowerShell 的路径处理或 Java 的过滤条件发生偏差，文档数字与机械门会出现矛盾，评审就能发现。两种实现只共享公开口径，不共享可能同时出错的内部函数。

## Java 证据检查

本版本首先要求维护脚本能在实际 Windows 仓库上完整运行，并输出 1475 个生产文件而不是在长路径处中断。其次运行 `JavaMaintainabilityBudgetTests`，证明生产和测试聚合预算、五个重点文件上限以及脚本和计划文档的可发现性。该测试属于普通 Maven 测试套件，因此本地 `mvnw verify` 和 GitHub Actions 都会执行。

真正的回归门仍由项目原有体系承担。Spotless 检查新增 Java 测试的格式；SpotBugs 确认没有引入静态缺陷；JaCoCo 保持既有覆盖率底线；全量测试验证订单、库存、支付、Outbox、RabbitMQ、失败事件、审批与运维证据行为。v1834 不以“我没有改业务代码”为理由跳过全量验证，因为构建配置、测试发现和文档门本身也可能发生回归。

账本证据与 Git 证据也要对齐。J43 不再保留一整墙实现叙述，而是指向 v1833 的专用提取文档，同时写明 commit、tag 和 CI run。J44 只记录本版本的状态与主文档指针，详细设计放在 `docs/maintainability/java-maintainability-program-v1834.md`。这落实了评审提出的“进度行不超过约三行”要求，让账本重新承担导航作用。

## mini-kv 证据检查

本版本只修改 Java 仓库，没有读取、重写或移动 mini-kv 的源码、fixture、归档与 tag。mini-kv 在四项目体系中仍是 Java 可消费的上游只读证据源，但源码行数预算是 Java 内部维护规则，不属于跨项目 schema。因此无需等待 mini-kv 发布新版本，也不能把 Java 的阈值写进 mini-kv 仓库。

边界保持的检查重点有两点。第一，维护脚本只扫描 Java 仓库自己的两个源码目录，不跟随绝对路径去统计 `D:\C\mini-kv`。第二，本版本没有改动任何引用 mini-kv 历史证据路径或摘要的 Java 类。即使未来拆分 ReleaseApproval 构建器，也只能移动和组合现有计算，不能改变冻结 fixture 字节、摘要输入顺序或上游路径。

## 阻断与安全边界

本版本冻结所有功能性变化。没有新增写路由，没有打开 active shard router，没有读取凭据值，没有解析原始生产端点，没有连接托管审计系统，没有执行 schema migration，没有触发部署、回滚、恢复，也没有自动启动或停止 Node、Java 或 mini-kv。脚本只做本地只读文件扫描，测试只做源码读取和断言。

维护性预算本身也设置了安全边界。它不自动删除或重写巨型文件，因为机械拆分需要由具体版本结合调用关系和测试完成；它不根据字节数直接判定失败，避免格式差异造成噪声；它不把所有历史大文件永久列为豁免，而是优先列出五个最高风险单点并要求逐版降低。新增大文件即使未进入这五个名字，也会受到聚合档位和最大行数约束。

另一个阻断条件是“不允许空壳拆分”。如果后续只是新增助手类，同时旧类仍保留全部逻辑，生产文件总数增加、单文件上限不降，那么维护性测试和版本文档都不能证明净改善。真正的拆分必须把查询、过滤、导出、审批或摘要构建职责转移到边界清楚、可单测的协作者，并让原文件显著缩小。

## 测试覆盖

`productionSourceHotspotBudgetCanOnlyTighten` 覆盖生产源码最大值和三个档位；`testSourceHotspotBudgetCanOnlyTighten` 对测试源码执行相同检查，并明确禁止出现一千行以上测试文件；`namedPriorityHotspotsCannotGrowBehindAggregateCounts` 逐一读取五个重点文件，避免聚合数字掩盖局部增长；`censusAndProgramKeepTheBudgetReproducible` 保证脚本和计划文档存在，并检查关键字段、唯一命令和基线数字。

这四个测试没有用 fixture 模拟源码树，而是直接读取当前仓库。原因是维护性预算约束的对象就是仓库结构，复制一份假目录会让门失去意义。测试读取是确定性的，不依赖网络、时间、数据库或 Docker。失败时维护者可以立即运行 PowerShell 普查命令查看热点，而不必猜测是哪一个文件突破阈值。

全量验证还会覆盖历史的代码讲解合规测试。本文件在最终 verify 之前写入，包含规定的十个主题标题，中文字符不少于三千，中文占主要比例，并明确写出“禁止硬凑”和“本项目”。内容围绕本项目真实脚本、预算、风险和测试展开，不通过重复口号扩充篇幅。若字数不足，应增加真实工作量和机制解释，而不是堆叠同义句。

## 一句话总结

v1834 的价值是把“这个 Java 项目有巨型文件，应当优化”从口头判断转化为两套可复现统计、四条会失败的聚合预算、五个不会偷偷反弹的单文件上限和一条只能收紧的后续路线；它不改变任何运行行为，却让接下来的深度重构第一次有了明确起点、可量化收益和不可倒退的机械护栏。

本项目从这一版开始不再把拆分当作版本数量游戏。每一刀必须减少真实认知负担、保留既有契约并被测试证明；禁止硬凑文件、字数或所谓优化点。只有原巨型类缩小、职责边界更清晰、预算数字下降且完整验证通过，下一版才算向“更接近完美”前进了一步。
