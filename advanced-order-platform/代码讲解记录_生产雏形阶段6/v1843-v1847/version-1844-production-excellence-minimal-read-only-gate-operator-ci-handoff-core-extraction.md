# version-1844：Operator-CI 交接核心与归档验证拆分讲解

本篇只解释 Java 本项目在 v1844 完成的真实工程变更。它不是新增业务功能，也不是把同一段话换一种说法反复铺开，而是把原先拥挤在根 `ops` 包中的 Operator-CI 交接核心、归档渲染和归档验证实现迁入一个有边界的维护包，并把上游输入、内部计算、下游输出以及安全约束逐项讲清。全文遵守“禁止硬凑”的要求：每一段都对应现有类、现有字段、现有测试或可复现的检查命令。

## 实际工作量说明

这一版迁移了二十七个生产类和七个包内测试。二十七个生产类不是一个可以随手移动的平面清单，而是两层连续流水线。第一层是 Operator-CI 基础交接注册表，包括服务、响应模型、四类目录、分数卡、渲染器和构造支持；第二层是交接归档验证注册表，包括来源快照、制品验证、操作通道验证、CI 批次验证、边界验证、分数卡和 Markdown 渲染。两层之间存在明确依赖，后一层必须读取前一层的公开响应，不能绕过服务自己重建数据。

迁移后，两个 Spring 控制器仍留在根 `ops` 包。这样做不是迁移不彻底，而是遵守当前终局约束：HTTP 入口继续集中可见，复杂实现离开根包。两个控制器只保留构造注入和一次 `service.registry()` 调用，真正的聚合逻辑全部进入 `ops.maintenance.minimalreadonlygateoperatorcihandoff`。与实现紧密相关的七个测试随包移动，两个同时验证控制器映射与 Markdown 输出的测试留根，并通过公开测试工厂访问新包。这种安排让测试位置服从被测责任，而不是简单按文件名前缀一刀切。

根目录直接 Java 文件由六百六十五降至六百三十八，可迁移非控制器由五百六十降至五百三十三，Operator-CI 桶由一百四十降至一百一十三，未归类文件仍为零。总 `ops` Java 文件没有增加，仍受一千三百五十二的上限约束。换言之，这一版得到的是目录复杂度和依赖可见性的下降，不是通过复制类或新建空壳换取表面数字。

## 入口路由

这一组能力有两个只读 GET 入口。第一个入口返回 Operator-CI 基础交接注册表，第二个入口返回该交接内容的归档验证注册表。请求不需要正文，不接收凭据，不接收任意 URL，也不允许调用者通过参数选择写入目标。控制器收到 HTTP 请求后，只调用对应服务的 `registry()` 方法，再把不可变响应交给 Spring 序列化。这里的“输入”实际上是一次无副作用的读取意图，业务输入来自服务内部注入的上游只读证据，而不是用户提交的数据。

路由字符串没有在新包中复制。两个服务都使用 v1840 已公开的 `OpsShardReadinessReleaseAcceptanceRoutePaths`：先取统一基础路径，再拼接各自的相对路径常量。根 `OpsShardReadinessRoutePaths` 仍作为兼容聚合器向控制器提供相同常量，但真正的字节所有权只有一个。这样既保持现有 HTTP 地址完全不变，又避免新包反向依赖庞大的根聚合器。若未来路由所有者发生漂移，v1844 回归测试会因为找不到指定公开所有者而直接失败。

从调用视角看，第一条链是“GET 请求进入根控制器，控制器调用新包基础服务，基础服务读取 v1843 执行归档，返回交接响应”。第二条链是“GET 请求进入归档验证控制器，控制器调用新包归档验证服务，归档验证服务读取基础交接响应，返回验证响应”。两条链都没有命令式动作，也不会因为访问端点而启动 Java、Node 或 mini-kv 进程。

## 响应模型

基础响应是一个 Java `record`。最前面的字段先声明项目、版本以及安全布尔值，包括只读、是否允许执行、是否启动 Java 服务、是否启动 mini-kv、是否读取凭据值、是否解析原始端点和是否允许托管审计 HTTP。随后是端点、配置档、来源计划、必须完成的归档验证计划、建议的操作计划、来源归档版本与端点、交接状态。再往后是各类数量和通过数量，最后才是来源快照、操作通道、CI 批次、边界锁、分数卡、Markdown 章节、检查清单和总状态。

这种字段顺序有实际意义。消费者可以先看安全声明和总状态，再决定是否展开详细列表；自动检查可以直接比较数量字段，不必重新遍历全部内容；人工阅读者又能通过 Markdown 章节理解同一份结构化证据。嵌套记录分别表达来源归档快照、操作通道、CI 批次计划、边界锁、分数卡条目和 Markdown 章节。它们都只携带值，不持有服务、连接或可变仓储，因此响应一旦构造完成就不会在序列化过程中改变。

归档验证响应沿用相同思想，但把问题从“交接计划是否就绪”推进到“交接计划的每一部分是否已形成可核验归档”。它记录一个来源交接快照、六项制品验证、四项操作通道验证、五项 CI 批次验证、八项边界验证、六项分数卡和六个 Markdown 章节。每一类都有总数和通过数，边界类还单独记录锁定数。最终状态不是手写的固定 `passed`，而是所有预期数量、所有通过数量、所有锁定数量、来源状态以及 Markdown 数量共同满足时才为 `passed`，任一条件缺失就为 `blocked`。

## 上游证据配置

v1844 的直接上游是 v1843 已拆出的执行归档验证服务。Spring 在创建基础交接服务时注入 `OpsShardReadinessMinimalReadOnlyGateExecutionArchiveVerificationRegistryService`。基础服务调用它的 `registry()`，拿到一个已经完成来源计划、读取目标、闸门检查、边界检查和归档验证的不可变响应。随后 v1844 只做解释和编排，不再读取原始文件，也不重新判断上游内部细节。上游状态、版本、端点和分数卡都从公开响应取得，这就是包间契约。

这样的配置避免了两种常见问题。第一，v1844 不会越过 v1843 服务直接调用其包内目录，否则上游重构会扩散到整个 Operator-CI 链。第二，v1844 不会把上游证据复制成另一套常量，否则两套数据可能逐渐不一致。基础服务只暴露对上游服务和响应的依赖；归档验证服务再只依赖基础交接服务。依赖方向始终从执行归档流向 Operator-CI 交接，再流向归档验证，形成单向可替换的链。

在测试中，公开测试工厂按照同样顺序组装对象：先创建执行注册表服务，再创建执行归档验证服务，然后创建 Operator-CI 基础服务，最后创建 Operator-CI 归档验证服务。测试没有使用反射注入，也没有为了跨包方便而把内部目录全部改成 public。生产边界只有两组 service/response，测试边界只有两个工厂类，公开面被控制在真实消费者需要的最小范围。

## 服务层核心流程

基础服务的第一步是读取上游执行归档响应。第二步由来源归档目录把上游版本、端点、计划、归档状态和四类验证数量压成一个来源快照。第三步生成四条操作通道，每条通道都有顺序、负责人、来源证据、就绪标记和具体指令。第四步生成五个 CI 批次计划，记录命令族、范围、是否通过以及失败时是否阻断下一批。第五步生成八个边界锁，明确哪些行为必须保持关闭以及关闭原因。

第六步计算五项分数卡。它分别核对上游归档状态、操作通道数量、CI 批次数量、边界锁数量，以及上游分数卡通过数。这里没有模糊的“看起来差不多”：预期和实际完全相等才产生 `passed`。第七步由渲染器根据同一批结构化列表生成 Markdown 章节。第八步由支持类复制所有列表、统计就绪和通过数量、生成检查清单，并在所有通道就绪、所有批次通过、所有边界锁定、所有分数通过且固定数量均正确时给出最终状态。

归档验证服务随后读取基础交接响应。它先形成来源交接快照，再分别构造六项制品验证、四项通道验证、五项批次验证和八项边界验证。各目录只负责一种投影，渲染器只负责把既有结果转成 Markdown，支持类负责不可变复制、计数和最终状态。这种拆分让“数据从哪里来”“怎样转成验证条目”“怎样呈现”“怎样决定总状态”各有位置，避免把所有责任堆进一个巨型服务文件。

一个通俗例子是：上游交付了一份已经封存的执行检查包。基础交接服务像值班负责人，先确认包的版本和状态，再列出四个接手岗位、五批检查任务和八条不能突破的红线；归档验证服务像复核员，逐项确认清单、岗位、批次和红线是否都已被归档，并给出数字化分数卡。接口输出的是这份交接与复核报告，而不是执行任何检查命令本身。

## Java 证据检查

Java 侧首先检查类型与包边界。二十七个实现文件必须只存在于新包，旧根路径必须不存在；两个控制器必须继续存在于根包，并显式导入新包服务和响应。七个包内测试必须进入新测试包，两个控制器 Markdown 测试必须继续留根。这个精确清单比仅检查文件数量更可靠，因为错误移动一个同数量文件也会失败。

其次检查依赖方向。基础服务源码必须包含 v1843 执行归档验证包和公开服务，两个服务都必须使用 v1840 公开 RoutePaths 所有者。仍在根包等待 v1845 迁移的 ArchiveDigest 八个消费者必须显式导入 v1844 归档验证 service 或 response。这样下一刀开始前，下游依赖已预先满足，不需要在 v1845 同时修改上游内部结构。

再次检查静态分析和数字。两个响应及其嵌套 Markdown 记录在 SpotBugs 排除配置中各有两套镜像位置，所有旧根 FQN 必须消失，新包 FQN 必须出现。根文件上限收紧到六百三十八，剩余数固定为五百三十三，Operator-CI 桶固定为一百一十三，总 `ops` Java 文件不得超过一千三百五十二，未归类文件必须为空。任何人若把文件移回根包、复制生产类或放宽上限，机械门都会失败。

## mini-kv 证据检查

这一版没有启动或修改 mini-kv，也没有把 Java 端点伪装成跨项目运行结果。响应中的 `startsMiniKvService` 必须保持为假，服务不执行 `minikv_cli`，不打开套接字，不读取 mini-kv 工作区，也不写入 mini-kv 归档。Java 在这里表达的是“Operator-CI 接手 Java 只读证据时，mini-kv 进程边界仍关闭”，而不是声称已经完成真实联合运行。

mini-kv 相关证据在本链中的作用是边界声明。操作通道和 CI 批次可以引用既有计划名称或来源说明，但不能把引用当成现场执行凭据。若未来系统级验收需要真实 mini-kv 输出，应由独立、显式启用的跨项目套件启动真实二进制、采集新鲜输出并形成统一报告；v1844 的只读服务不能偷偷承担这项职责。这一区分保证单仓证据、冻结契约与真实集成证据不会混为一谈。

因此 mini-kv 检查的输入是现有上游证据中的边界状态，处理是把“不得启动、不得写入、不得解析秘密端点”写入锁和检查清单，输出是响应中的布尔值、边界条目和 `passed/blocked` 状态。没有外部进程就不会产生虚假的运行日志，也不会让一次普通 GET 请求改变另一个仓库的状态。

## 阻断与安全边界

两个服务方法都标注 `@Transactional(readOnly = true)`。这不仅向读者表达意图，也让事务层在支持的数据库上采用只读语义。响应明确把 `executionAllowed`、`startsJavaService`、`startsMiniKvService`、`readsCredentialValue`、`resolvesRawEndpointUrl` 和 `managedAuditHttpAllowed` 保持为假。目录和渲染器只处理内存中的不可变值，没有仓储 `save`、消息发布、进程启动、HTTP 客户端调用、部署或回滚代码。

最终状态采用失败关闭策略。基础层只有在四条通道全部就绪、五个批次全部通过、八条边界全部锁定、五项分数全部通过且来源归档状态通过时才成功。归档层还要求六项制品、四项通道、五项批次、八项边界、六项分数和六个 Markdown 章节全部满足，并确认所有边界既锁定又归档。缺一项不会返回“部分成功”，而是明确 `blocked`。

迁移过程也有工程阻断线：不能改 endpoint 字节来适应包路径，不能把包内目录全部公开来消除编译错误，不能改测试期望或 fixture 让迁移通过，不能提高根文件或总文件上限，不能把控制器藏入深包，不能把历史归档改名。编译器只用于发现真实跨包边界，发现后通过最小 import 和最小 public 面修复，不通过复制实现规避。

## 测试覆盖

第一层是编译门。`test-compile` 会同时编译一千余个生产源和全部测试源，因此遗漏的生产 import、测试工厂可见性或路由所有者都会在运行测试前暴露。v1844 迁移第一次编译准确列出了两个控制器、八个 ArchiveDigest 消费者和 RoutePaths 依赖；补齐最小边界后第二次编译通过，这说明依赖面已经闭合。

第二层是聚焦测试。原有基础服务测试继续检查来源快照、通道、批次、边界锁、分数卡和状态；归档验证的来源、目录、边界分数卡和聚合检查继续验证六、四、五、八、六这些固定计数以及全部通过条件；两个留根 Markdown 测试继续覆盖控制器映射和可读输出。新增 v1844 治理测试则锁定文件精确清单、包路径、上下游 import、SpotBugs FQN、根目录数字和讲解文档。

第三层是历史与全局门。v1843 的历史测试从“必须恰好六百六十五”改为“不得高于六百六十五”，保留前版成果又允许继续下降；当前全局上限、精确计数和 v1809 历史总门同步收紧到六百三十八。终局 census 重新计算所有桶并要求零未归类。Walkthrough 门检查中文占比、必需标题、版本标记和真实篇幅。最后的完整 `mvnw verify` 还会运行所有单元与集成测试、JaCoCo 覆盖率、Spotless 和 SpotBugs，任何一层失败都不允许提交版本收尾证据。

## 维护收益与下一刀

拆分前，任何维护者搜索 Operator-CI 前缀都会在根包看到一百四十个混合层次文件，很难判断基础交接、归档验证、摘要、消费包和验收档案之间的方向。拆分后，基础与归档验证的二十七个实现形成一个内聚包，根包只留下公开 HTTP 入口和后续尚未迁移的明确消费者。IDE 包视图、CodeGraph 调用图和编译错误都会呈现同一个方向，理解成本显著下降。

下一刀是 ArchiveDigest。v1844 已经提前让它的七个 response 消费类和一个 service 消费类导入新包公开边界，因此 v1845 不需要回头打开 v1844 内部目录。它只需移动自己的摘要计算、重放指令、分段目录、来源目录、响应、服务和测试，并继续把控制器留根。这样的“先迁被依赖者，再迁消费者”顺序，使每个版本都可独立编译、独立验证和独立回滚。

## 一句话总结

v1844 把 Operator-CI 交接从根包中的文件堆整理成“v1843 执行归档输入、基础交接聚合、归档验证输出、ArchiveDigest 下游消费”的透明只读链，同时用精确文件清单、状态计数、路由所有权、SpotBugs FQN、中文讲解和全量门禁保证行为没有暗改。
