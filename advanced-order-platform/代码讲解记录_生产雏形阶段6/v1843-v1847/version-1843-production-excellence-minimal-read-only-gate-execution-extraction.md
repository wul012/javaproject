# version-1843：最小只读门执行与归档验证闭包提取

本篇讲解对应本项目 v1843。名称中的“执行”很容易让人误以为接口会启动服务、运行部署或写入路由，实际代码恰好用于证明这些动作仍被禁止。基础注册表描述一次最小只读门应该检查哪些来源计划、读取目标、门条件、边界规则、持续集成批次、归档要求和人工交接；归档验证注册表再逐项确认这些证据已经形成可审阅快照。两层都只构造内存值并返回 `passed` 或 `blocked`，不执行响应里描述的命令。本文只解释真实结构、真实输入输出与真实失败条件，禁止硬凑。

v1843 也是下一条 Operator-CI 依赖链的起点。后续核心注册表以本版归档验证响应作为唯一执行证据来源，再依次形成归档验证、摘要、消费者包和验证档案。先提取被依赖的 Execution 闭包，可以让后续每版只导入一个已经稳定的公开边界，避免从链尾向前搬时反复修改包名和公开面。

## 实际工作量说明

本版迁移三十一个非控制器生产类。其中基础注册表由服务、响应、支持、总渲染器、渲染支持，以及来源计划、读取目标、门检查、边界策略、持续集成批次、归档要求和操作员交接目录组成；归档验证注册表由服务、响应、支持、总渲染器、渲染支持、来源快照、制品验证、读取目标验证、门检查验证、边界验证、持续集成验证、操作员交接验证和评分卡组成。两部分共享同一语义闭包，归档层只读取基础层，因此一次迁移比拆成两个小版本更完整。

十三个包内测试和测试支持随实现进入新包，两个控制器测试留在根包。留根测试通过两份公开测试工厂装配服务；四个仍在根包的 Operator-CI 后续测试工厂也显式导入本版两级服务。公开测试工厂只是测试代码的装配桥，不会进入生产制品，也没有迫使目录、渲染器或支持类变为公开。

根包直接生产文件由六百九十六降为六百六十五，最终允许保留的一百零五不变，仍待迁移的非控制器文件由五百九十一降为五百六十。MinimalReadOnlyGateExecution 桶由三十一降为零，未归类文件保持为零，全部运维生产文件仍不超过一千三百五十二。这个结果说明文件真实离开根包，同时没有通过复制类、改统计脚本或增加新生产文件伪造下降。

静态分析配置中的八个全限定名也同步迁移。八条规则来自两组镜像，每组覆盖基础响应、基础章节记录、归档验证响应和归档章节记录。机械守卫要求新全限定名存在、旧根包响应名不存在，从而保证包移动不会让原本用于集合暴露分析的规则悄悄失效。

## 入口路由

对外保留两个只读入口。基础注册表入口的后缀是最小只读门执行注册表，归档入口的后缀是最小只读门执行归档验证注册表。两个 Spring 控制器继续位于根包，便于维护者在固定位置浏览全部 HTTP 入口；服务、响应和内部目录进入维护包，减少根包同级类数量。

控制器仍以根包全局聚合器声明请求映射。迁入的两个服务则直接读取 v1840 已公开的发布验收路由所有者，因为该所有者已经是这两个后缀的真实来源，根包聚合器也只是委托给它。这样控制器和服务虽然位于不同包，最终仍引用同一字节字符串，没有新建第三份常量，也没有增加生产文件总量。

一次请求不需要请求体。调用方读取基础入口时，控制器调用基础服务的注册方法；读取归档入口时，控制器调用归档服务，后者先调用基础服务取得同一份结构化响应。控制器不解析操作命令、凭据值、原始端点或部署参数。两个服务都标记只读事务，且实现没有仓储写入、进程启动、网络执行或文件写入对象。

包迁移后，两个控制器只显式导入对应服务和响应；后续 Operator-CI 核心只导入归档验证服务和响应。这是生产跨包面的全部内容。其他三十余个目录与渲染器保持包级可见，因此外部代码不能绕过支持类自行拼装一个“通过”响应。

## 响应模型

基础响应首先记录项目、版本、只读标记和一组能力标记。只读为真，执行许可、启动 Java、启动 mini-kv、读取凭据值、解析原始端点和受管审计 HTTP 均为假。随后记录端点、配置标识、来源计划、前一冒烟通道、注册表状态和各类证据数量，最后携带结构化集合、渲染章节、检查清单与最终状态。

基础响应包含五条来源计划、五个读取目标、二十个门检查、十条边界规则、四个持续集成批次、六项归档要求和五项操作员交接。来源计划记录版本、标题、角色及检查数；读取目标记录所有者、协议、地址句柄、命令或路由，以及是否只读、是否由外部启动；门检查记录分组、证据与通过状态；边界规则记录被禁止动作和理由；持续集成批次记录顺序、命令族、范围及是否阻断下一批；归档与交接则描述应保存什么以及人工如何继续。

归档验证响应继续保留相同的只读与能力标记，并记录基础注册表版本和端点。它包含一份来源快照、六项制品验证、五项读取目标验证、二十项门检查验证、十项边界验证、四项持续集成批次验证、五项操作员交接验证和七条评分卡。每项验证都保留来源事实与归档状态，调用者可以看出是来源本身失败、没有归档，还是数量不匹配。

两层响应都使用记录类型承载不可变值。支持类先对所有列表执行不可变复制，再基于复制后的内容计算数量、检查文本和状态。调用方不能在状态计算完成后通过旧列表引用增删元素，也不能把“检查时通过、返回时被改动”的数据交给下一层。

## 上游证据配置

基础注册表没有运行时服务上游。它从版本化静态目录读取 Node v367 计划、前序门决定、常规门和冒烟通道等来源描述，并把这些描述转成 Java 侧可机械检查的值对象。这里的 Node 版本是证据来源标识，不是 Java 接口启动 Node 或读取 Node 工作区的授权。

归档验证服务唯一的服务上游是同包基础注册表服务。它调用基础注册方法，得到版本、端点、五类能力标记和七组结构化证据，再由各验证目录映射成归档视图。它不会重新访问根包的旧实现，也不会分别抓取多个横向服务，因此依赖方向只有“基础注册表到归档验证”。

下游 Operator-CI 核心的注册服务、通道目录、支持类和来源归档目录会读取归档验证响应。v1843 为这四个消费者增加新包导入，并保持归档服务和响应为公开；基础服务也公开，因为归档服务构造和后续测试装配需要它。其他实现仍然内部可见。

这条依赖顺序可以写成：静态来源计划生成基础响应，基础响应生成归档验证响应，归档验证响应生成 Operator-CI 核心响应。下一版移动核心时，它将直接消费已经稳定的新包边界；再下一版摘要层也只消费上一层。这样的顺序把跨包变化限制在当前消费者，而不是让所有后续层同时感知多个旧地址。

## 服务层核心流程

基础服务先分别调用来源计划、读取目标、门检查、边界策略、持续集成批次、归档要求和操作员交接目录。总渲染器把这些集合组织为可人工审阅章节，支持类复制集合，统计通过读取目标、通过门检查和被拒绝边界的数量，再生成包含数量与禁止事项的检查清单。

基础状态函数采用完全匹配而不是多数规则：通过读取目标数必须等于读取目标总数，通过门检查数必须等于门检查总数，被拒绝边界数必须等于边界规则总数。只要一个读取目标不是通过、一个门检查失败，或一条禁止动作被错误允许，状态就返回阻断。持续集成、归档要求和操作员交接虽然也进入响应，但不会被接口自动执行。

归档验证服务取得基础响应后，构造一份来源快照，并依次生成制品、读取目标、门检查、边界、持续集成和操作员交接验证。评分卡把七组预期数量与实际数量对照；渲染器把验证结果转换为章节；支持类复制所有列表并统计每组通过数。

归档状态要求六项制品验证、五项读取验证、二十项门验证、四项持续集成验证、五项交接验证和七条评分全部通过，同时十条边界都必须保持拒绝。任何一组少一项、状态不为通过，或边界出现允许值，结果都为阻断。归档验证不会因为基础响应写着通过就跳过逐项核对。

用通俗例子说明：基础响应像一张只读演练清单，列出应该看哪些目标、哪些门必须绿、哪些动作永远不许做；归档验证像复核员逐格检查清单是否有证据、数量是否齐全。复核员可以报告通过或阻断，但手里没有启动系统、读取密码或执行部署的工具。

## Java 证据检查

Java 编译器首先验证真实边界。三十一个实现改包后，第一次生产编译只指出两个留根控制器和四个 Operator-CI 消费者缺少服务或响应导入。补齐后主编译通过。测试编译继续指出两个控制器测试和四个后续测试工厂需要新测试或服务导入；仅公开两份测试工厂的方法后，完整测试编译通过。没有为了省事把全部类改为公开。

v1843 结构守卫逐个枚举三十一个生产文件，要求新包存在、根包旧位置消失，同时要求两个控制器仍在根包。它逐个枚举十三个迁移测试，要求新测试包存在、旧位置消失，并确认两个控制器测试留根。这样的精确清单能发现漏移、重复和误搬控制器。

依赖守卫读取两个真实服务，确认它们使用公开路由所有者，并确认归档验证服务消费基础服务。它还读取 Operator-CI 注册服务、通道目录、支持类和来源目录，要求四者显式导入新包的归档验证响应。静态分析守卫检查两种响应的新全限定名并禁止旧响应名。

计数守卫要求根包精确等于六百六十五，全部运维生产文件不超过一千三百五十二；终局 census 要求保留一百零五、待迁移五百六十、Execution 桶为零、未归类为空。v1842 的六百九十六从精确值降为历史上界，v1843 持有新的精确值，全局上限与镜像精确门同步下降，阈值没有回升。

## mini-kv 证据检查

虽然基础响应包含读取目标和命令描述，本版不会启动、停止或修改 mini-kv。读取目标中的命令只是供人工或独立联合测试识别的文本，服务没有进程构造器、命令执行器、网络客户端或文件写入器。响应字段明确把启动 mini-kv 标记为假。

因此 mini-kv 对本接口没有运行时输入，本接口对 mini-kv 也没有运行时副作用。Java 可以证明的是：相关边界规则全部被拒绝、检查清单记录不自动启动上游、不写路由、不读取秘密、不解析原始地址和不连接受管审计环境；它不能据此声称真实跨项目联合测试已经运行。

未来若做联合验收，应由显式启用的系统测试启动真实可执行文件、采集新鲜输出、检查退出码和清理进程。那套执行能力必须与当前注册表分离，不能因为字段名含“执行”就塞进只读观察接口。

## 阻断与安全边界

基础层在读取目标、门检查或边界拒绝数量不完全匹配时阻断。归档层在任一制品、读取目标、门、持续集成、交接或评分未通过，或任一禁止边界未拒绝时阻断。后层不会把前层阻断改写为通过，也没有“只差一项可以忽略”的容错捷径。

能力字段形成第二道透明边界：执行许可为假，启动 Java 为假，启动 mini-kv 为假，凭据读取为假，原始端点解析为假，受管审计 HTTP 为假。服务还没有订单、库存、支付或事件仓储依赖，所以只读事务之外也不存在隐藏写入路径。

持续集成批次只描述命令族、范围和阻断顺序。接口不会在请求线程中运行 Maven、GitHub Actions 或脚本。归档要求只描述需要保存的证据，不会写磁盘或移动历史目录。操作员交接只描述人工步骤，不会把文本解释成自动化指令。

## 测试覆盖

基础层测试覆盖来源计划、读取目标、门与边界目录、渲染结果、服务状态和控制器路由。归档层测试覆盖来源快照、制品与读取目标验证、门与边界验证、持续集成与交接、评分卡、渲染章节、不可变集合、服务状态和归档控制器。

两份测试支持负责稳定装配基础服务和归档服务。根包控制器测试通过公开测试工厂复用装配；后续 Operator-CI 测试工厂直接导入公开生产服务，验证整个依赖链仍可构造。测试支持公开面只存在于测试源码，不改变生产 API。

聚焦门会同时运行 Execution 全簇、Operator-CI 核心回归、v1842 历史守卫、v1843 精确守卫、终局 census、维护性预算和讲解合规。最后仍执行完整 `mvnw verify`，覆盖 Spring 上下文、订单与库存等业务回归、格式、覆盖率和 SpotBugs。实施提交和证据提交各自触发远端流水线，下一版开头检查上一版结果。

## 一句话总结

v1843 把三十一个最小只读门执行与归档验证实现、十三个包内测试完整移出根包，在两个入口、两类响应、路由字节和禁止能力不变的前提下，把根包从六百九十六收紧到六百六十五，并为后续 Operator-CI 五级证据链建立了稳定、单向、可阻断的上游边界。
