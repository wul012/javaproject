# version-1845：Operator-CI 归档摘要层拆分讲解

本篇解释 Java 本项目 v1845 的真实工作。这里的 ArchiveDigest 可以译成“归档摘要”，它不是密码学哈希服务，也不会重新执行 CI，更不会把尚未发生的跨项目运行包装成已经发生。它接收 v1844 已形成的 Operator-CI 归档验证响应，把其中分散的来源、制品、通道、批次、边界和分数浓缩为一份适合下游 ConsumerPackage 使用的只读摘要。全文遵守“禁止硬凑”：每项说明都能追到现有字段、目录类、服务调用或测试断言。

## 实际工作量说明

这一版迁移十七个生产类和五个包内测试。生产类覆盖摘要服务与响应、来源归档投影、摘要分区、消费包预览、只读重放指令、边界锁、分数卡、Markdown 渲染以及各自的支持类。它们此前与后续 ConsumerPackage、VerificationDossier 和验收归档混在根 `ops` 包中，虽然类名前缀相近，责任却处于不同阶段。v1845 把“从归档验证生成摘要”这一段单独归入 `ops.maintenance.minimalreadonlygateoperatorcihandoffarchivedigest`。

Spring 控制器继续留在根包，控制器 Markdown 测试也继续留根。控制器只承担公共 HTTP 入口、构造注入和调用服务；Markdown 测试同时关心根入口与可读输出，留下更符合其责任。其余五个测试紧贴服务、来源、目录、消费与重放逻辑，随实现移动。新包只公开服务、不可变响应和一个测试工厂，所有目录与渲染器继续保持包内可见，没有为了省几条 import 就把内部实现整体暴露。

根目录文件从六百三十八降到六百二十一，可迁移非控制器从五百三十三降到五百一十六，Operator-CI 桶从一百一十三降到九十六，未归类仍为零。总 `ops` Java 文件不增加，继续受一千三百五十二上限约束。数字下降来自十七个既有文件的真实迁移，不来自删除保护测试、不来自提高豁免、不来自新建空目录。

## 入口路由

归档摘要端点是一个无请求体的只读 GET。调用者不提交命令、路径、凭据、主机地址或运行参数。根控制器使用统一基础路径和 ArchiveDigest 相对路径接收请求，然后调用新包服务的 `registry()`。服务返回不可变响应，控制器不加工、不缓存、不写库，只交给 Spring 序列化。输入因此可以分为两层：外部输入只是“读取摘要”的 HTTP 意图，内部业务输入是通过构造注入获得的 v1844 归档验证服务输出。

迁移前服务从根 `OpsShardReadinessRoutePaths` 读取常量；迁移后直接使用 v1840 已公开的 `OpsShardReadinessReleaseAcceptanceRoutePaths`。基础路径和相对路径字节完全相同，只改变编译期所有权。根路由聚合器仍为旧控制器提供兼容入口，但新包不再依赖根包的庞大聚合文件，也没有复制同一字符串。若路由被改写、另建第二所有者或聚合器超过一千一百一十一行，已有门禁会失败。

一次典型调用是：运维界面发出 GET，请求不携带正文；控制器调用摘要服务；摘要服务先读取 v1844 归档验证注册表，再产生六类摘要分区、四个消费包预览、五条重放指令、八个边界锁和六项分数；支持类计算总状态；响应被序列化返回。整个过程中没有执行批处理命令，也没有调用 Node 或 mini-kv。

## 响应模型

响应使用 Java `record`，开头先给出项目、版本和安全布尔值：只读必须为真，允许执行、启动 Java、启动 mini-kv、读取凭据值、解析原始端点、允许托管审计 HTTP 必须为假。之后给出端点、配置档、来源计划、必需归档验证计划、Operator 交接计划、来源归档版本、端点、状态和当前摘要状态。消费者无需展开列表，就能先判断这份数据来自哪里以及是否越过安全边界。

中间的计数字段分别记录一个来源快照、六个摘要分区及通过数、四个消费包及就绪数、五条重放指令及只读数、八个边界锁及锁定数、六项分数卡及通过数、六个 Markdown 章节。后半部分再给出对应列表、检查清单和总状态。总数与列表同时存在不是重复：机器可以用计数快速做守卫，人和审计工具可以继续展开具体条目核验。

嵌套模型各自只表达一种事实。`SourceArchiveSnapshot` 保存 v1844 版本、端点、配置档、来源交接版本、归档状态及四类验证数量；`DigestSection` 保存某类证据的来源总数、通过数、文本证据和状态；`ConsumerPacket` 表示摘要预备交给哪个角色以及是否同时包含摘要和边界锁；`ReplayInstruction` 表示已有 CI 批次在需要复核时应怎样先复用归档；`BoundaryLock` 保存禁止行为及锁定原因；分数卡和 Markdown 则分别面向机械判定与人工阅读。

## 上游证据配置

唯一生产上游是 v1844 的 `OpsShardReadinessMinimalReadOnlyGateOperatorCiHandoffArchiveVerificationRegistryService`。Spring 将它注入 ArchiveDigest 服务，服务调用 `registry()` 获取公开响应。摘要层不会访问 v1844 包内的制品目录、通道目录或渲染器，也不会从文件系统重新扫描所谓归档。这样一来，上游只要保持 service/response 契约，内部如何拆分对 v1845 完全透明。

来源响应已经包含六项制品验证、四项操作通道验证、五项 CI 批次验证、八项边界验证、六项分数卡和六个 Markdown 章节。v1845 不篡改这些事实，而是按消费视角重新投影。例如摘要分区的 `artifact-verifications` 直接使用上游制品总数和通过数；`boundary-lock-verifications` 直接使用上游边界总数、通过数与锁定数。来源未通过时，相应摘要不会被强行标记通过。

测试工厂也沿同一链构建对象：执行基础服务、执行归档验证服务、Operator-CI 基础服务、Operator-CI 归档验证服务，最后才是摘要服务。这个顺序让测试输入接近真实依赖注入，而不是绕过上游手工拼一个“永远通过”的响应。公开测试工厂只为留根控制器测试和 v1846 ConsumerPackage 测试提供入口，其他测试继续在包内直接访问必要的目录。

## 服务层核心流程

服务第一步读取 v1844 归档验证响应。第二步由来源目录压成一个来源快照，记录上游版本、端点、配置、交接版本、归档状态以及制品、通道、批次、边界四类数量。第三步生成六个摘要分区：来源交接快照、制品验证、操作通道验证、CI 批次验证、边界锁验证和来源归档分数卡。每个分区都比较来源总数与来源通过数，完全相等才为 `passed`。

第四步生成四个消费包预览，分别面向 operator、CI、operator-CI 和 release-review。四个包都声明包含摘要与边界锁，是否就绪取决于上游总状态。第五步从上游五个 CI 批次验证映射五条重放指令。指令的核心不是“立即重跑”，而是“任何重跑前先复用对应批次的归档证据”；`readOnly` 固定为真，只有上游批次通过且指令只读时才通过。

第六步把上游八项边界验证逐条映射成八个边界锁。锁保留代码、禁止行为和锁定状态，原因文本区分“归档边界仍被锁定”与“缺失归档边界锁”。第七步计算六项分数卡，核对来源状态、摘要分区、消费包、重放指令、边界锁以及来源分数卡。第八步把同一结构化结果渲染为六个 Markdown 章节。最后支持类复制列表、统计通过数并计算总状态。

总状态采用全量合取：来源必须通过；快照必须恰好一个；六个摘要分区全部通过；四个消费包全部就绪；五条重放指令全部只读；八个边界全部锁定；六项分数全部通过；Markdown 必须恰好六节。任一条件不满足就返回 `blocked`。因此 ArchiveDigest 不是把复杂状态压成一个乐观标签，而是把各类数量和失败位置同时保留下来。

## Java 证据检查

第一组机械证据锁定文件边界。十七个生产文件必须出现在新包且不再出现在根包，新包生产文件数量必须恰好十七；五个测试必须出现在新测试包且旧路径消失，新包测试数量必须恰好五。根控制器和根控制器 Markdown 测试必须仍在，并且必须导入新包。这可以发现错移、漏移、复制和控制器隐藏等问题。

第二组证据锁定调用方向。摘要服务必须导入 v1844 归档验证公开边界，必须使用 v1840 公开 RoutePaths 所有者。仍在根包的十一个 ConsumerPackage 生产类必须导入摘要 service 或 response，不能访问摘要包内目录。v1844 历史门也被推进到新包读取摘要文件，它继续验证“摘要只能消费 v1844 归档边界”，没有删除或放松原断言。

第三组证据锁定配置与数字。SpotBugs 中摘要响应和嵌套 Markdown 响应在两套镜像块共四条 FQN 必须全部指向新包，旧根 FQN 必须为零。全局根上限、精确根计数和 v1809 历史门同步收紧到六百二十一；终局 census 要求五百一十六个剩余非控制器、九十六个 Operator-CI 文件和零未归类。总 Java 文件仍不得超过一千三百五十二。

## mini-kv 证据检查

ArchiveDigest 名称容易让人误以为它会读取 mini-kv 中保存的摘要，但本版没有这种行为。代码不启动 `minikv_cli`，不建立 RESP 连接，不读取 mini-kv WAL 或快照，不修改 mini-kv 仓库，也不调用 Node 代为执行。`startsMiniKvService` 必须为假，`executionAllowed` 也必须为假。输入完全来自 Java 内存中的 v1844 不可变响应。

mini-kv 在这条链中的意义是边界对象之一：系统未来可能由跨项目套件读取真实 mini-kv 输出，但普通 Java GET 只能报告“当前交接摘要保持只读，未启动 mini-kv”。重放指令也只建议先复用归档证据，不负责执行命令。这样避免了访问一个报告端点却意外启动外部进程，也避免把静态契约对齐误写成真实联合测试。

若将来系统验收需要新鲜 mini-kv 结果，输入应是显式启用的环境和真实二进制，处理应由独立集成套件完成，输出应带运行时间、命令退出码和新鲜证据。v1845 的输入、处理和输出都没有这些元素，因此文档只声称单仓只读摘要与跨项目边界保持一致，不声称完成现场联调。

## 阻断与安全边界

摘要服务标注 `@Transactional(readOnly = true)`，所有目录只从上游响应生成内存值，没有仓储保存、消息发布、网络调用或文件写入。响应的危险能力布尔值全部关闭。八个边界锁继承上游锁定事实；若任一边界没有归档或没有锁定，总状态就被阻断。五条重放指令固定为只读，并明确要求任何重跑前先复用归档证据。

工程迁移也遵守失败关闭。不能为消除编译错误而公开所有目录，不能复制路由字符串，不能更改响应记录，不能删除失败测试，不能修改 fixture 字节，不能提高 root 或总文件上限，不能改历史归档路径。编译器发现的跨包消费者通过最小 service/response import 修复；SpotBugs 通过 FQN 迁移修复；历史门通过更新真实文件位置修复，而不是降低断言。

ConsumerPackage 是下一层，但 v1845 不提前迁移它。摘要层只把公开边界准备好，保持本版范围可验证、可回滚。若 ConsumerPackage 需要包内目录才能工作，应视为边界设计失败；当前十一个消费者只使用公开 service/response，证明这条切分线成立。

## 测试覆盖

编译门先验证一千余个生产源和全部测试源。v1845 移动后第一次 `test-compile` 直接通过，说明根控制器、根 Markdown 测试、ConsumerPackage 生产类与测试支持都已获得正确 import，公开测试工厂的可见性也足够。一次通过不替代测试，但它表明包图没有悬空类型。

聚焦测试覆盖摘要来源、六类目录、消费包、重放指令、聚合状态和控制器 Markdown 输出。新增治理测试再覆盖十七和五的精确清单、控制器留根、v1844 上游、v1840 路由所有者、十一个下游消费者、SpotBugs FQN、六百二十一根文件以及讲解文档。v1844 历史门继续验证自己的边界，终局 census 重新分类全部根文件。

最终还要执行完整 `mvnw verify`。它会运行全部单元与集成测试、生产配置测试、架构和维护预算门、Walkthrough 中文与篇幅门、JaCoCo 覆盖率、Spotless 和 SpotBugs。只有完整门成功，才能提交实现；远端 CI 启动后才能补账本；版本末尾还要用第二提交和注释 tag 收口。任何失败都会留在本版修复，不把问题推给 v1846。

## 下一层输入输出关系

v1846 ConsumerPackage 的输入将是 v1845 公开摘要响应。它不需要知道六个摘要分区如何计算，也不需要访问边界目录，只需读取来源版本、摘要状态、四个预备消费包、五条只读重放指令和八个边界锁，再组装面向实际消费者的清单、受众、CI 矩阵、清单文件和分数卡。v1845 已让十一个下游类显式导入新包，因此下一版迁移时不会反向改动摘要内部。

从端到端看，v1843 提供执行归档，v1844 把它转成 Operator-CI 交接和归档验证，v1845 再压成可消费摘要。每一步输入都是上一层公开不可变响应，处理只做确定性映射、计数和失败关闭，输出都保留来源版本、端点、详细列表、检查清单和总状态。这种透明链比一个巨型类同时读取、执行、渲染和验收更易维护。

## 一句话总结

v1845 把归档验证转换为结构化摘要的十七个实现和五个测试收进独立包，以一个公开 service/response 边界连接 v1844 与 ConsumerPackage，并用只读重放、全量状态合取、精确 census、SpotBugs FQN 和完整门禁证明它只整理证据，不执行系统。
