# v1805 候选文档注册表整体迁出代码讲解（J15）

本版本是 v1796 清查之后的第九刀契约保持型整理，也是迄今为止单次迁移规模最大的一刀。它把整个候选文档注册表家族——请求包交接、提交预检、收件包、材料请求、材料提交预检、材料提交预检交接、画像分区注册表，以及请求包本体这八条注册表通道——从根 `ops` 包整体迁入新建的 `ops.maintenance.candidatedocument` 子包。迁移共搬动五十七个非控制器实现文件以及家族路由常量类，八个对外控制器与全局路由聚合类继续留在根包。所有路由、响应结构与只读语义逐字节不变。这份讲解先于完整验证写成，逐项据实陈述，绝不把字数留到验证之后才补，也禁止硬凑凑数。

之所以敢把这么大一个家族一次性迁走，是因为先用并行普查为候选家族测算了跨家族端点耦合边数，候选文档家族测出的端点边数为零，是所有候选里最干净的；随后我又用直接检索做了对抗式复核，纠正了一条早期记忆中“候选文档存在耦合”的过时判断，确认这个家族确实自成一体。正是这种“先量化耦合、再对抗式复核、最后才动手”的纪律，让这一刀在体量巨大的同时仍然风险可控。

## 入口路由

候选文档家族对外暴露八条只读注册表路由，分别对应八个控制器：请求包交接、提交预检、收件包、材料请求、材料提交预检、材料提交预检交接、画像分区注册表与请求包本体。每条路由都由共享的基础路径拼接上一段以候选文档为前缀的后缀常量构成，例如收件包、材料请求、画像分区注册表等后缀。

这些后缀常量原本集中存放在家族路由常量类里，而该常量类此前是包级可见、且其后缀由全局聚合类逐一委派转发。迁移时我把家族路由常量类一并搬入新子包，并将其改为公开类、补上公开的基础路径常量、把全部后缀常量改为公开。控制器仍然留在根包，并继续从全局聚合类读取这些后缀，因此控制器的路由声明无需任何改动；真正需要改动的只是被搬走的实现文件——它们改为直接引用迁入子包后的家族路由常量类。

## 响应模型

家族内的九个响应记录（请求包、请求包交接、提交预检、收件包、材料请求、材料提交预检、材料提交预检交接、画像分区注册表等）随家族一起迁入子包。这些响应模型聚合各通道的来源回执、目录条目、画像分区、交接说明、校验闸门、运行期边界等只读字段，并附带渲染后的段落文本，全部使用不可变集合。

迁移不改动任何响应记录的字段、顺序或不可变语义，只改变它们所在的包。由于这些响应记录此前被静态分析以受控暴露豁免方式标注，搬包会让原先按完整类名匹配的豁免失配，因此我把静态分析豁免清单里十九条候选文档相关条目（覆盖九个响应类）整体改写到迁入子包后的新类名前缀，保持“只缩不增”的豁免基线不被破坏。

## 上游证据配置

候选文档家族的依赖注入全部是家族内部注入：注册表服务在构造时组合本家族的兄弟服务，而不依赖任何外部证据服务。正因如此，整个家族可以作为一个整体平移，不会产生跨包的服务装配缺口，这也是它比之前几刀更干净的关键所在。

唯一一处真正的跨家族关系，是两个候选文档目录类引用了“对照证据候选收件预检目录”这条路由——它原本由全局聚合类以字面量内联定义。普查最初按端点常量口径统计时漏掉了这条以路由常量形式存在的跨家族引用，是完整编译阶段以“找不到符号”精确报出来的。我把这条路由常量迁入候选文档路由常量类作为其唯一定义处，并让全局聚合类改为委派引用它，这样既消除了字面量重复，又与聚合类对所有家族常量一贯的委派模式保持一致；对照证据家族仍然经由聚合类读取同一取值，行为完全不变。

## 服务层核心流程

家族内的服务层流程保持不变：每个注册表服务在初始化时把家族路由常量类的基础路径拼接上自己的后缀常量得到只读端点，随后依据本家族的目录、画像分区、交接、校验、运行期边界等只读数据组装结果，最后交由渲染器与支撑类拼成响应。迁移没有改动任何业务逻辑，只把服务读取路由常量的来源从包级可见的全局聚合类改为公开的家族路由常量类。

之所以必须改这个来源，是因为全局聚合类是包级可见的，搬到子包后的服务无法再访问它。由于该家族对外端点边数为零，家族文件里出现的每一处聚合类引用都指向候选文档自己的后缀或基础路径，于是可以用一次整体替换把它们统一改为家族路由常量类引用，再补齐那条对照证据跨家族常量即可。替换之后家族文件之间彼此同包，互相引用无需任何导入。

这里值得特别说明家族内部依赖注入为何能整体平移而不破裂。候选文档家族里的注册表服务在构造时注入的，全部是本家族的兄弟服务，例如材料提交预检交接服务会组合材料提交预检服务与材料请求服务。这些被注入的类型与注入它们的类型在迁移后仍然处于同一个子包，因此构造关系在搬包前后保持完全一致，既不需要把任何被注入类型改为公开，也不需要在跨包之间补充导入。这与之前几刀里服务注入外部证据服务、必须把外部类型与端点常量逐一公开的情形截然不同，正是“家族内部自洽”这一特性，让一个五十七文件的大家族能够以最小的可见性改动整体迁出。换句话说，真正决定迁移代价的不是文件数量的多少，而是家族边界是否清晰、对外耦合是否收敛；候选文档家族恰好两者兼备，所以体量虽大，改动面却很窄。

## Java 证据检查

Java 侧证据检查按“编译先行、分步收敛”的方式推进。第一轮仅编译先暴露出两处跨家族路由常量缺口，我据此把那条对照证据常量迁入家族路由常量类并让聚合类委派，随后主编译一次通过。第二轮仅测试编译又暴露出三处留在根包的测试引用了随家族迁走的两个共享测试支撑类，我把这两个支撑类及其被引用的静态方法改为公开，并为三个根包测试补齐导入，测试编译随之通过。

第三步由完整验证流水线统一校验：单元测试全绿、各包覆盖率地板满足、静态分析零新增、代码风格零违规。治理阈值方面，根包直接文件数从一千二百四十降到一千一百八十三，单刀减幅五十七，是本项目整个整理计划里最大的一次，我把治理护栏阈值同步下调到一千一百八十三。

## mini-kv 证据检查

本次迁移与 mini-kv 没有任何关系。候选文档家族是只读证据接口，不发起任何连接，也不读写任何键值。家族内若有涉及 mini-kv 的陈述，也仅停留在只读响应里对证据边界的描述层面，迁移不会触发 mini-kv 的真实连接或自动启动。

因此可以明确：本版本对 mini-kv 的运行时行为零影响，既不改变连接语义，也不改变任何存储读写语义。整刀只是把候选文档相关类换了一个包，并把跨家族常量收敛为单一委派，不触及任何网络或存储动作。

## 阻断与安全边界

本版本严格守住既有安全边界。它不打开任何写路由、不路由活跃分片、不读取凭据值、不解析原始端点地址、不建立受管审计的网络连接、不部署、不回滚、不触发 Java 或 mini-kv 的自动启动。它所做的全部，就是把候选文档家族换包、把家族路由常量类公开、把一条跨家族常量收敛为委派，并让留在根包的控制器与测试补齐对迁入类型的导入。

归档边界同样不可触碰：本次迁移不重命名也不移动任何归档根目录，从 `a/` 到 `f/`、形如 `e/<version>/` 的目录、各类证据 JSON、截图归档以及历史代码讲解目录都原地不动，Node 侧对 Java 证据归档的引用因此不会失效。

## 测试覆盖

测试侧按职责拆分：十一个测试留在根包，因为它们要么断言留在根包的控制器，要么断言全局聚合类的包级常量；这十一个测试改为导入迁入子包后的实现与路由常量类型。另有三十个纯家族内测试随家族迁入测试子包，它们与被测类型同包，互相引用无需导入。

为支持迁移，两个被根包测试引用的共享测试支撑类被改为公开类，其被引用的静态构造方法也一并公开，使得迁走的测试与留守根包的测试都能据此构造家族服务。新增的专门守护测试逐一断言代表性实现文件确实位于新子包、不再出现在根包，并断言八个控制器与全局聚合类仍留在根包；治理阈值守护测试则把根包直接文件数从一千二百四十收紧到一千一百八十三。

## 实际工作量说明

本节据实说明工作量，绝不夸大，也禁止硬凑字数。本次真实改动包括：用版本控制移动五十七个家族实现文件与家族路由常量类、改写其包声明、把家族内对聚合类的引用整体改指到家族路由常量类；把家族路由常量类公开、补公开基础路径、公开后缀常量；为那条对照证据跨家族常量在家族路由常量类里建立唯一定义并让聚合类委派；迁移三十个家族内测试、把两个共享测试支撑类及其方法公开、为三个根包测试补齐导入；把十九条静态分析豁免条目改写到新类名；下调治理阈值；新增守护测试、整合说明文档、变更日志、进度行、子目录索引与本讲解。

这一刀的难点不在体力，而在判断与收敛：必须先以零端点边数为信号锁定候选家族，再以对抗式直接检索复核“是否真的零耦合”，最后还要靠完整编译把普查口径之外的那条跨家族路由常量逼出来并妥善收敛。本项目正是通过这种逐层验证，才把一个五十七文件的大家族在契约逐字节不变的前提下安全迁出。

## 一句话总结

本项目在 v1805 把整个候选文档注册表家族迁入新建的 `ops.maintenance.candidatedocument` 子包，根包直接文件数从一千二百四十降到一千一百八十三，是整个整理计划迄今最大的一刀，所有路由取值与只读语义逐字节不变。
