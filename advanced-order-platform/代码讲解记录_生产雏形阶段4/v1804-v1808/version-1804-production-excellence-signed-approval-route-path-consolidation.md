# v1804 签名审批路由常量叶子整合代码讲解（J14）

本版本是 v1796 清查之后的第八刀契约保持型整理，但它与前面七刀都不同：前面七刀搬动的是某个注册表的实现层（服务、目录、渲染器、响应、支撑等），而这一刀只整合三个纯粹的路由常量持有类——签名审批的草稿就绪、捕获工件预检、捕获预检三个路由常量类——把它们迁入新建的 `ops.maintenance.signedapproval` 子包。本版本不搬动任何服务、控制器或响应。它的目的，是先把签名审批维护子包连同它共享的路由常量叶子立起来，为后续体量更大的操作员证据取值供给签名审批注册表家族整体迁入预留落点。这份讲解先于验证写成，逐项据实陈述，绝不把字数留到验证之后才补，也禁止硬凑凑数。

之所以这一刀刻意做小，是因为根 `ops` 包里剩下的体量较大的家族，普遍呈现两种纠缠：其一，它们的服务与控制器并不直接引用自己家族的路由常量类，而是统一从根部的全局路由聚合类读取常量；其二，这些家族彼此之间还交叉引用对方服务上的端点常量。这意味着，若要整体迁出其中一个家族，必须连带把跨家族、跨包引用到的端点常量逐一公开并补充导入，牵涉面很广。因此在啃下那块硬骨头之前，先把可以零风险搬动的路由常量叶子收拢进新子包，是一条稳妥且有意义的过渡路径。

## 入口路由

被整合的三个路由常量类分别承载一组以“操作员证据取值供给签名审批”为前缀的路由后缀常量：草稿就绪一组、捕获工件预检一组、捕获预检一组。每个后缀都是形如“以斜杠开头的相对路径片段”的字符串，最终由对应注册表的服务拼接上共享的基础路径，构成对外的只读端点。

这些路由后缀此前由根部的全局路由聚合类逐一转发：聚合类里每个同名常量都直接委派到叶子类里的对应常量取值。本次迁移把三个叶子类搬入新子包，并将类与其全部后缀常量改为公开，于是聚合类只需新增三行子包导入，便能继续以原先的委派写法转发同样的取值。路由字符串没有任何变化，变的只是这些常量声明所在的物理包与可见性级别。

## 响应模型

这三组路由后缀所服务的注册表家族（操作员证据取值供给签名审批的草稿就绪、捕获工件预检、捕获预检三条注册表）本身并不在本次迁移范围内，它们的响应模型仍然留在根包。这些响应模型聚合了来源回执、目录条目、模板与审查摘要、操作员输入镜像、时序窗口、通道签名、声明理由、来源证据、脱敏溯源、失败即锁等只读字段，并附带渲染后的段落文本。

本版本不触碰任何响应记录的字段顺序、字段命名或不可变集合语义，因此也不涉及任何响应类的静态分析豁免迁移。换言之，响应层完全保持原样，只有这些响应所对应路由的常量持有类换了包。这样做的好处是，把“路由常量归位”与“实现层归位”拆成两步推进，每一步都更小、更可验证，避免一次性改动过大带来不可控的风险。

## 上游证据配置

这三个路由常量类是纯粹的常量持有类，没有构造依赖，也不注入任何上游证据服务。它们的“上游”关系体现在被谁引用上：直接引用方只有两类，一是根部的全局路由聚合类（做委派转发），二是每条注册表各自的一个路由常量守护测试（做等值校验）。注册表的服务与控制器并不直接引用这些叶子类，而是经由全局聚合类读取同名常量。

正因为直接引用方只有“聚合类加单个守护测试”这两处，本次迁移的影响面被收得很窄：把三个叶子类与其后缀常量公开后，聚合类补三行导入、三个守护测试各补一行导入即可。注册表家族里数十个服务、控制器与目录类全部从全局聚合类读取常量，处于同包，无需任何改动，端点取值因此逐字节延续。

这里需要特别强调一个判断依据：在动手之前，必须先把“谁直接引用了叶子类”和“谁只是间接读取了同名常量”这两件事分得清清楚楚。前者是迁移真正的影响面，后者并不受迁移影响。本项目通过对全部主代码与测试代码的双向检索确认，三个叶子类的直接引用方各自只有两处，而数十个注册表实现文件读取的是全局聚合类暴露的常量，并非叶子类本身。正是这一区分，才让我有把握断定本刀的影响面仅限于聚合类与三个守护测试，而不会波及庞大的注册表家族。把这种“先厘清引用形态、再决定迁移边界”的纪律固定下来，对后续更复杂的跨家族迁移同样适用：越是体量大的家族，越要先回答清楚每一个被迁出符号的直接引用方究竟有哪些，绝不能凭命名前缀想当然地估算影响面，否则极易在完整验证阶段才暴露遗漏，白白浪费十余分钟的构建时间。

## 服务层核心流程

被服务的注册表家族的服务层流程保持不变：每个注册表服务在初始化时，把全局聚合类暴露的某个签名审批后缀常量拼接到共享基础路径上，得到自己的只读端点；随后服务在处理请求时，依据上游发布审批预演证据组装目录、摘要、镜像、锁等只读结果，最后交由渲染器与支撑类拼成响应。

本次迁移没有改动任何服务层代码，也没有改动服务读取常量的来源（依旧是全局聚合类）。服务层之所以不受影响，关键在于这一刀只动了“聚合类委派指向的叶子类”，而没有动“服务读取的聚合类常量”本身。聚合类常量的取值在迁移前后完全一致，服务拼出的端点字符串也因此完全一致，这正是契约保持的核心保证。

## Java 证据检查

Java 侧的证据检查分三步推进。第一步做仅编译，确认三个叶子类迁包并公开后、聚合类补齐三行导入后，主代码引用关系全部闭合；由于叶子类是纯常量持有类、不引用任何其他类型，主编译一次通过。第二步做仅测试编译，确认三个留在根包的路由常量守护测试在各自补齐一行叶子类导入后，能够继续访问公开后的叶子常量，测试编译一次通过。

第三步将通过完整验证流水线统一校验：单元测试全绿、各包覆盖率地板满足、静态分析零新增、代码风格零违规。由于本版本不迁移任何带受控暴露的响应类，静态分析豁免清单无需任何改动。治理阈值方面，根包直接文件数从一千二百四十三降到一千二百四十，相应把治理护栏阈值同步下调到一千二百四十。

## mini-kv 证据检查

本次迁移与 mini-kv 没有任何关系。被整合的是路由常量持有类，不发起任何连接，也不读写任何键值。被这些路由所服务的签名审批注册表家族本身是只读证据接口，它们对 mini-kv 的态度也仅停留在“以只读方式陈述证据边界”的层面，并不会触发 mini-kv 的真实连接或自动启动。

因此可以明确：本版本对 mini-kv 的运行时行为零影响，既不改变连接语义，也不改变任何存储读写语义。所有与 mini-kv 有关的陈述都留在原注册表的只读响应里，迁移只改变了路由常量类所在的包，不触及任何网络或存储动作。

## 阻断与安全边界

本版本严格守住既有安全边界。它不打开任何写路由、不路由活跃分片、不读取凭据值、不解析原始端点地址、不建立受管审计的网络连接、不部署、不回滚、不触发 Java 或 mini-kv 的自动启动。它所做的全部，就是把三个路由常量类换一个包并公开常量，再让原有的两类引用方补齐导入。

归档边界同样不可触碰：本次迁移不重命名也不移动任何归档根目录，从 `a/` 到 `f/`、形如 `e/<version>/` 的目录、各类证据 JSON、截图归档以及历史代码讲解目录都原地不动，Node 侧对 Java 证据归档的引用因此不会失效。这一刀的安全性几乎是所有版本里最高的，因为它根本不涉及任何运行期逻辑。

## 测试覆盖

测试侧保持最小改动。三个路由常量守护测试继续留在根包，因为它们要断言“迁出的后缀常量与根部全局聚合类里同名的包级常量逐字符相等”，这条断言依赖根包内对聚合类包级常量的可见性；每个守护测试只新增一行对迁出叶子类的导入。除此之外没有任何测试搬家。

为防止回退，本版本新增一个专门的守护测试，逐一断言三个路由常量类确实位于新子包、且不再出现在根包，并断言根部全局聚合类仍留在根包；同时把根包直接文件数的治理阈值从一千二百四十三下调到一千二百四十。配合既有的三个等值守护测试，路由取值与归位结构都得到双重保护。

## 实际工作量说明

本节据实说明工作量，绝不夸大，也禁止硬凑字数。本次真实改动包括：用版本控制移动三个路由常量类并改写包声明；把三个类与其全部后缀常量改为公开；为根部全局聚合类补三行子包导入；为三个留在根包的路由常量守护测试各补一行叶子类导入；下调治理阈值；新增守护测试、整合说明文档、变更日志、进度行、子目录索引与本讲解。

这一刀的难点不在改动量，而在前期判断：必须先确认这三个叶子类的直接引用方确实只有聚合类与单个守护测试，且注册表家族是经由聚合类间接读取常量，才能断定迁移影响面足够窄。为此本版本先用并行普查与逐项核对厘清了剩余家族的耦合形态，确认体量较大的家族都存在“聚合类供常量、家族间互引端点常量”的双重纠缠，从而把本刀稳妥地落在零风险的路由常量叶子上，而把跨家族端点常量公开这件更大的事留给后续版本。

## 一句话总结

本项目在 v1804 把三个签名审批路由常量类迁入新建的 `ops.maintenance.signedapproval` 子包，根包直接文件数从一千二百四十三降到一千二百四十，所有路由取值与只读语义逐字节不变，并为后续注册表家族的整体迁入立起了落点。
