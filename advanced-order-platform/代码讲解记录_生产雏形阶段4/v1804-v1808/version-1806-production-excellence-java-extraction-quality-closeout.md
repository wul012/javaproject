# v1806 Java 抽离质量收口代码讲解

本版本是一次质量收口，而不是新的业务功能抽离。前面几版从 v1797 到 v1805 连续把多个成熟的 ops 实现簇迁入更窄的维护子包，根包直放文件数从一千三百三十降到一千一百八十三，整体方向是正确的；但快速复核时暴露出一个必须写进仓库的事实：v1798 的历史 tag 指向一次远端 CI 失败的提交，后续 v1799 已经修复并记录了那次讲解门禁问题。v1806 的价值，就是不靠口头记忆、不靠聊天上下文，而是把这个事实、当前绿色基线、禁止重写历史 tag 的处理原则，全部沉淀到本项目自己的文档、测试、变更日志和进度表里。

## 入口路由

本版本没有新增入口路由，也没有移动任何控制器。所有已有的 `/api/v1/ops/shard-readiness` 只读端点都保持原样，候选文档、签名审批、沙箱连接、凭据解析、截图说明归档、代码讲解四个子家族等已经抽离出去的端点也没有被重新映射。v1806 的入口不是 HTTP API，而是维护者阅读路径：`docs/ops/java-extraction-quality-closeout-v1806.md` 成为本次收口的主要入口，`docs/ops/README.md` 把它挂到 ops 可读性保养索引里，测试再确认这个索引不会悄悄丢失。

这种处理符合当前阶段的工程边界。若为了“收一版”而硬加一个运行时 endpoint，反而会扩大系统表面积，让一个质量事实变成生产路由契约。这个项目已经有大量只读注册表，新增 endpoint 必须服务于真实运行期查询；而 v1806 要解决的是版本证据归档问题，不是运行时业务问题。因此入口路由保持零变化，所有解释都落在文档和测试层。

同时，v1806 明确没有把 v1798 tag 移动到修复后的提交。历史 tag 一旦被远端用户、CI 日志、审计记录、文档引用过，就不应该轻易重写。正确做法是新增一个收口版本说明：v1798 是历史异常，v1799 是修复边界，v1805 是当前绿色基线，v1806 记录这条判断。这样入口更诚实，也更利于追责和复盘。

## 响应模型

本版本没有改变任何 Java 响应模型。所有已经抽离到子包中的 response record 仍然保持原字段、原顺序、原只读语义、原不可变集合处理和原序列化结构。候选文档家族中多个响应类、沙箱连接响应类、凭据解析证据归档响应类、代码讲解相关响应类，都不因为 v1806 有任何字节级契约变化。

真正新增的“模型”是文档中的质量事实模型。`java-extraction-quality-closeout-v1806.md` 里把事实拆成几组可检查的字段：当前精确 tag、当前根包直放文件数、当前 ratchet 数值、本地轻量收口套件结果、格式门禁、远端 CI run id、历史异常 tag、异常提交号、修复边界和禁止强推历史 tag 的策略。它不是 Java record，却承担着与只读响应类似的作用：把散落在命令输出和人工判断里的质量事实固定成结构化文本。

这种模型化很重要。质量收口最怕一句“现在没问题了”飘在聊天里，过几天没人知道“现在”指哪个提交、“没问题”指本地测试还是远端 CI、“v1798 的失败”是否已经被修复到同一个 tag。v1806 用文档字段把这些模糊词拆开，测试再逐项检查关键短语存在，未来维护者不需要重跑全部历史命令，也能知道该信任哪条版本线。

## 上游证据配置

v1806 的上游证据来自三类来源。第一类是本地仓库状态：当前 HEAD 精确位于 v1805 tag，根包直放 Java 文件数实测为一千一百八十三，治理测试里的 `MAX_ROOT_OPS_MAIN_JAVA_FILES` 也是一千一百八十三，工作区干净。第二类是远端 CI 状态：GitHub Actions 上 v1805 的 Java Maven CI run `27524935139` 通过，v1804、v1803、v1802、v1801、v1800、v1799 也都已有成功记录，而 v1798 有一次明确失败。第三类是项目内既有进度表和变更日志：v1799 已经写明它修复了 v1798 遗留的讲解门禁问题。

这三类证据结合起来，形成一个比较稳的判断：当前代码线可以继续推进，但历史 v1798 tag 不能被当成绿色交付点。v1806 没有试图掩盖这个瑕疵，也没有把问题扩大成业务风险。它把结论收束成一条维护政策：不重写历史 tag，不把 v1798 描述为推荐基线，把 v1799 及之后视作修复后的抽离线，在出现更新且通过 CI 的 Java tag 前，使用 v1805 作为当前绿色基线。

本项目后期已经形成“证据随版本走”的习惯。每个抽离版本不仅要有代码迁移，还要有文档说明、测试护栏和中文讲解。v1806 延续这个习惯，只是证据类型从“哪些类移到哪个子包”变成“哪个 tag 可以被信任、哪个 tag 只能作为历史异常存在”。这也是工程后期保养必须补上的一类证据。

## 服务层核心流程

v1806 没有触碰服务层核心流程。订单创建、库存占用、支付模拟、outbox、失败事件回放、ops readiness 注册表、候选文档注册表、签名审批路径、沙箱连接证明等服务类都没有变更。所有 Spring bean 装配关系、事务边界、只读标记、控制器构造方式、route path 聚合方式都保持 v1805 的状态。

这并不是工作量不足，而是刻意的风险控制。质量收口版本的职责是把“是否可信”说清楚，不应该顺手改运行代码。若在同一版里既记录 v1798 历史异常，又修改某个服务类，验证失败时就会混淆两个问题：是收口文档写错，还是运行逻辑变了。v1806 避免这种混杂，只把改动集中在文档、测试、变更日志、进度表和讲解文件。

服务层真正得到的收益是间接的：后续维护者看到当前基线是 v1805，就能继续在 v1805 之后做新的拆分，而不是误以为 v1798 也是可回滚基线。回滚或审计时，如果有人问“能否回到 v1798”，文档会明确回答：可以作为历史提交查看，但它不是推荐的绿色运行线；应优先选择 v1799 之后的 remediated line。

## Java 证据检查

Java 侧新增了 `ReadabilityUpkeepOpsConsolidationQualityCloseoutV1806Tests`。这个测试检查三件事。第一，v1806 收口文档存在，并包含当前 v1805 精确 tag、根包计数、ratchet 数值、四十一个本地轻量测试、Spotless 门禁、远端 CI run id、v1798 历史异常、异常提交号、禁止重写历史 tag 和 v1799 修复线。第二，进度表、变更日志和 ops README 都能发现 v1806 收口信息。第三，当前根包直放 Java 文件数仍然等于一千一百八十三，防止收口版悄悄引入根包膨胀。

此外，`ReadabilityUpkeepDocsTests` 被扩展到检查 v1806 文档在 docs ops 入口中存在，并包含停止线和历史异常说明。`ProductionReadinessDocumentationTests` 也补齐近期版本号，从 v1798 到 v1806 都进入 changelog 可发现性检查。这样做不是为了形式化地多写几个断言，而是为了让“当前版本政策”不再只靠人记忆。只要后续有人删除 v1806 文档、删掉 README 索引、改坏 changelog，轻量测试就会失败。

本地收口测试会重点跑文档护栏、抽离护栏、讲解合规和生产文档检查；格式门禁会跑 `spotless:check`；完整收版前还需要跑默认 `verify`。由于这版不动运行代码，最重要的风险不是业务行为，而是文档事实是否准确、测试是否能护住事实、版本号是否能被发现。

## mini-kv 证据检查

v1806 没有读取、启动、停止、修改 mini-kv，也没有触碰 Node 项目。四项目统筹里，mini-kv、Java、Node 可以在非契约内部工作上并行推进；这次 Java 收口就是纯 Java 仓库内部的质量证据整理，不需要让 C++ 或 Node 参与。文档里提到 mini-kv 的唯一地方，是停止线：本版本不会启动 mini-kv，不会打开外部连接，不会改变跨项目证据路径。

这条边界值得写清楚。历史上 Java、Node、mini-kv 之间存在大量归档和证据引用，如果一次 Java 质量收口为了“更完整”去扫描或移动别的仓库，就会制造新的耦合。v1806 的收口方式是把 Java 看到的事实写在 Java 仓库内，把需要跨项目注意的点限制在“不动历史 tag、不动归档、不启动外部系统”。这正好符合用户要求的“只做自己的项目”。

因此 mini-kv 证据检查的结论是零影响：没有进程，没有端口，没有文件，没有测试夹带启动，也没有把 mini-kv 当成运行依赖。Java 当前绿色基线的判断来自 Java 自己的 CI、测试、文档和 tag，不消耗 mini-kv。

## 阻断与安全边界

v1806 的安全边界非常明确：不改业务代码，不改路由，不改响应 schema，不改运行 profile，不改部署脚本，不改回滚策略，不改归档布局，不重写 tag，不强推 tag，不读取凭据，不解析 raw endpoint，不连接受管审计，不启动 Java、mini-kv、Node、Docker 或浏览器。它只是新增可读文档和守护测试，把已经观察到的版本质量事实固化。

尤其是“不重写历史 tag”这一点，比看起来更重要。修复历史 tag 失败有两种方式：一种是强行移动 tag，让 v1798 看起来像从来没有失败过；另一种是新增版本记录事实，让历史保持原样。前者表面干净，实则破坏审计；后者看起来多留一个瑕疵，实则诚实可靠。v1806 选择后者，因为本项目已经进入证据驱动阶段，历史真实比表面完美更重要。

同时，v1806 也不把 v1798 的问题夸大成运行时事故。快速复核显示 v1799 之后的远端 CI 连续恢复，当前 v1805 也成功通过远端 CI，本地轻量护栏和格式门禁也通过。问题被限定为历史 tag 质量标记，而不是当前主线不可用。这个边界能防止团队在后续沟通里过度修复或重复排查。

## 测试覆盖

本版测试覆盖分成三层。第一层是新增的 v1806 专项测试，专门检查收口文档、进度表、变更日志、README 和根包计数。第二层是既有的文档可发现性测试，扩展到 v1806 文档，确保 docs ops 索引不会漏掉收口说明。第三层是生产版本文档测试，补充近期版本号，让 changelog 的版本政策覆盖到当前 v1806。

此外，代码讲解归档测试会检查本文件是否满足中文长文、标准标题、实际工作量说明、禁止硬凑和本项目归属等规则。本版本的讲解没有用大量英文命令和类名堆砌，而是用中文把工程判断写清楚：为什么不移动 tag，为什么不加运行 endpoint，为什么 v1799 是修复边界，为什么 v1805 是当前绿色基线，为什么这版不触碰 mini-kv 和 Node。

收版前的验证目标是：专项 focused tests 通过、`OpsCodeWalkthroughArchiveComplianceTests` 通过、`ProductionReadinessDocumentationTests` 通过、`spotless:check` 通过、默认 `verify` 通过。由于版本本身不改运行代码，若这些门禁都通过，就可以把 v1806 作为质量证据收口 tag 推到远端。

## 实际工作量说明

本项目这一版的实际工作量不是“写几行说明”，而是把一次快速质量复核转成可执行的仓库证据。具体工作包括：确认当前分支干净、确认当前 tag 是 v1805、确认 Java remote 只剩 `javaproject`、确认远端 CI 上 v1805 到 v1799 的成功线和 v1798 的失败点、实测根包直放文件数、确认 ratchet 数值、运行本地四十一个轻量护栏测试、运行格式门禁，然后把这些事实写入 v1806 文档、变更日志、进度表、docs ops 索引和专项测试。

这不是硬凑版本。禁止硬凑的含义不是每版都必须改业务代码，而是每版必须解决一个真实维护问题。v1806 解决的是“历史 tag 质量事实没有被项目自身记录”的问题。这个问题如果不处理，未来有人做回滚、做审计、写发布说明或交给另一个模型继续工作时，很容易误把 v1798 当成合格基线。把事实写进仓库，比在聊天里说一句“注意 v1798”更可靠。

还有一个实际收益：v1806 给后续版本提供了收口范式。以后如果某次 CI 失败被后续版本修复，但历史 tag 已经存在，就不应强行改历史，而应新增一个明确的质量收口版本，记录失败点、修复点、当前推荐基线和禁止操作。这样项目历史既真实，又可维护。

## 一句话总结

v1806 不改 Java 运行行为，而是把 v1798 历史失败 tag、v1799 修复边界、v1805 当前绿色基线和“不重写历史 tag”的原则写进文档与测试，让本项目的 ops 抽离线在继续推进前先有一个清楚、可验证、可追溯的质量收口。
