# v1801 生产卓越代码讲解：截图解释归档注册表簇抽离

本版本是连续第五刀 ops 根包瘦身，也是**第一刀走出代码讲解家族**的抽离。前四刀（合规、质量门、质量审计、深度）把代码讲解家族的四个注册表簇悉数迁出根包；本刀把“截图解释归档注册表”这一同样成熟的只读证据簇，从拥挤的根包搬到更窄的子包 `ops.maintenance.screenshotexplanationarchive`。本刀一次移动十个文件（九个实现文件加本家族路由类），把根包直放文件从一千二百九十降到一千二百八十。它在结构上与前四刀完全同构，是同一套已验证范式在新家族上的稳态复用，目标依旧是降低根包压力、保持对外契约逐字节不变。

## 入口路由

入口路由保持完全不变，仍是 `/api/v1/ops/shard-readiness/screenshot-explanation-archive-registry`。截图解释归档注册表的控制器没有移出根包，它继续使用根包里的基路径常量与本簇路由后缀常量作为路由注解的取值来源；Spring 组件扫描覆盖整个根包及其子包，控制器留在根包、实现类进入子包，不会影响 bean 装配或路由注册。外部调用方看到的地址、方法与响应结构没有任何漂移。控制器与根路由聚合表都留在根包，继续承担“对外入口”的角色，实现细节则整体下沉到语义更窄的子包，延续“根包管契约、子包管实现”的分层。值得强调的是，本刀虽然是第一次走出代码讲解家族，但选择截图解释归档作为对象的判断，恰恰是因为它和前四刀一样：自带本家族路由类、服务只引用自己家族的路由后缀、没有跨家族牵连，因此能直接复用范式而不必先解决根路由表的可见性问题。

## 响应模型

截图解释归档注册表的响应记录被移动到新子包，字段语义一字未改：它仍然记录项目、版本、各类只读边界布尔位（包括“是否捕获截图”这一关键布尔位，恒为否）、端点、profile、各类计数，以及当前归档目录、命名规则、分段目录、边界审计、验证步骤、markdown 小节、检查项等列表。响应继续保持公开类型，因为它是控制器的返回类型，序列化也需要稳定的公开类型；而目录、渲染器、支持类多数保持包内私有，只在子包内部协作。可见性分层与前四刀一致：只公开路由类、服务、响应这三种跨包确实需要的类型，不把整组实现一次性提升为全局可见。本版本同样没有顺手对响应记录做字段重排或命名缩短，因为本刀的唯一目标是证明搬包安全，而不是混入模型语义变更。

## 上游证据配置

截图解释归档注册表是对“截图解释归档治理规则”的只读再表达，读取的是本项目已经固化的当前归档目录、命名规则、分段目录、边界审计与验证步骤，而不是数据库或远端服务。本版本移动了这些目录类，迁移之后它们同处截图解释归档子包，主题内聚度更高，不再是散落在上千个根包文件中的普通只读证据类。目录数据本身没有任何改动：当前归档目录的条目、命名规则、分段划分、各类禁止边界（禁止捕获真实截图、禁止写路由、禁止读取凭据实值、禁止解析裸端点地址、禁止连接管理审计、禁止自动启动相邻服务）、验证步骤的内容，全部保持旧值。新文档承担变更账本职责，列出十份被移动文件、声明控制器与路由聚合表留在根包、记录根包计数从一千二百九十到一千二百八十的变化，并再次写明历史归档目录一律不移动；尤其是这份注册表所描述的截图解释归档分段本身原地不动，移动的只是 Java 实现类的包归属。

## 服务层核心流程

服务层核心流程仍由截图解释归档注册表服务的查询方法完成：依次读取当前归档目录、命名规则、分段目录、边界审计、验证步骤等目录，经支持类组装响应、经渲染器输出 markdown。流程没有重排、没有新增副作用、没有把静态目录改成注入式 bean。唯一的变化在端点字符串的生成方式：原来服务在根包内直接读取根路由表的基路径与本簇后缀常量，移动到子包后若继续访问根包包内私有常量就必须扩大根表可见性，因此本版本把本家族路由类改为公开并新增包内基路径常量，服务的端点常量改由本家族常量拼接，拼出的字符串与迁移前逐字节相同。根路由聚合表仍通过一个 import 继续委托本家族公开的后缀常量。这样依赖方向从“子包回流根包”被切断为“根包代理子包”，与前四刀完全一致；对一个已经积累上千个只读证据类的后期工程而言，守住依赖方向比移动几个文件更重要。

## Java 证据检查

第一层证据是文件计数：ops 主源码总数仍是一千三百五十二、Readiness 命名文件仍是一千二百一十，根包直放文件从一千二百九十降到一千二百八十，正好是移动十份主文件的结果。治理增长棘轮常量同步从一千二百九十收紧到一千二百八十，后续若有人把文件放回根包，测试立即失败。第二层证据是新增的第五个抽离守护测试，它逐个检查十份实现文件在截图解释归档子包目录存在、在根包目录不存在，确认控制器与路由聚合表仍在根包，并读取本版本文档校验若干关键短语，同时校验入口索引文档已包含新文档名、子包名与“一千二百九十到一千二百八十”的计数描述。第三层证据来自原有截图解释归档簇测试：移动后的服务、渲染器、边界、不可变、收尾、F 根目录策略、支持类测试进入新包；分段文档测试、根路由路径测试、控制器测试留在根包，其中控制器与路由路径测试改为直接构造服务、并导入公开的路由类。

## mini-kv 证据检查

本版本没有读取、启动、修改或整理 mini-kv。mini-kv 仍只是边界对象：文档声明不自动启动，测试断言不启动相邻服务，边界目录保留对应的禁止规则，Java 侧不借这次搬包去触碰 C++ 仓库，也不新增任何跨仓耦合。结论明确：没有进程启动、没有文件移动、没有归档迁移、没有新增依赖、没有把 Java 服务与 mini-kv 运行时绑定。截图解释归档注册表关心的是 Java 侧截图与解释文档的归档布局规则，与底层键值存储无关。

## 阻断与安全边界

安全边界没有放松。截图解释归档注册表仍是只读注册表：不捕获真实截图、不接受请求体、不写库、不发消息、不连管理审计、不解析裸端点地址、不读取凭据实值、不触发部署或回滚、不启动相邻进程。移动包名不改变运行态行为，测试继续断言只读、不捕获截图、不允许执行等边界。历史归档不可移动这一条由文档与抽离守护测试的关键短语检查共同固定；本簇尤其敏感，因为它描述的正是截图与解释归档的目录布局，因此特别强调“描述归档布局的注册表实现可以换包，但被描述的归档目录本身绝不移动”。可见性边界也被克制处理：只把路由类、服务、响应暴露到跨包可用，其余目录、渲染器、支持类仍保持包内私有。

## 测试覆盖

本版本继续把中文讲解放在全量门禁之前写好。闭环以格式化规整开始，随后跑全量构建验证，覆盖编译、包边界、覆盖率逐包下限、静态分析棘轮、格式棘轮，以及要求较新版本中文讲解达到三千汉字、以中文为主体、并包含标准章节与工作量说明的护栏。预先把响应记录及其嵌套类的内部表示暴露豁免随类改名平移到新子包，因此静态分析阶段没有冒出告警。需要特别说明本簇测试的两处处理：其一，F 根目录策略测试调用包内私有的测试支持来取得响应，因此它必须跟随测试支持一起搬进子包，否则跨包访问包内私有会失败；其二，分段文档测试不引用任何被移动的类，因此原样留在根包不动。最终全量构建验证通过，所有测试零失败，覆盖率逐包下限满足，静态分析零新增告警，格式干净。

## 实际工作量说明

本项目这一版的实际工作量集中在“把已验证范式第一次推广到代码讲解家族之外，并正确处理新家族里多出来的测试形态”，而不是制造新功能。具体步骤：先做形态普查，确认代码讲解家族的注册表簇已抽完，再在仍带本家族路由类的候选里挑出截图解释归档注册表——它服务只引用自己家族的路由后缀、无跨家族牵连，是走出代码讲解家族后最干净的下一刀；用版本控制的移动命令搬迁十份主文件与七份包内测试（比前几刀多了 F 根目录策略测试），改写包声明；把本家族路由类改公开并新增基路径常量；把服务的端点常量改为引用本家族常量并提升为公开；为根控制器、根路由聚合表、根控制器测试、根路由路径测试补齐对子包公开类型的导入，并把根控制器测试里对包内测试支持的调用改为直接构造服务；判断分段文档测试无需移动、F 根目录策略测试必须移动；预先把响应记录的内部表示暴露豁免平移到新全限定名；收紧棘轮到一千二百八十；新增本版本的抽离守护测试与文档；并在全量验证之前先写好这份达到字数与中文主体要求的讲解。

这段说明也回应“禁止硬凑”的要求：真正需要被记录的，不是“移动了文件、测试通过”这种空话，而是为什么第一次走出代码讲解家族却仍能复用同一范式、为什么挑截图解释归档而不是耦合更深的家族、为什么控制器与路由聚合表不动、为什么服务改用本家族常量而不把根表公开、为什么目录数据一个字都不改、为什么 F 根目录策略测试要移而分段文档测试不移、为什么静态分析豁免是平移而非新增。把这些工程判断写清，后续如果还要从其它带本家族路由类的家族继续抽离，就能直接照搬这套稳态做法，而不必重新推导边界。

## 五刀阶段性小结与后续方向

到本版本为止，根包直放文件从盘点时的一千三百三十,经五刀降到一千二百八十，累计减少五十个，而 ops 主源码总数始终保持不变。前四刀清空了代码讲解家族的注册表簇，本刀证明了同一范式可以平滑地推广到代码讲解家族之外的任何“自带本家族路由、无跨家族牵连”的注册表簇。这条经验非常关键：它意味着接下来的瘦身不必局限于某一个家族，而是可以按“是否自带本家族路由类、服务是否只引用自己家族的后缀、是否没有跨家族常量引用”这三条标准，在整个根包里筛选下一批干净的注册表簇，逐个稳步抽离。

后续方向仍需一次新的形态普查再定。带本家族路由类的家族还有若干（例如凭据解析、沙箱连接、发布验收、签名审批相关的若干路由类），需要逐一核对它们的服务是否只引用自己家族的后缀、是否存在跨家族常量引用，优先选最干净的继续复用本范式；而像最小只读门家族那种没有本家族路由类、非控制器文件直接引用根私有路由表的簇，则需要先决定是否给根路由聚合表一个受控的公开策略之后再处理，不宜贸然作为下一刀。把“先易后难、先无耦合后有耦合”的次序继续固定下来，是这一阶段除文件移动之外最值得传承的判断。

## 一句话总结

v1801 把截图解释归档注册表的实现层从拥挤的 Java ops 根包抽到 `ops.maintenance.screenshotexplanationarchive`，在不改路由、不改响应、不动归档、不启动外部系统的前提下把根包直放文件从一千二百九十降到一千二百八十，成为第一刀走出代码讲解家族的同构抽离；讲解先行、静态分析豁免预置平移，最终全量构建验证通过，用文档与测试把这条拆分范式继续固定。
