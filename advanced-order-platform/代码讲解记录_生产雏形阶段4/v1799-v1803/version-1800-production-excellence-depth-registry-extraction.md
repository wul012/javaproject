# v1800 生产卓越代码讲解：代码讲解深度注册表簇抽离

本版本是连续第四刀 ops 根包瘦身，把代码讲解深度注册表（code walkthrough depth registry）从拥挤的根包搬到更窄的子包 `ops.maintenance.walkthrough.depth`。至此，代码讲解家族的四个成熟注册表簇——合规、质量门、质量审计、深度——已经全部从根包抽离完毕。本刀一次移动八个文件（七个实现文件加本家族路由类），把根包直放文件从一千二百九十八降到一千二百九十。它在结构上与前三刀完全同构，是同一套已验证范式的第四次稳态复用，目标依旧是降低根包压力、保持对外契约逐字节不变。

## 入口路由

入口路由保持完全不变，仍是 `/api/v1/ops/shard-readiness/code-walkthrough-depth-registry`。和前三刀一样，深度注册表的控制器没有移出根包，它继续使用根包里的基路径常量与本簇路由后缀常量作为路由注解的取值来源；Spring 的组件扫描覆盖整个根包及其子包，控制器留在根包、实现类进入子包，不会影响 bean 装配或路由注册。外部调用方看到的地址、方法与响应结构没有任何漂移。控制器与根路由聚合表都留在根包，继续承担“对外入口”的角色，而实现细节则整体搬进语义更窄的子包，形成清晰的内外分层。这种安排是前三刀反复验证过的：把契约面固定在根包、把实现面下沉到子包，既降低了根包的认知负担，又不触动任何被下游依赖的稳定点。

## 响应模型

深度注册表的响应记录被移动到新子包，字段语义一字未改：它仍然记录项目、版本、各类只读边界布尔位、端点、各类计数，以及深度规则、边界审计、验证步骤、markdown 小节、检查项等列表，还有那个表示“讲解最少汉字数”的阈值字段。响应继续保持公开类型，因为它是控制器的返回类型，序列化也需要稳定的公开类型；而目录、渲染器、支持类多数保持包内私有，只在子包内部协作。可见性分层与前三刀一致：只公开路由类、服务、响应这三种跨包确实需要的类型，不把整组实现一次性提升为全局可见。本版本同样没有顺手对响应记录做字段重排或命名缩短，因为本刀的唯一目标是证明搬包安全，而不是混入模型语义变更；把结构整理与事实变更分开，是这套保养流程一以贯之的纪律。

## 上游证据配置

深度注册表是对“代码讲解深度治理规则”的只读再表达，读取的是本项目已经固化的深度规则、边界审计与验证步骤，而不是数据库或远端服务。本版本移动了这些目录类，迁移之后它们同处深度子包，主题内聚度更高，不再是散落在上千个根包文件中的普通只读证据类。目录数据本身没有任何改动：深度规则的条目、各类禁止边界（禁止写路由、禁止读取凭据实值、禁止解析裸端点地址、禁止连接管理审计、禁止自动启动相邻服务）、验证步骤的内容，全部保持旧值。新文档 `docs/ops/depth-registry-extraction-v1800.md` 承担变更账本职责，列出八份被移动文件、声明控制器与路由聚合表留在根包、记录根包计数从一千二百九十八到一千二百九十的变化，并再次写明历史归档目录一律不移动。

## 服务层核心流程

服务层核心流程仍由深度注册表服务的查询方法完成：依次读取深度规则、边界审计、验证步骤等目录，经支持类组装响应、经渲染器输出 markdown。流程没有重排、没有新增副作用、没有把静态目录改成注入式 bean。唯一的变化在端点字符串的生成方式：原来服务在根包内直接读取根路由表的基路径与本簇后缀常量，移动到子包后若继续访问根包包内私有常量就必须扩大根表可见性，因此本版本把本家族路由类改为公开并新增包内基路径常量，服务的端点常量改由本家族常量拼接，拼出的字符串与迁移前逐字节相同。根路由聚合表仍通过一个 import 继续委托本家族公开的后缀常量。这样依赖方向从“子包回流根包”被切断为“根包代理子包”，对一个已经积累上千个只读证据类的后期工程而言，守住依赖方向比移动几个文件更重要。

## Java 证据检查

第一层证据是文件计数：ops 主源码总数仍是一千三百五十二、Readiness 命名文件仍是一千二百一十，根包直放文件从一千二百九十八降到一千二百九十，正好是移动八份主文件的结果。治理增长棘轮常量同步从一千二百九十八收紧到一千二百九十，后续若有人把文件放回根包，测试立即失败。第二层证据是新增的第四个抽离守护测试，它逐个检查八份实现文件在深度子包目录存在、在根包目录不存在，确认控制器与路由聚合表仍在根包，并读取本版本文档校验若干关键短语，同时校验入口索引文档已包含新文档名、子包名与“一千二百九十八到一千二百九十”的计数描述。第三层证据来自原有深度簇测试：移动后的服务、渲染器、边界、支持类测试进入新包，根包的路由路径测试与控制器测试留在原处，继续证明根聚合表与控制器对外不漂移。

## mini-kv 证据检查

本版本没有读取、启动、修改或整理 mini-kv。mini-kv 仍只是边界对象：文档声明不自动启动，测试断言不启动相邻服务，边界目录保留对应的禁止规则，Java 侧不借这次搬包去触碰 C++ 仓库，也不新增任何跨仓耦合。结论明确：没有进程启动、没有文件移动、没有归档迁移、没有新增依赖、没有把 Java 服务与 mini-kv 运行时绑定。若 mini-kv 自身需要做归档清理或大文件拆分，应在它自己的仓库里按它自己的计划进行，不应通过 Java 的深度注册表间接完成。

## 阻断与安全边界

安全边界没有放松。深度注册表仍是只读注册表：不接受请求体、不写库、不发消息、不连管理审计、不解析裸端点地址、不读取凭据实值、不触发部署或回滚、不启动相邻进程。移动包名不改变运行态行为，测试继续断言只读、不允许执行等边界。历史归档不可移动这一条由文档与抽离守护测试的关键短语检查共同固定。可见性边界也被克制处理：只把路由类、服务、响应暴露到跨包可用，其余目录、渲染器、支持类仍保持包内私有，避免新子包被当成一个随意访问的全局工具箱。

## 测试覆盖

本版本吸取上一刀的教训，把中文讲解放在全量门禁之前写好，而不是等绿灯之后再补。闭环以格式化规整开始，随后跑全量构建验证。验证覆盖编译、包边界、覆盖率逐包下限、静态分析棘轮、格式棘轮，以及那条要求所有较新版本中文讲解必须达到三千汉字且以中文为主体、并包含标准章节与工作量说明的护栏。预先把响应记录及其嵌套类的内部表示暴露豁免随类改名平移到新子包，因此静态分析阶段没有重演此前因全限定名失配而冒出的告警。最终全量构建验证通过，所有测试零失败，覆盖率逐包下限满足，静态分析零新增告警，格式干净。

## 实际工作量说明

本项目这一版的实际工作量集中在“第四次稳态复用已验证范式，并把上一刀总结出的流程纪律真正落实”，而不是制造新功能。具体步骤：确认深度注册表自带本家族路由类、服务只引用本家族路由后缀、没有跨家族牵连，是干净的同构下一刀；用版本控制的移动命令搬迁八份主文件与四份包内测试，改写包声明；把本家族路由类改公开并新增基路径常量；把服务的端点常量改为引用本家族常量并提升为公开；为根控制器、根路由聚合表、根控制器测试、根路由路径测试补齐对子包公开类型的导入，并把根控制器测试里对包内测试支持的调用改为直接构造服务；预先把响应记录的内部表示暴露豁免平移到新全限定名；收紧棘轮到一千二百九十；新增本版本的抽离守护测试与文档；并在全量验证之前先写好这份达到字数与中文主体要求的讲解。

这段说明也回应“禁止硬凑”的要求：真正需要被记录的，不是“移动了文件、测试通过”这种空话，而是为什么继续选同构的注册表簇、为什么控制器与路由聚合表不动、为什么服务改用本家族常量而不把根表整体公开、为什么目录数据一个字都不改、为什么静态分析豁免是平移而非新增、以及这一刀如何把上一刀“讲解写在验证之后导致隐患”的教训落实为“讲解先行、验证兜底”的固定动作。把这些工程判断与流程纪律写清，后续如果还要继续从根包抽离别的家族，就能直接照搬这套稳态做法，而不必重新推导边界，也不会再因为收尾顺序不当而留下会被持续集成复现的隐患。

## 四刀阶段性小结与后续方向

到本版本为止，代码讲解家族的四个注册表簇已悉数迁出根包，根包直放文件从盘点时的一千三百三十,经四刀降到一千二百九十，累计减少四十个，而 ops 主源码总数始终保持不变。这组数字说明四刀都不是删功能、不是改名逃避统计，而是把同主题的实现持续内聚到更窄的包里，并让每一刀都给棘轮留下一个更低、不可回退的上限。更重要的沉淀是这套范式本身已经被验证了四次：先确认目标簇自带本家族路由类且无跨家族牵连，再整体搬迁实现、保留入口与归档，再平移静态分析豁免、收紧棘轮、补齐文档与守护测试，最后先写讲解再跑全量验证。任何接手者都可以照着这条次序继续推进。

后续方向需要一次新的形态普查再定。代码讲解家族的注册表簇已经抽完，接下来可以评估其它命名家族里是否还存在同样“自带本家族路由、无跨家族牵连”的成熟簇，优先复用本范式；而像候选文档家族那种非控制器文件直接引用根私有路由、甚至跨家族引用的簇，则需要先决定是否给根路由聚合表一个受控的公开策略、或为其设计本家族路由类之后再处理，不宜贸然作为下一刀。把“先易后难、先无耦合后有耦合”的次序固定下来，是这一阶段除文件移动之外最值得传承的判断。

## 一句话总结

v1800 把代码讲解深度注册表的实现层从拥挤的 Java ops 根包抽到 `ops.maintenance.walkthrough.depth`，在不改路由、不改响应、不动归档、不启动外部系统的前提下把根包直放文件从一千二百九十八降到一千二百九十，完成了代码讲解四个注册表家族的全部迁出；讲解先行、静态分析豁免预置平移，最终全量构建验证通过，用文档与测试把这条拆分范式继续固定。
