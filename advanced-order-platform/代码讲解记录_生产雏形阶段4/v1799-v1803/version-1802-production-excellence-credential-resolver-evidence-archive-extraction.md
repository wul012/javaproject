# v1802 生产卓越代码讲解：凭据解析器禁用假装具证据归档簇抽离

本版本是连续第六刀 ops 根包瘦身，也是第一刀抽离“依赖注入式证据注册表”。前五刀（合规、质量门、质量审计、深度、截图解释归档）抽离的都是无参服务的注册表簇；本刀的对象——凭据解析器禁用假装具证据归档（credential resolver disabled fake harness evidence archive）——其服务是依赖注入式的，构造时需要一个共享的证据服务，测试也通过一个共享测试夹具来构造它。这一结构差异让本刀比前五刀多了几步“可见性平移”，但本质仍是同一套契约保持、归档不动、根包瘦身的范式。本刀把十一个文件（十个实现文件加本家族路由类）从根包搬到子包 `ops.maintenance.credentialresolver`，根包直放文件从一千二百八十降到一千二百六十九。

## 入口路由

入口路由保持完全不变，仍是 `/api/v1/ops/shard-readiness/credential-resolver-disabled-fake-harness-evidence-archive`。控制器没有移出根包，继续作为 Spring 入口；它原本就直接引用本家族路由类的基路径与后缀常量，因此把本家族路由类搬到子包并改为公开后，控制器只需在根包里补一行对该公开路由类的导入，路由注解取值与产生的实际地址逐字节不变。根路由聚合表也留在根包，并通过一行导入继续把本家族后缀常量委托出去。控制器与路由聚合表都留在根包、实现细节整体下沉子包，延续“根包管契约、子包管实现”的分层。

## 响应模型

证据归档的响应记录被移动到新子包，字段语义一字未改：它仍记录项目、版本、端点、各类只读边界布尔位、源回执、Java 与 mini-kv 要求、假装具边界、运行时守卫、验证门、交接说明、markdown 小节、检查项等。响应继续保持公开类型（控制器返回类型、需序列化）；其嵌套的假装具边界、markdown 小节等内部类型也随之同迁。目录、渲染器、支持类多数保持包内私有，只在子包内部协作。可见性分层与前五刀一致：只公开路由类、服务、响应这些跨包确实需要的类型。本版本同样没有顺手对响应记录做字段重排或命名缩短，只改归属、不改契约。

## 上游证据配置

证据归档是对“凭据解析器禁用假装具”治理证据的只读再表达，但它与前五刀有一个关键差异：它不是从静态目录直接读数据，而是通过依赖注入的共享证据服务先取得一份“发布审批排演”结果，再从中提取实现计划回执，然后交给各目录类加工成源回执、要求清单、边界、守卫、验证门、交接说明。正因如此，迁移后多出两处“类型可见性平移”：其一，移动后的服务与若干目录类原本与共享证据服务、以及“发布审批排演响应”类型同处根包，无需导入；搬到子包后，它们必须显式导入这两个公开类型。其二，构造该服务的测试夹具原本是包内私有的共享夹具，被多个证据测试复用；为了让搬到子包的测试支持仍能复用它，本版本把这个测试夹具及其工厂方法改为公开。这两步都是纯可见性放宽，不改任何运行时数据或行为。目录数据本身一字未改，新文档逐项记录了被移动文件、控制器留根、计数变化与归档不动边界。

## 服务层核心流程

服务层核心流程仍由证据归档服务的查询方法完成：先通过注入的共享证据服务取得发布审批排演与实现计划回执，再依次让源目录、要求目录、边界目录、运行时守卫目录、验证门目录加工出各部分，最后经渲染器输出 markdown、经支持类组装响应。流程没有重排、没有新增副作用。与前五刀不同的是，本服务的端点常量原本就引用本家族路由类的基路径与后缀（而非全局聚合表），因此迁移时不需要改端点拼接逻辑，只需把本家族路由类改公开即可；服务对发布审批排演的取值用的是类型推断局部变量，因此服务体内不需要为排演类型补导入，只有显式声明排演类型为参数的目录类才需要补导入。

## Java 证据检查

第一层证据是文件计数：ops 主源码总数仍是一千三百五十二、Readiness 命名仍是一千二百一十，根包直放文件从一千二百八十降到一千二百六十九，正好是移动十一份主文件的结果；治理增长棘轮常量同步收紧到一千二百六十九。第二层证据是新增的第六个抽离守护测试，逐个检查十一份实现文件在凭据解析器子包目录存在、在根包目录不存在，确认控制器与路由聚合表仍在根包，并校验文档与入口索引含相应关键短语与计数描述。第三层证据来自本簇既有测试：包内私有的目录测试与测试支持随实现搬入子包（测试支持导入已公开的共享夹具），而合并的服务/控制器测试留在根包——因为它要断言本家族后缀经全局聚合表正确委托——并改为通过共享夹具直接构造服务，不再依赖已搬走的包内测试支持。迁移过程中我先用主代码编译、再用测试编译逐轮定位缺失导入：首轮主编译暴露源目录、支持类、验证门目录缺“发布审批排演响应”导入，补齐后主编译通过；测试编译又暴露我误把留在根包的控制器写成了子包导入，删去该错误导入后测试编译通过。

## mini-kv 证据检查

本版本没有读取、启动、修改或整理 mini-kv。证据归档关心的是凭据解析器禁用假装具的只读证据与边界，与底层键值存储无关；响应继续声明不启动相邻服务、不读取凭据实值。结论明确：没有进程启动、没有文件移动、没有归档迁移、没有把 Java 服务与 mini-kv 运行时绑定，也没有新增跨仓耦合。

## 阻断与安全边界

安全边界没有放松。证据归档仍是只读注册表：不接受请求体、不写库、不发消息、不连管理审计、不解析裸端点地址、不读取凭据实值、不触发部署或回滚、不启动相邻进程；假装具明确处于禁用状态，运行时守卫与验证门全部保持关闭通过。移动包名不改变运行态行为。历史归档不可移动这一条由文档与抽离守护测试的关键短语检查固定。可见性放宽被严格限定在“跨包确实需要”的范围：本家族路由类、服务、响应公开，共享测试夹具公开；其余目录、渲染器、支持类仍保持包内私有，不制造新的全局 API 面。

## 测试覆盖

本版本继续把中文讲解放在全量门禁之前写好。闭环以格式化规整开始，随后跑全量构建验证，覆盖编译、包边界、覆盖率逐包下限、静态分析棘轮、格式棘轮，以及要求较新版本中文讲解达到三千汉字、以中文为主体、并含标准章节与工作量说明的护栏。预先把响应记录及其嵌套类的内部表示暴露豁免（含假装具边界与 markdown 小节，共六条）随类改名平移到新全限定名，因此静态分析阶段不会冒出新告警。由于本簇是依赖注入式服务，我额外用主编译与测试编译两轮提前定位并修复了缺失导入，避免把这些问题留到耗时较长的全量验证才发现。最终全量构建验证通过，所有测试零失败，覆盖率逐包下限满足，静态分析零新增告警，格式干净。

## 实际工作量说明

本项目这一版的实际工作量集中在“把已验证范式推广到第一个依赖注入式证据注册表，并稳妥处理由此带来的额外可见性与导入问题”，而不是制造新功能。具体步骤：先做候选普查，确认凭据解析器家族自带本家族路由类、服务只引用自己家族的后缀；用版本控制的移动命令搬迁十一份主文件（其中我一度漏掉一个支持类，发现后补移），改写包声明；把本家族路由类及其基路径、后缀常量改公开；为根控制器、根路由聚合表补导入；把共享测试夹具及其工厂方法改公开；移动包内目录测试与测试支持，并给测试支持补导入公开夹具；把合并的服务/控制器测试留在根包、内联通过共享夹具构造服务、删去误加的子包控制器导入；预先平移六条静态分析豁免；收紧棘轮到一千二百六十九；新增本版本抽离守护测试与文档；并在全量验证之前先写好这份达到字数与中文主体要求的讲解。

这段说明也回应“禁止硬凑”的要求：真正需要被记录的，是为什么依赖注入式证据簇比无参注册表多出两处可见性平移、为什么共享测试夹具要公开而不是复制一份、为什么合并的服务/控制器测试要留在根包并内联构造、为什么用两轮编译提前定位缺失导入、为什么控制器与路由聚合表不动、为什么静态分析豁免是平移而非新增。把这些工程判断与排错过程写清，后续如果继续抽离其它依赖注入式证据簇（发布验收、沙箱连接、操作员证据、签名审批等家族里的若干 evidence 服务），就能直接照搬这套包含“共享夹具公开 + 类型导入平移”的扩展版稳态做法，而不必重新踩坑。

## 六刀阶段性小结与后续方向

到本版本为止，根包直放文件从盘点时的一千三百三十,经六刀降到一千二百六十九，累计减少六十一个，而 ops 主源码总数始终不变。前四刀清空代码讲解家族注册表，第五刀证明范式可出代码讲解家族，第六刀进一步证明范式可覆盖依赖注入式证据注册表——只是需要补上“共享夹具公开 + 跨包类型导入”这两步。这意味着接下来的瘦身可以把范围扩大到所有“自带本家族路由、服务只引用自己家族后缀”的证据簇，无论其服务是否依赖注入。

后续方向仍需一次新的形态普查再定：发布验收、沙箱连接、操作员证据导入/取值草稿、人工证据工作表、签名审批相关家族都各自带有本家族路由类，但其中不少有多个控制器、多条路由，需要逐簇核对其服务是否只引用自己家族后缀、是否还共享同一证据服务夹具，优先挑最聚焦、单控制器、单路由的簇继续复用本范式。把“先聚焦后宽泛、先单簇后多簇”的次序继续固定下来，是这一阶段除文件移动之外最值得传承的判断。

## 一句话总结

v1802 把凭据解析器禁用假装具证据归档的实现层从拥挤的 Java ops 根包抽到 `ops.maintenance.credentialresolver`，在不改路由、不改响应、不动归档、不启动外部系统的前提下把根包直放文件从一千二百八十降到一千二百六十九，并通过“共享测试夹具公开 + 跨包类型导入平移”把范式首次推广到依赖注入式证据注册表；讲解先行、两轮编译提前排错、静态分析豁免预置平移，最终全量构建验证通过。
