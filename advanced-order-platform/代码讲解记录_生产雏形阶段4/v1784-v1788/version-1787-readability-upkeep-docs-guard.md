# 第一千七百八十七版代码讲解：可读性保养文档门禁与维护周期

v1787 的目标是把前面三版形成的文档、模型和接口纳入更严格的文档门禁。v1784 新增路线服务测试地图和根包压力地图，v1785 建立审计响应和资料地基，v1786 暴露只读审计入口。到这一版，如果不补文档测试，新增地图可能会慢慢漂移，README 可能丢链接，维护周期也可能只停留在口头经验里。所以 v1787 新增 `readability-upkeep-cycle.md`，更新 `docs/ops/README.md`，并扩展 `ReadabilityUpkeepDocsTests`，让文档入口、路线地图、根包压力地图和维护周期都进入测试。

这版仍然只做 Java 本项目，而且主要是文档和测试。它不是小粒度凑版本，因为文档门禁在后期工程里非常关键。一个项目走到大量版本之后，代码能跑只是底线，证据能不能被后来者读懂同样重要。v1787 把“怎么继续做可读性保养”写成周期，并用测试保证周期文件、地图文件和 README 导航不会掉线。

## 入口路由

本版没有新增新的运行时路由。当前运行时入口仍然是 `/api/v1/ops/readability/upkeep-registry` 和 `/api/v1/ops/readability/upkeep-audit`。v1787 的入口变化发生在文档层：`docs/ops/README.md` 新增 `readability-upkeep-cycle.md` 的导航，同时已有的 route-service-test map 和 root-package-pressure map 也被 docs test 检查。

保留运行时路由不变是有意的。v1786 已经把 audit route 暴露出来，本版要做的是让文档门禁追上接口，而不是继续新增接口。后期保养如果一直只加 endpoint，却不守住 docs 和测试，很快又会回到“有很多入口但没人知道怎么读”的状态。v1787 的文档入口就是为了防止这种退化。

`ReadabilityUpkeepDocsTests` 现在会检查 `docs/ops` 下存在 README、shard readiness map、walkthrough registry map、archive layout map、registry template、route-service-test map、root-package-pressure map 和 readability upkeep cycle。这样新地图不只是文件系统里的散装文件，而是被测试承认的项目文档入口。

## 响应模型

本版不改响应模型。`ReadabilityUpkeepRegistryResponse` 和 `ReadabilityUpkeepAuditResponse` 都保持 v1786 的结构。文档门禁版不应为了体现变化而强行增加字段，因为字段变化会影响运行时契约。当前真正需要加强的是文档可发现性和维护周期，而不是 JSON 形状。

这种克制很重要。后期保养不是每版都要改接口。接口一旦发布，字段就应当谨慎变化；文档和测试可以更频繁地加厚，帮助接口被正确理解。v1787 选择只改 docs 和 docs test，让响应契约保持稳定。这也能降低全量测试和 CI 的风险。

虽然模型不变，docs test 仍然间接保护模型。路线服务测试地图必须包含 audit route 和 audit service test，根包压力地图必须提到 readability 子包和不做默认批量重命名，维护周期必须包含 Map、Model、Expose、Guard、Close。只要这些文档信号存在，维护者就能把响应模型放回正确上下文里理解。

## 上游证据配置

本版新增的上游证据是 `docs/ops/readability-upkeep-cycle.md`。它把后期可读性保养拆成五个阶段：地图、模型、暴露、守护、收口。地图阶段要求先建立可读入口；模型阶段要求响应和资料拆分；暴露阶段要求只读服务和控制器；守护阶段要求 docs test、boundary test、renderer test 和讲解合规；收口阶段要求版本、目录、tag、push 和 CI 证据对齐。

这份周期文档不是部署流程。它明确说自己是本地 Java 项目维护规则，不是发布动作。文档边界继续排除写路由、主动分片路由、凭据值读取、原始端点解析、受管审计连接、部署、回滚、自动启动 Java、自动启动 mini-kv 和其他项目变更。这样维护周期不会被误解成执行流程。

上游证据还包括 v1784 的两张地图。Docs test 现在要求 route map 包含 registry route、audit route 和 audit service test，要求 pressure map 包含 readability 子包和“批量重命名不是默认维护动作”。这些断言把文档中的关键边界固化下来，避免后续编辑时删掉最重要的话。

## 服务层核心流程

服务层代码在 v1787 没有变化，原因是前一版的流程已经足够清楚：资料、渲染、支撑、服务、控制器分层。v1787 把这条流程写入文档周期，而不是再次改服务。维护周期中的 Model 和 Expose 两步，正好对应 v1785 和 v1786 的工作：先建模型和资料，再暴露只读接口。

从工程角度看，docs guard 也是服务层流程的一部分。服务层输出能否被维护，取决于文档是否说明它为什么存在、由哪些测试保护、后续怎么收口。没有这些，服务层虽然能通过单元测试，却很难长期维护。v1787 把文档门禁补上，等于是把服务流程外侧的解释层固定住。

`ReadabilityUpkeepDocsTests` 扩展后，会读取多个 Markdown 文件并检查关键字符串。它不解析表格，也不检查每一句文案，这种粒度正合适。文档测试应该守住入口和关键边界，而不是让每次润色都失败。当前断言集中在文件存在、README 链接、路线信号、根包迁移边界和周期步骤。

## Java 证据检查

Java 证据第一层是新增文档文件。`readability-upkeep-cycle.md` 把五步周期写成表格，并说明每步输出和守护方式。它还要求新版本不能只改讲解，通常要至少改变一个持久项目产物：地图、模型、资料、服务路由、聚焦测试、文档门禁或收口状态。这个规则直接回应用户对“不要做很小粒度”的要求。

第二层是 README 导航。新增周期如果没有进入 README，就很可能被遗忘。v1787 把它加入 `docs/ops/README.md` 的地图表，让维护者从同一个入口看到主题地图、模板、类名试点、路线测试地图、根包压力地图和维护周期。这样的入口对于后期项目非常实用。

第三层是测试。`ReadabilityUpkeepDocsTests` 扩展后，不仅检查文件存在，还检查关键内容。路线地图必须同时提到 registry route 和 audit route，根包压力地图必须强调新 readability 子包和不默认批量重命名，维护周期必须包含五步，并要求不要创建只改讲解的版本。测试把用户的长期规则转成项目门禁。

## mini-kv 证据检查

mini-kv 在本版中继续作为边界说明，而不是输入。维护周期文档明确排除 mini-kv autostart，也排除其他项目变更。Docs test 不读取 mini-kv，不检查 C++ 文件，不要求 mini-kv 运行。Java 可读性保养的文档门禁只守 Java 项目内部材料。

这点看似重复，但实际很关键。用户允许 Java 和 C++ 较自由推进，但当前任务明确只做自己的项目。v1787 的文档周期如果写得含糊，后续维护者可能会把跨项目联动当成默认流程。现在边界写清楚，测试只检查 Java docs，项目就不会无意把外部仓库变成 Java CI 的前置条件。

本版也没有启动浏览器或页面截图。新增的是后端文档和测试，没有前端页面需要自动化检查。按项目规则，只有需要浏览器自动化、页面检查或运行截图时才用相关工具；当前验证重点是 Maven 测试。

## 阻断与安全边界

v1787 阻断两类风险。第一类是运行时风险。文档周期继续排除写路由、主动分片路由、凭据读取、原始端点解析、受管连接、部署回滚、自动启动服务。没有新增运行时代码，因此这些风险没有被打开。

第二类是维护风险。文档如果没有测试，很容易变成“写完即失效”。本版通过 docs test 阻断文档漂移：文件不能消失，README 不能断链，路线地图不能丢 audit route，根包压力地图不能丢不做批量重命名的边界，维护周期不能丢五步和版本工作量要求。这样后续修改文档时必须保留关键约束。

还有一个边界是“不能只改讲解就出版本”。维护周期明确说新可读性保养版本通常要改变至少一个持久项目产物。这个规则不是否定讲解，而是把讲解放回证据链里：讲解解释真实工作，不能代替真实工作。Docs test 检查这句话，避免规则被无意删掉。

## 测试覆盖

本版主要测试是 `ReadabilityUpkeepDocsTests`。它现在覆盖 docs/ops 入口文件存在性、registry template、主题地图、archive map、route map、pressure map 和 maintenance cycle。结合 `OpsCodeWalkthroughArchiveComplianceTests`，文档层既有入口门禁，也有讲解深度门禁。结合前两版的 audit catalog、service、renderer、boundary、controller 测试，当前可读性保养已经从代码到文档都有守护。

定向验证仍然运行 `mvn -q "-Dtest=ReadabilityUpkeep*Tests,OpsCodeWalkthroughArchiveComplianceTests" test`。这个命令可以快速发现 docs 断言、audit 接口和讲解合规问题。收尾前还会运行全量测试，确保文档测试扩展没有影响其他模块。

文档测试的断言刻意保持关键而不琐碎。它不要求文档一字不差，因为文档需要持续优化；它只要求最重要的结构和边界保留。这种测试粒度比快照测试更适合项目文档。维护者可以改写句子，但不能删掉入口、路线、边界和周期。

## 实际工作量说明

v1787 的实际工作量包括新增维护周期文档、更新 docs/ops README、扩展 docs 测试，并编写当前版本中文讲解。它没有新增运行时功能，但它把前三版产出的路线、模型和接口纳入文档门禁。对于后期项目而言，这种门禁是实实在在的维护能力，不是装饰。

这不是硬凑。用户要求每版要有足够工作量和中文讲解，禁止硬凑；v1787 选择把“版本不能只改讲解”写进维护周期，并用测试守住。这等于把用户的协作规则转成项目规则。以后如果有人试图做一个只改讲解、没有持久产物的版本，至少文档会明确说这不符合周期。

本项目的文档结构在这一版更完整。`docs/ops` 现在不只是几张地图，而是有索引、模板、类名试点、路线服务测试地图、根包压力地图和维护周期。维护者可以从索引进入主题，从模板理解代码层，从路线地图追接口，从压力地图理解子包纪律，从周期文档理解版本节奏。这比单篇 README 更稳。

v1787 也把“不要默认批量重命名”再次写进测试。根包压力确实存在，但本项目已经有大量历史接口和证据。没有兼容测试和迁移计划时，默认批量重命名会破坏可追溯性。Docs test 保留这句话，就是为了让后续维护者在看到压力时先想到证据，而不是立刻移动文件。

这版还让文档和代码互相照应。v1786 的 audit route 已经存在，v1787 的 route map 测试要求文档写到它和对应服务测试。这样代码新增不会孤立，文档新增也不会空转。一个后期项目要想长期可维护，就需要这种互相照应，而不是代码、文档、测试各走各的。

维护周期里的五步也为后续批次提供模板。先地图，再模型，再暴露，再守护，最后收口。这个节奏不要求每批都完全一样，但它提醒我们不要跳过关键层。比如后续做另一个只读治理主题，就可以先写地图，再建响应和资料，再暴露接口，再补 docs guard，最后更新版本和 CI 证据。

本版没有打开任何进程，也没有留下临时文件。验证依赖 Maven 测试和文本读取。这样的版本虽然看起来不像新增业务功能那样显眼，但它能让后续业务和治理功能更容易被理解。工程后期保养的价值往往就在这些地方：减少迷路，减少漂移，减少无谓争论。

最后，v1787 为 v1788 收口做好准备。下一版可以把 audit response 版本从 v1786 收口到最终 v1788，补批次 README 状态，运行全量测试，push 提交和 tag，并观察 CI。没有 v1787 的 docs guard，v1788 收口只能说明代码能跑；有了 docs guard，收口才能说明代码、文档、测试和讲解都对齐。

## 一句话总结

v1787 用维护周期文档、README 导航和 docs 测试把 Java 本项目的可读性保养流程固定成可守护规则，确保新增地图、audit 路由、根包边界和版本工作量要求不会在后续维护中漂移。
