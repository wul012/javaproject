# Java code walkthrough writing standard

Reference style:

```text
D:\nodeproj\orderops-node\代码讲解记录\107-production-readiness-summary-v3-v103.md
```

That Node v103 document is the model because it explains the real implementation surface instead of only listing release bullets. Java walkthroughs should follow the same discipline.

## Required rule

It is acceptable for a Java version to have no walkthrough. If a walkthrough exists, it must contain enough implementation detail for a later maintainer to find the code, understand the response/model shape, verify upstream evidence, and confirm the safety boundary.

Short receipt notes can stay in evidence folders, but they should not be presented as code walkthroughs unless they follow this structure.

从 Java v1774 起，新的代码讲解默认使用中文书写，并且每个版本的独立讲解至少包含 3000 个汉字。这个门槛不是为了堆字数，而是为了保证一个版本的入口、模型、服务流程、证据链、测试覆盖、边界和维护意图都能被后来者复盘。达不到 3000 汉字时，应优先加大本项目实际工作量，补足实现面、测试面、文档面或重构面，而不是用空话填充。

`OpsCodeWalkthroughArchiveComplianceTests` 会对 v1774 之后的讲解执行中文长篇门禁：标准章节必须存在，不能使用 legacy marker，汉字数量必须达到门槛，正文不能以英文为主，并且必须包含 `## 实际工作量说明`。以后如果确实需要英文引用、命令或类名，可以保留在正文中，但解释主体必须是中文。

`## 实际工作量说明` 必须说明这一版在本项目中实际完成了哪些源码、测试、文档、索引、拆分、重构、验证或清理工作。禁止硬凑：不能用重复话术、空泛背景、与本项目无关的跨仓库流水账或没有证据的总结来填满篇幅。若本项目工作量不足以支撑 3000 汉字讲解，应继续扩大这一版的真实工程改动，或者把它合并到更有维护价值的版本中。

## Version granularity rule

Do not create tiny Java versions by default. A version should be large enough that its walkthrough can explain a coherent route/model/service/test/boundary story, and small enough that a reviewer can still understand the change in one sitting.

If a planned version can only say "renamed one constant", "added one receipt", or "moved one marker", fold it into the nearest meaningful version. Refactor-only versions are acceptable only when the walkthrough names the maintenance risk that was reduced.

The quality gate registry at `/api/v1/ops/shard-readiness/code-walkthrough-quality-gate-registry` records the active granularity, explanation, evidence, review, and boundary rules.

## Legacy clearance marker

Historical files that predate this standard may be retained with this marker:

```text
legacy-nonstandard-walkthrough
```

The marker means the file is kept only as historical trace material and does not count as a standard code walkthrough. When such a file is rewritten, remove the marker and add the required sections below.

Do not use the marker for new Java versions after v289. New walkthroughs must either follow the required structure immediately or be omitted.

## Required structure

Use these sections unless a section truly does not apply. If a section does not apply, say why in one sentence.

```markdown
# 第<中文或数字>版代码讲解：<scope>

本版目标是...

它不是/仍然不会...

## 入口路由

## 响应模型

## 上游证据配置

## 服务层核心流程

## Java 证据检查

## mini-kv 证据检查

## 阻断与安全边界

## 测试覆盖

## 实际工作量说明

## 一句话总结
```

For Java-only work, `mini-kv 证据检查` may say `本版不消费 mini-kv 证据` and explain the boundary. Do not delete the section when the surrounding roadmap includes Java/Node/mini-kv handoff context.

## What each section must answer

`入口路由`: controller, endpoint, method, route constant, fixture endpoint, or scheduled/test entry. If there is no route, name the service/test entry instead.

`响应模型`: response record, DTO, JSON fields, schema version, readiness flags, and any field whose value proves read-only behavior.

`上游证据配置`: Node plan, fixture path, historical snapshot, catalog entry, environment property, or static contract consumed by this version.

`服务层核心流程`: the service methods and the order in which they compose catalog, fixture, archive, digest, boundary, or response data.

`Java 证据检查`: Java-side archive, fixture, README, catalog, route, or test checks added or preserved.

`mini-kv 证据检查`: mini-kv artifact consumed or explicitly not consumed.

`阻断与安全边界`: execution flags, disabled actions, write blockers, credential/raw endpoint restrictions, audit/deployment/rollback restrictions, and anything that must remain impossible.

`测试覆盖`: exact targeted tests and whether full test execution was run. If not run, state the reason.

`实际工作量说明`: the concrete project-local work that justifies the version size: source changes, tests, docs/index cleanup, refactoring, verification, and cleanup. It must explain why the text is not padding.

`一句话总结`: one precise sentence describing what maintainability or readiness improved while naming the boundary that stayed closed.

## Anti-patterns

- Do not write only four bullets such as "added tests, archived JSON, boundary remains read-only".
- Do not say "read-only" without naming the fields, paths, or tests that prove it.
- Do not claim production readiness when the implementation still exposes `readyForProductionOperations=false`, `executionAllowed=false`, or equivalent blockers.
- Do not mix unrelated versions in one walkthrough unless it is explicitly a closeout document and lists the included version range.
- Do not split one coherent change into tiny versions when the resulting walkthroughs would be shallow.
- Do not add new walkthroughs to an already oversized directory root; create or use a version-range folder.
- Do not mark a new file as `legacy-nonstandard-walkthrough`.
- Do not add a post-v1773 walkthrough that is mostly English or shorter than 3000 Chinese characters.
- Do not hard-pad a walkthrough with repeated prose; increase real project-local work or merge the version instead.
- Do not make another repository the main body of a Java walkthrough; upstream plans may be cited only as boundary context.
