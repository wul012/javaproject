# v1869 优雅门收敛与不可绕过基线讲解

## 实际工作量说明

v1869 是一次治理机制优化，目标不是再增加一组 readiness 字段，也不是把既有类从一个包移动到另一个包，而是修复优雅规则与实际机械检查之间的落差。上一轮质量复核发现，仓库已经把生产 Java 最大文件压到七百三十八行，根 `ops` 目录也准确收敛为一百个控制器和四个共享核心，但长名称门仍只比较三个总数：超长文件名数量、超长标识符出现次数、唯一超长标识符数量。只看总数存在一个明显漏洞，维护者可以删除一个旧长名，同时加入一个完全不同的新长名，只要三个数字不增长，测试仍会通过。这样的门能够阻止债务总量膨胀，却不能兑现“新代码零容忍”和“碰过的文件必须变好”的优雅承诺。

本版把名称债务从三个统计数升级为可审查的精确集合。`config/java-name-baseline.txt` 保存当前所有超过四十字符的 Java 文件路径，以及当前所有超过四十字符的词法标识符。它不是把两万多次出现逐条复制进去，而是对文件路径和唯一标识符去重，因此七千余条记录就能描述完整存量边界。现有出现次数仍由旧门约束，精确集合负责回答“具体允许哪些旧名字”，两个维度组合以后，既不能凭空加入新名字，也不能用同数量交换掩盖债务替换。

工作量还包括一套统一的 Git 变更观察器。它同时理解三种执行时刻：本地未暂存或已暂存的工作树、刚提交但尚未推送的干净工作树、GitHub Actions 检出的单个提交。测试不依赖人工传入基准版本，而是优先读取工作树相对 `HEAD` 的变化；工作树没有 Java 变化时，再读取 `HEAD^` 到 `HEAD`。新增的未跟踪文件通过 `git ls-files --others --exclude-standard` 单独纳入，避免最危险的新文件在本地验证时被漏掉。所有这些改动只进入测试与 census，不改变任何生产类、HTTP 路由、响应模型或运行配置。

## 入口路由

v1869 的入口不是新的 HTTP endpoint，而是维护者运行质量门时进入代码变化事实的路径。第一个入口仍是 `scripts/java-maintainability-census.ps1 -Json`，它保持原有生产和测试源码统计；增加 `-WriteNameBaseline` 后，脚本使用同一套词法规则生成精确名称基线。这样 census 与 JUnit 不会各自发明“什么算标识符”的口径：两者都先移除注释、字符串、字符字面量和文本块，再匹配 Java 标识符，并以四十字符作为唯一阈值。

第二个入口是 `GitChangeSet`。它把 Git 命令限制在 `src/main/java`、`src/test/java` 和 `docs` 三类明确路径，不扫描归档，也不读取兄弟仓库。Git 在子目录执行 `diff` 时可能返回仓库根相对路径，而 `ls-files` 可能返回项目相对路径；第一次聚焦测试正是在这里失败，路径被错误拼成两次 `advanced-order-platform`。修复后，所有 Git 输出先规范为斜杠，再剥离 `git rev-parse --show-prefix` 返回的项目前缀，最后才解析为本项目绝对路径。这个转换集中在一个方法里，后续门不再各自猜路径基准。

第三个入口是两个 JUnit 类。`JavaEleganceGateTests` 负责存量基线与共享路由、SpotBugs 预算；`JavaChangeGateTests` 负责当前版本新增和触碰的文件。两者分工明确：前者保证旧债只能减少，后者保证新债不能进入。完整 `mvnw verify` 会自然执行它们，CI 不需要增加一条容易漂移的自定义 shell 步骤。由 Maven 统一调度也意味着 Windows 本地、Linux Actions 和开发者 IDE 看到的是同一失败条件。

## 响应模型

名称基线采用最小的两列文本协议。以 `F` 开头的行表示一个超长 Java 文件路径，以 `I` 开头的行表示一个超长词法标识符；注释行说明版本来源与只减不增规则。路径统一使用仓库内的正斜杠形式，标识符保留 Java 源码中的精确大小写。这个模型刻意不存储时间戳、机器绝对路径、扫描顺序或重复次数，从而避免不同机器产生无意义差异。出现次数仍由既有三个数值预算负责，基线只保存身份集合。

JUnit 读取基线时拒绝未知记录类型、重复文件路径和重复标识符。随后它重新扫描实时源码，构造同样的两个集合，并要求与基线完全相等。这里使用“完全相等”而不只是“实时集合是基线子集”，是为了防止已经删除的旧债长期留在基线中，日后又被悄悄重新引入。只要代码消除一个长名，维护者就必须同步重新生成基线；如果代码新增一个长名，基线也必须改变，而下一道父提交比较会拒绝任何新增记录。

父提交比较根据执行阶段选择来源。本地修改基线时，当前 `HEAD` 中的基线就是上一版；CI 检出新提交且工作区干净时，`HEAD^` 中的基线就是上一版。v1869 是首次建立基线，父提交没有该文件，因此只在这一版跳过历史比较；从 v1870 开始，当前集合必须同时满足实时源码精确相等、相对上一版集合只减不增。这个一次性引导条件由 Git 对象是否存在决定，不使用可以永久开启的布尔开关。

## 上游证据配置

上游事实只有当前 Java 仓库的 Git 历史与源码树。`GitChangeSet` 不调用 GitHub API，不读取远端分支，也不要求网络。版本开始时仍按仓库规范执行 `git fetch javaproject --tags --prune`，确认本地与 canonical remote 对齐；进入测试以后，门只使用已经检出的对象和工作树，因此离线复现仍然成立。远端 CI 的职责是用 Linux checkout 再次运行同一门，而不是提供门所需的数据。

`java-maintainability-census.ps1` 继续使用 `StreamReader.ReadLine()` 计算行数，没有退回会遗漏空行的 `Measure-Object -Line`。名称扫描也继续从 UTF-8 文件读取完整源码。新增基线写入使用无 BOM 的 UTF-8，并以 ordinal 顺序排序，避免区域设置影响文件差异。脚本先扫描生产和测试源码各一次，再同时服务 JSON 摘要与基线生成；没有为了新输出把五十秒级 census 重复执行两遍。

现有三个总量预算保持原值：生产超长文件路径一千二百九十七个、超长标识符出现二万一千一百六十九次、唯一名称二千八百五十七个；测试对应七百九十五、一万零二百二十六和三千八百三十四。v1869 新增的测试文件及所有新方法名都在四十字符以内，所以这些基线没有上调。未来重命名或数据驱动重构只能让数值下降；任何放松测试期望来迁就新增债务都属于版本失败。

## 服务层核心流程

本版没有触碰订单、库存、支付、Outbox、失败事件审批或重放服务。这里所说的“服务层流程”是优雅门自身处理一次提交的流程。首先，变更观察器收集工作树中已跟踪文件的完整 `git diff HEAD`，再并入未跟踪 Java 文件。若两者都为空，它认定自己处于提交后或 CI 场景，改为读取 `HEAD^..HEAD`。这样同一版本在提交前和提交后不会得到两套相反结论。

名称门逐个读取变化中的 Java 文件。文件 stem 超过四十字符立即失败；去除注释与字符串后的任一标识符超过四十字符同样失败。它不因为这个名字已经存在于存量基线而放行，因为“碰过的文件必须达标”正是童子军规则的含义。对于历史超长类，维护者若必须修改它，就要先提取短抽象、重命名类并同步所有引用、SpotBugs FQN 与测试，而不能继续在旧长名上累加逻辑。

源码增量门读取 `src/main/java` 的 numstat。普通功能版本新增行不能超过四百；若新增行超过四百，只有删除行不少于新增行的重构才可通过。这个规则允许把一个巨型实现拆成多个短文件而不惩罚机械迁移，同时拒绝以“重构”为名净增加大块生产逻辑。未跟踪生产文件没有 numstat，门会直接按 UTF-8 实际行数计入新增量，避免新文件再次成为盲区。

family 门按新增 Java 文件的父目录分组。当同一包一次新增三个或更多文件时，至少一份本次变化的 Markdown 必须含有不超过十行的 `Family design` 小节，并明确写出抽象、数据边界和行为边界。它不能证明两个类在语义上百分之百相似，却能机械阻止“先批量生成，后面再考虑抽象”的惯性。真正的结构相似仍由评审结合代码判断，门负责让设计意图在第三个文件出现前可见。

## Java 证据检查

第一次正向聚焦运行编译一千四百八十三个生产源和八百八十五个测试源，`JavaEleganceGateTests`、`JavaChangeGateTests`、`JavaMaintainabilityBudgetTests` 与构建配置测试共十三项。它没有修改任何期望来通过，而是先暴露两个路径错误：Git diff 输出带项目目录前缀，导致本地绝对路径重复；相对基线路径直接与绝对项目根做 relativize，触发不同 Path 类型异常。修复集中在 `GitChangeSet`，测试代码和四十字符阈值保持不变，第二次运行十三项全部通过。

为了验证门确实会失败，本版临时创建了一个五十六字符 stem 的 Java 测试文件。只运行 `JavaChangeGateTests` 时，构建准确失败在 `changedJavaUsesShortNames`，报告实际值五十六、允许值四十，并指向临时文件的完整路径。随后使用补丁删除临时文件，再复跑绿色。这个负向实验不进入 Git 历史，不写入归档，也不靠阅读测试源码推测效果；它提供了“门在违规时真的会关”的直接证据。

基线本身还接受三重检查。实时源码集合必须与文件逐项一致；当前基线相对上一提交只能删除；旧的总量预算仍必须不增长。有人若把一个新长名写入基线，实时相等可能通过，但父提交集合检查会失败；有人若只删除基线行而不改源码，实时相等会失败；有人若在旧名字上增加大量使用，总量出现次数会失败。三层门分别覆盖身份、历史方向和使用规模，没有单个数字承担全部语义。

## mini-kv 证据检查

v1869 不修改 mini-kv、Node 或 aiproj，也不改变 Java 提供给它们的只读证据契约。名称基线只扫描本项目 `src/main/java` 与 `src/test/java`，不会把兄弟仓库路径写入配置，更不会触碰 Node 固定的 Java 历史归档绝对路径。跨项目成熟度标签继续保持“显式环境变量、单机、只读、无执行权”，本版治理门不能被解释为新的运行集成能力。

mini-kv 在这里提供的是方法上的参照：它的归档与代码规模也使用只减不增 census，而不是靠整理报告自称变小。Java 名称门沿用同样原则，但对象从文件数扩展到具体名称集合。两个仓库不共享实现代码，也不需要同步提交；共同点只是证据必须由可重跑命令产生，历史 fixture 和归档不能为通过新门而改写。

Node capstone 仍可读取 v1868 及后续 Java jar 的既有 evidence endpoint。因为 v1869 没有生产源码变化，不需要重跑跨项目 live capstone；完整 Java verify 与既有 contract tests 足以证明字节边界未被触碰。如果后续优化进入生产服务或响应类型，再根据实际契约影响决定是否重跑 Node 侧真实消费，而不是每个测试工具改动都制造一次跨项目仪式。

## 阻断与安全边界

优雅门只读取 Git 元数据和源码文本，不执行被扫描代码。它不启动 Spring、RabbitMQ、数据库或 Docker，不读取 credential value，也不改变文件权限。Git 命令固定为 diff、status、ls-files、rev-parse 和 show；没有 checkout、reset、clean、commit 或 push。即使门运行失败，工作树内容仍由维护者控制，测试不会自动回退或覆盖文件。

名称扫描先剥离字符串和注释，避免稳定路由、JSON 字段、错误消息或证据文本因长度被误判为 Java 标识符。这个边界尤其重要：很多只读 contract 字符串本来就需要完整表达业务含义，四十字符预算约束的是代码符号，不是外部协议内容。文本块同样先被移除，防止 Markdown 模板中的长单词污染结果。反过来，真正的类名、方法名、字段名和局部变量都属于扫描对象，不能借助换行或格式化规避。

生成上限只读取生产源码，测试与讲解不计入四百行功能预算，但它们仍受文件尺寸与名称门约束。删除支撑的净不增长豁免只适用于行数判断，不自动授予行为变更权；任何路由、schema、fixture 或执行边界变化仍要由对应契约测试审查。family 说明也不是豁免单，写了设计说明仍必须满足名称、尺寸、覆盖率和安全边界。

## 测试覆盖

v1869 的验证顺序是：先运行原始 census 确认起点，再生成精确基线；执行 Spotless 与十三项聚焦门；进行一次预期失败的超长文件负向实验；删除临时文件并恢复绿色；完成本篇讲解和归档 manifest；最后运行完整 `mvnw -B verify`。完整验证会覆盖全部业务测试、文档契约、JaCoCo 包级阈值、SpotBugs 排除基线、Spotless 与制品打包。讲解必须在最终 verify 前存在，确保归档和讲解门验证的是最终文本。

本版不以新增测试数量作为价值指标。两个新测试类的价值在于它们改变了失败面：过去只有总量增长会失败，现在新长名、触碰旧长名、过大的净新增源码和未经说明的新 family 都会在提交进入 canonical remote 前失败。测试代码本身保持短名称，没有用一个新的巨型治理类替代旧漏洞。Git 进程退出码与输出被封装为不可变结果，不再使用可能受并发测试影响的静态可变退出码。

最终 verify 后还要重新执行 census，确认生产文件数与最大行数未变化，测试源只增加两份短名治理文件，长名三个预算保持原值。归档只允许增加本篇 v1869 讲解，历史 manifest 的每个旧摘要必须保持一致。提交、tag 与 push 后，中间 CI 只确认已经启动；后续优化版本开头检查其结论，最终优化版本再等待双 job 全绿。这符合长批次不空转等待、失败优先修复的项目纪律。

## 一句话总结

v1869 把“不要再写难看的长名字”从一条容易认同、也容易绕过的文字要求，变成了能够识别具体旧债、拒绝任何新债、约束触碰文件并跨本地与 CI 保持同义的机械门。它没有让一千多个历史长文件瞬间消失，但从这一提交开始，存量只能逐项减少，不能通过交换名称或更新总数把债务重新包装。禁止硬凑规则数量，真正的价值是让下一轮业务核心解耦和 ops 去重发生在一个不会继续欠新债的地基上。
