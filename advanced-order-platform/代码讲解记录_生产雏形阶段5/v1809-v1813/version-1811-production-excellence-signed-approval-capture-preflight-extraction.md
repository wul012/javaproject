# v1811 操作员证据取值供给·签批·捕获预检注册表迁出代码讲解（J21）

本版本是 v1796 根包治理清查之后的第十四次契约保持型迁出，编号 J21。它处理的是“操作员证据取值供给·签批·捕获预检”这一组只读注册表。简单说，这一组代码不是在系统里真的签署审批，也不是把审批材料落成工件，而是在签批链路进入“捕获工件预检”之前，先把需要被检查、需要被阻断、需要被证明仍然只读的条件列出来。它的价值不在于产生业务状态，而在于把一个危险动作之前的所有前置证据摆成可审计的、不可变的响应。v1811 做的事，是把这组实现从拥挤的根 `ops` 包中迁入 `ops.maintenance.signedapprovalcapturepreflight` 子包，保留对外路由和控制器位置不变，所有 HTTP 路由字符串、响应字段、响应内容和只读边界逐字保持。

## 这一组代码到底在链路里做什么

签批相关家族可以按一条流水线理解：先有上游的 `ApprovalPreflight`，它确认审批前置条件、身份别名、时间窗口、导入防火墙、脱敏摘要、零值计数等基础边界；接着进入本版处理的 `SignedApprovalCapturePreflight`，它把“准备捕获签批证据”需要引用的输入、声明、策略和阻断原因排列出来；再往后才是 v1810 已经迁出的 `CaptureArtifactPreflight`，也就是把捕获结果整理为工件片段之前的预检。三个阶段听起来相近，但职责不同。`ApprovalPreflight` 像是检查能不能进入审批准备阶段；`CapturePreflight` 像是检查能不能安全地描述一次捕获；`CaptureArtifactPreflight` 像是检查能不能把捕获描述切成后续工件片段。

本版的家族不会创建签批、不会保存签名、不会读取真实密钥，也不会连接外部系统。它的输入不是用户提交的可变业务请求，而是代码内固定的只读目录、策略、声明和上游端点引用。它的输出是一组响应对象，里面包含版本、端点、profile、捕获输入条目、捕获声明条目、捕获策略条目，以及警告和阻断说明。维护者访问这些端点时，看到的是“如果要进入签批捕获，哪些输入必须被证明存在，哪些输入只能是别名或摘要，哪些动作被明确禁止”。这就是它的实际价值：把高风险流程的边界提前讲清楚，并用自动化测试确保这些边界不会因为后续重构而散掉。

## 入口路由

入口层仍然由两个根包控制器负责。`FoundationController` 暴露基础类端点，包括目录、模板摘要绑定、复核摘要绑定、操作员输入镜像和时间窗口；`AssuranceController` 暴露保障类端点，包括通道签名策略、声明理由、来源证据、脱敏溯源、失败即锁和收尾。控制器的输入是普通 GET 请求，路径仍由根 `OpsShardReadinessRoutePaths` 聚合器声明；控制器不接收请求体，不读取凭据，不启动流程。控制器的输出是对应服务返回的 `OpsShardReadinessOperatorEvidenceValueSupplySignedApprovalCapturePreflightResponse`。

服务层负责把固定目录装配成响应。每个服务都有一个 `ENDPOINT` 常量、一个 `PROFILE` 常量和一个只读方法。比如目录服务返回全部输入、全部声明和全部策略；模板摘要服务只取输入目录的一段、声明目录的一段、策略目录的一段，然后交给 support 组装；失败即锁服务会输出锁定原始密钥、签名材料和审批授权的证据说明。服务层的输入仍然是静态目录切片和固定字符串，输出是不可变响应对象。迁出前这些服务在根包中直接读取包级可见的全局路由聚合器；迁出后它们改读 `ops.maintenance.signedapproval` 中已经公开的族路由常量类，并且本版只给这个族路由常量类补了公开 `BASE_PATH`。因此端点字符串仍然是同一个基础路径加同一个后缀，改变的是代码所有权，不是对外契约。

## 响应模型

目录层分成三类。`InputCatalog` 记录 25 个捕获输入，每一项包含输入编码、源字段、阶段、要求、阻断理由、证据文件标识、证据片段标识和源端点。`AttestationCatalog` 记录 25 个声明，表达哪些条件已经被镜像、哪些条件仍然只读、哪些条件不能升级为真实授权。`PolicyCatalog` 记录 20 个策略，覆盖通道、签名、脱敏、来源证据、失败即锁等约束。目录层的输入是硬编码的只读条目，输出是不可变列表。support 层再把这些列表复制成不可变集合，并构造响应中的段落文本。这样做的好处是，控制器、服务、目录、响应的职责分明，未来继续迁移或压缩长类名时，不需要把“端点路由”和“证据条目”揉在同一个文件里。

## 这次为什么选择它

v1810 已经把下游的 `CaptureArtifactPreflight` 迁走，并且发现它的 `FragmentCatalog` 会读取本家族的十个服务端点。因此，`CapturePreflight` 留在根包里时，根包已经同时承担了本家族自身实现、下游片段目录引用和根控制器入口三种职责。它是一个自然的下一刀：路由叶子类早在 v1804 就已经进入 `ops.maintenance.signedapproval`，大部分服务端点在 v1810 已经为了下游片段目录变成 public，控制器又可以留在根包不动。换句话说，最难改变的对外路由已经提前解耦，本版可以集中处理实现所有权。

实际迁移时，生产代码共移动十六个非控制器文件，包括目录服务、输入目录、声明目录、策略目录、响应记录、support、十个服务实现。两个控制器没有移动，因为它们仍然是公开路由入口，继续留在根包能避免改变 Spring 扫描和路由聚合的外观。测试侧移动六个纯家族内部测试，保留两个控制器测试和一个路由常量测试在根包。这个分层很重要：只要测试还需要直接证明根聚合器、根控制器和族路由常量之间的等价关系，它们留在根包就合理；只验证目录、support 和服务响应形状的测试，则应该跟随实现进新子包。

## 上游证据配置

这次最需要透明说明的是两条跨家族端点边。第一条是出向边：迁走后的 `InputCatalog` 仍然要引用十一个上游 `ApprovalPreflight` 服务的 `ENDPOINT`，因为每个捕获输入都要说明自己的源证据来自哪里。涉及的上游端点包括目录、收尾、摘要蓝图、身份签名、导入防火墙、溯源绑定、脱敏摘要、时间窗口、值拒绝、零值账本和归档计划。它们仍然在根包，没有被本版搬走。本版只把这些服务类已有的 `ENDPOINT` 常量公开为不可变字符串，并在新子包里显式导入。这样做的含义很窄：新包可以读取“上游只读端点地址”，但不能调用上游业务方法、不能改变上游响应、不能扩张上游职责。

第二条是入向边：v1810 已经迁入 `ops.maintenance.signedapprovalcaptureartifactpreflight` 的 `CaptureArtifactPreflightFragmentCatalog` 会读取本家族十个服务端点，用于说明捕获工件片段来自哪些捕获预检证据。迁出后，这个下游目录不能再从根包导入这些服务类，所以本版把它的 imports 改到 `ops.maintenance.signedapprovalcapturepreflight`。这条边同样只发生在端点字符串层，不涉及服务调用。端点字符串作为证据地址被引用，是当前项目历史结构下可以接受的妥协；真正的执行仍然没有跨包启动。

第三类不是家族之间的业务耦合，而是留在根包的控制器和路由测试对新包类型的编译依赖。控制器构造函数需要注入服务，控制器方法需要返回响应记录，所以服务类和响应记录必须是 public。路由测试需要比较根聚合器、族路由常量和服务 `ENDPOINT` 的一致性，所以 catalog 服务的 `ENDPOINT` 也必须公开。这里的公开不是扩大业务能力，而是让公开入口仍能装配和证明被迁出的实现。

## 服务层核心流程

服务层核心流程可以概括为三步：先由服务常量确定只读端点，再从输入、声明、策略目录中截取对应证据段，最后交给 support 构造响应记录并复制为不可变集合。迁包前后这三步没有变化，变化的只是服务常量引用的路由 owner 从根聚合器改成了公开族路由常量类。这个流程的透明性很重要，因为只要服务层不接收请求体、不读取密钥、不写数据库，控制器暴露再多只读 GET 端点，也仍然停留在证据说明层。

## 为什么不是继续留在根包

根 `ops` 包的问题不是某一个文件坏，而是它长期承载了太多互不相同的维护主题。每多一个注册表家族留在根包，后续维护者定位代码时就要在上千个文件里搜索，测试护栏也更容易把“入口必须留根包”和“实现可以外迁”混为一谈。本版把根包直接 Java 文件数从 1,121 降到 1,105，数字本身只是表象，真正的收益是所有权更清楚：签批捕获预检的实现、目录和响应都在一个窄包中；公开控制器和全局路由聚合器才继续留在根包。

这种拆分还有一个长期好处。现在的类名很长，是因为旧结构必须把完整上下文都塞进类名里。一旦同类实现稳定进入 `signedapprovalcapturepreflight` 子包，未来如果要继续做可读性优化，就可以在不损失语义的前提下考虑更短的局部类名和更清晰的目录分组。也就是说，包迁移不是终点，而是后续安全改名和拆分的前置条件。没有包边界，贸然缩短类名只会让维护者更难判断文件归属；有了包边界，名字才有缩短空间。

## Java 证据检查

本版遵循编译器优先的方式。第一次编译暴露了机械替换造成的重复 `public` 修饰符，说明批量公开常量必须再做文本检查。第二次编译暴露了 `InputCatalog` 对上游 `ApprovalPreflight` 的真实引用，这也印证了前面“不要只靠单行 grep 判断端点边”的经验。因为这些引用很多写成类名一行、`.ENDPOINT` 下一行，简单的单行正则很容易漏掉。最终边界以 javac 为准：缺哪条导入、哪个常量仍是包内可见，编译器会直接指出。

## 测试覆盖

新增的 `ReadabilityUpkeepOpsConsolidationExtractionV1811Tests` 做四件事。第一，确认 `docs/ops/signed-approval-capture-preflight-extraction-v1811.md` 能从 ops README 发现，防止版本说明写完后无人能找到。第二，确认代表性实现文件已经在 `ops.maintenance.signedapprovalcapturepreflight`，并且不再出现在根 `ops` 包。第三，确认两个控制器和根路由聚合器仍在根包，保证公开入口没有被顺手搬走。第四，把根包文件数护栏压到 1,105，防止后续新增实现时又把根包当作默认落点。除此之外，原有 route-path 测试仍然比较根聚合器、族路由常量和服务端点，证明路由取值没有漂移。

## mini-kv 证据检查

本版没有触碰 mini-kv。签批捕获预检家族输出的是 Java 侧只读证据说明，不读取 C++ 键值数据，不建立 mini-kv 网络连接，不修改 WAL、快照、RESP 命令处理，也不移动 mini-kv 的 `e/` 归档。即使响应文本里提到来源证据和运行边界，也只是把 Java 注册表自己的只读端点关系说清楚，不会把任何请求转发到 mini-kv。四项目协作规则里要求 Java、Node、mini-kv 的历史证据路径稳定，本版严格停留在 Java 项目内部。

## 阻断与安全边界

本版不碰运行时能力。它不打开写路由，不启用活跃分片路由，不读取凭据值，不解析原始端点，不建立受管审计连接，不部署，不回滚，不启动 Java、Node 或 mini-kv 进程。它也不移动任何归档目录，不改 `a/` 到 `f/`，不改 `e/<version>/`，不重命名历史证据 JSON，不整理历史截图路径。原因很简单：Node 侧和其他项目可能引用 Java 历史归档路径，代码包迁移不能顺手做归档迁移。结构治理要一刀一刀做，不能把“实现归属变清楚”和“历史证据路径重排”混成一个风险面。

## 实际工作量说明

这版的真实改动包括：移动十六个生产实现文件和六个家族内部测试；更新新包 package 声明；把服务端点从根路由聚合器改指公开族路由常量；给 `OpsShardReadinessSignedApprovalCapturePreflightRoutePaths` 增加公开 `BASE_PATH`；补齐根控制器、根路由测试、v1810 下游片段目录和新包内部目录对跨包类型的导入；公开十一个上游 `ApprovalPreflight` 服务端点常量；公开本家族 catalog 端点常量以服务根包路由测试；更新 SpotBugs 响应类豁免包名；新增 v1811 短说明、中文长讲解和 readability 护栏；下调三个现有根包计数护栏。这里明确遵守本项目的讲解规则，禁止硬凑字数，也不把无关仓库或虚构工作写进来。它不是改业务逻辑的大版本，但它是维护性的大版本，因为它把一整组签批捕获预检实现从根包中剥离出来，同时把跨家族端点边界写清楚、测清楚。

## 一句话总结

v1811 把“签批捕获预检”这一只读注册表家族迁入 `ops.maintenance.signedapprovalcapturepreflight`，根包直接文件数从 1,121 降到 1,105；公开控制器和路由聚合器保留在根包，服务改用 v1804 已外迁的公开族路由常量，跨家族关系只通过公开不可变 `ENDPOINT` 字符串表达，所有路由、响应和安全边界保持不变。
